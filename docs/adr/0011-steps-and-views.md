# ADR-0011: Turns run in steps, and shared state is views folded from their effects

- **Status:** Proposed
- **Date:** 2026-10-13

## Context

Actors share nothing, and yet the engine has state that many of them read: which actors there are, where each kind's head points, whether everything one piece of mail set in motion has finished. Each of these is changed by many actors' turns and read by many others.

The earlier engine built a structure for each. Each needed its own layout, its own rule for who writes, its own argument for why a reader is safe, and its own tests, and the structures changed at different moments from one another (ADR-0008). Whoever needed the next piece of shared state had to invent another.

The first piece built here went the same way. The table of actors (ADR-0008's `ActorTable`) numbered its changes from one count so that a reader could hold a number. Measured on 32 threads, that count let fewer actors be spawned in a second than one thread managed alone. Two repairs were built and measured, and each was a further invention for this one table.

A turn already says everything it wants of the engine as a list of effects (ADR-0009's `What`). That list is a record of what happened.

## Decision

**There is one way to share state: turns leave effects, a view is folded from them, and a turn reads the view.** Nothing else is shared between actors, and no view is built by hand around a lock or an atomic.

**Turns run in steps.**

- Every actor that has mail when a step begins runs in that step. They run side by side on the engine's workers, and no turn in a step sees what another turn in it did, except a fused turn, which sees the table changes of its own run (ADR-0013).
- An actor handles the mail it had when the step began, in the order ADR-0009 gives, one turn for each piece.
- Mail sent in a step is handled in a later one, unless it is fused: handed to an actor in the same part and handled in the same step (ADR-0013).
- A step has a number, and steps are numbered upward from one count that only the engine advances, once a step.

**A step carries the time.** The engine reads no clock (ADR-0001). The host passes the time in when it starts a step, and every turn of that step reads that one time. A record of a run holds each step's time beside its number. Knowing the time does not run an actor: an actor runs when it has mail.

**A view is a fold over the effects of finished turns.** Its author writes what the view keeps of an effect, and how one such record changes the view's state. The author writes no lock and no atomic, and nothing about workers.

```rust
pub trait View {
    type Shard;                 // one part of the view's state
    type Record;                // what the view keeps of an effect

    /// The keys and records of an effect, one for each key it changes, emitted in `context`.
    fn takes(effect: &Effect, context: &Context) -> impl Iterator<Item = (u64, Self::Record)>;

    /// Folds one record into the part its key falls in.
    fn fold(shard: &mut Self::Shard, key: u64, record: Self::Record);
}
```

**Only the engine defines a view, for now.** The views are the ones the engine itself needs, and actors share everything else by mail. The engine's own views go through the interface above, so that a view defined outside the engine is later an addition.

**The engine keeps each view, and it does the same for every one.**

- While a step's turns run, they read the view and nothing writes it.
- When the step's turns have finished, their effects are folded into the view, and then the next step begins.
- Reading and folding never happen together, so the view needs no lock, and the program is checked for that when it is built.
- A view's keys are spread over parts, and the parts are folded side by side.

**A turn reads a view as it stood when its step began.** The view is not written while turns run, so every read in a turn agrees with every other. A view is one step behind: a turn never sees an effect of its own step, except that a fused turn sees the spawns and endings of its own run (ADR-0013).

**The step's number is the position of every view.** A record of a turn holds its step's number, and that number is all it needs to read the same views again.

**Who may write a key is limited, so that order between actors never decides a view.**

- A key has one owner, and only its owner's effects change it. The owner's records reach the fold in the order it asked for them. A child's place belongs to its parent, and a kind's head to its library (ADR-0008, ADR-0009), so these are settled where the effect is asked for.
- Or many actors write one key, through a fold that gives the same result in whatever order their records arrive: a count, a set.
- A key that many actors write and the last one wins is not allowed.

**Mail that reaches an actor in one step is put in a fixed order**: by its sender, then in the order that sender sent it. Mail from one source keeps its order, as ADR-0009 requires. Between two sources the rule promises an actor nothing, and the fixed order is there so that the same turns always leave the same result.

**The last view to fold a turn may take its effects by value.** Nothing reads an effect after that view, so what it keeps of an effect is moved in, not copied: the stream of what each actor reacts to takes a mail's bytes this way. Every other view borrows the effects.

**A view folds each effect with the context it was emitted in.** A turn's effects share one context, the item the turn handled (ADR-0012), and a view is handed it beside each effect. The context is what is folded, not a view that is read, so it plays no part in the order views fold in.

**A view reads no other view.** Each folds by itself, from the effects and their context, so every view and every part of one can fold at once, in any order, wherever the engine folds it. What a view would have read of another is worked out where the effect is made, or kept by the view itself. A turn resolves whom its mail is for when it sends it, from the table as the step began (ADR-0009). Two records that must meet are kept under one key, so they land in one part: a watch and the ending it waits for are both kept under the actor watched.

**A worker routes its turns' records as each turn finishes.** Each worker keeps a row of buckets for each view, one bucket for each part, and puts each record of a finished turn in the bucket of the part its key falls in. When the step's turns are done, each part folds its column: the bucket every worker filled for it, one worker after another. A key with one owner gets its records from the one worker that ran the owner's turns, in order. Measured on 16 workers at 10,000 actors, this halves the time to apply a step. On one worker the step is 5 to 7 percent slower: each record is stored in a bucket and read back before it is folded. A turn that asks for nothing is not routed, and a worker keeps one list of what its turns ask for over its whole share of the step, so a turn moves the worker's lists neither in nor out: measured on one worker, a turn that asked for nothing took about 55 ns where it took about 110, and a piece of mail at 10,000 to 100,000 actors cost 7 to 12 percent less. A finished turn's effects are routed in one pass, each effect into every view before the next is read, where each view once read the whole list in turn: measured on one worker, a turn that sent 1,000,000 pieces of mail took about 90 ms where it took about 107, and a piece of mail at 10,000 to 100,000 actors cost 8 to 14 percent less. The stream's records are the entries a part keeps, so a part takes a writer's bucket of mail whole: in place of its own list when nothing has arrived yet and the list has no more room than the bucket, or added to its end, so no record is read one by one and no writer's bucket gains room it did not need. Measured on one worker, a step that sent 1,000,000 pieces of mail took about 60 ms where it took about 94, and applying a step at 100,000 actors took about 1.6 ms where it took 2.7.

**The watches settle once a step's records are all in.** Who watches each actor is a view of its own, kept under the actor watched, so a watch and the ending it waits for meet in one part. Records reach a part in any order, so a watch and an ending of one step are paired when the step's records are all folded, not one at a time. Each part of the watches then hands an ending on for each actor watching the one that ended, and the engine puts it in that actor's stream: last of what the actor that ended caused. The watches read no other view, and the stream's buckets hold nothing but mail. A watch carries how the turn that asked for it saw the actor watched, worked out where the effect is made: live, when the table held it as the step began or it was stood up since, and ended otherwise. So the watches keep an actor only while its ending is still to come, and nothing of it once its watchers are shown: a watch of an actor that ended before the step is shown `Earlier` at once, and one of an actor whose closing turn runs in the step is paired with its ending.

**The table of actors is the first view.** It is folded from spawns and endings. Where a library's heads point is a view (ADR-0009). Who watches each actor is a view, and whether a chain of mail has finished is one when it is built. How far each actor's life has gone, the mail it has sent and whether it has ended, is a view, so the engine keeps beside its actors only what is fixed when one is seated: where it stands and its kind.

**When a step's turns have finished, the engine folds; an actor's items are handed to it when it runs.** Mail is kept under the actor it is for, whether or not that actor is still live, and the engine hands an actor its items only when the actor is live. Items for an actor that is not are dropped there, unhanded: one never made, one gone, or one that has ended, which runs its closing turn instead. So a child spawned in a step is there for mail sent to it in that step. The endings of a step are folded for the actors that watch them (ADR-0009), and a watch asked for in the step its actor ends is shown that ending once.

**Memory is freed on the thread that made it.** A worker's lists of effects, turns, and actors are handed back to it emptied and filled again the next step. The streams keep each part's items in one list, filled as the step's effects are folded and put in order once when the next step is planned; the workers read each actor's run of it where it lies, and it is emptied on the thread that steps the engine, which filled it. Measured on 4 workers, a list made on one thread and freed on another made each worker's share of a step take about three times as long.

**A step reuses what it hands out.** The lists a worker fills, the parts it runs and folds, the buffers parts are packed in, and the tally of how long turns took are emptied and kept from one step to the next for their room, so a step allocates nothing once its lists have grown to it but the list of shares it hands the host and the list of folds. A worker's lists stay with the slot it runs in, so the same thread fills them each step: pooled and handed to whichever worker asked next, they moved between cores, and a step of 100,000 actors on 16 workers took about 10 percent longer. Measured on two actors sending one piece of mail back and forth, a step made 32 allocations, and took about 2.2 µs; with them reused, 2, and 1.75 µs.

**A native host pins each worker to a core, and keeps the thread that steps the engine to the first workers' cache.** A step's memory stays warm in the cache of the core that uses it, so a worker that moves loses it. A step's shares go out from the stepping thread and its records come back to it, so the cores are taken from one group sharing a last-level cache until it is full before any from the next, with a core's second hardware thread only after every core's first, and the stepping thread is kept to the first group. It is kept to the group and not pinned to one core, where the scheduler can wake it on any of the group's cores after it sleeps through the workers' run: pinned to one core, it made a piece of mail on 4 workers at 10,000 actors about two thirds dearer, and on 2 workers in `fjthrput` about a quarter dearer. It is let back onto every core when the host stops. Measured on groups of four cores, against one worker from each group in turn and the stepping thread left to the scheduler: on 2 to 4 workers, `churn-wide` mail cost 27 to 34 percent less, `fib` 22 to 26 percent less, and 10,000 busy actors 12 percent less; on 16 workers, 100,000 busy actors cost 22 percent less; the rest were within noise. The cost is the cache one group holds: 100,000 busy actors on 4 workers cost about 20 percent more, as the step's memory no longer fits in one group's cache. Pinning the workers at all made a piece of mail 25 to 30 percent cheaper at 10,000 to 100,000 actors on 16 workers.

**The bytes of mail in flight come out of a quota the host gives.** Each writer writes the mail its turns send into an arena of its own, one for each parity of step, since mail is read in the step after the one it is sent in and no later; an arena is emptied, keeping its slab, when its writer's turn to write it comes round again. The host gives the engine a quota for all of them, and each step's plan gives every writer's arena an equal share, so a turn that sends a great deal writes into its slab and not into an allocation for each piece. Mail past a writer's share is spilled into bytes of its own, kept by the arena and freed when it is emptied. Measured at 100,000 actors on one worker, with slabs of 64 KiB where the quota gives each a share of a gigabyte, most pieces were spilled, and freeing them took 4.7 ms of each step's plan; with the share, 0.2.

**An actor is named by its id and its seat.** The engine numbers a seat for each actor it runs and keeps what it holds of the actor by that number. A reference carries the actor's seat beside its id, and so does every effect, for the actor that asked and for the one it names, so a record for an actor is kept under its seat with no lookup, the plan reads the seats front to back, and the workers run their actors in that order. A seat is the actor's for its whole life and is taken again once the actor has gone, so the id says whether the actor in a seat is the one named, and an item for an actor that no longer sits there is dropped. The seats are kept in the views' parts, part `p` holding every seat numbered `p` more than a multiple of the number of parts, with its actors, its empty seats, and its next new number. A worker seats the children its turns spawn as it runs them, in parts of its own: their empty seats, handed to it as the step begins, then new numbers in whichever of its parts has numbered fewest, so new seats spread across parts and no two workers give the same. A seat means nothing outside its engine, so a reference that crosses a boundary is written as its id alone and finds its seat again in the table that proves it where it is read. Measured at 10,000 to 100,000 actors, a piece of mail costs 4 to 17 percent less on one worker and 12 to 26 percent less on 4 and 16.

**A view of each actor keeps it under its seat.** A part of such a view holds every `parts`th seat in a list, front to back, with the id of the actor kept in each, so finding an actor is reading one place, and a lookup for any actor but the one kept there finds nothing. The number of parts is rounded up to a power of two, so the part a seat or key falls in is a mask and its place there a shift: measured at 100,000 actors, dividing by the number of parts instead on every lookup made a piece of mail about 8 percent dearer. Liveness and the log are kept this way. Keeping a value for a new actor in a seat drops the one kept for the actor before it, so a log is kept until another actor takes the seat and logs, and a log worth keeping longer is copied out before then. The table stays keyed by id, since it is where an id alone, from a path or from a reference read across a boundary, finds its seat. Measured at 10,000 to 100,000 actors, a piece of mail costs 5 to 20 percent less on one worker and 7 to 36 percent less on 4 and 16, and planning a step of 100,000 actors takes about 15 ms where it took 24.

**An actor that ends handles no more mail.** Mail it had when it ended and had not yet handled is not delivered, as mail that reaches it later is not. An actor that wants to finish what it was sent closes on a piece of mail that asks it to: everything queued ahead of that mail has been handled by then.

**An ending actor's closing turn is a turn of the next step.** At the end of the step in which an actor closes or fails, the fold marks it as ended. Only an actor's own ending marks it: the actors beneath it are not ended by the engine (ADR-0009). In the step after, the actor runs its closing turn (ADR-0009's `end`) among that step's other turns, in no order among them, and what it sends goes out with that step's mail.

**Between steps, the engine decides how many workers to wake or park for the next step.** The folded views say which actors have items to react to, and which owe a closing turn. What the engine has measured says about how long each of those actors' turns take: a moving average, weighted to the most recent. The decision is one signed number of workers: woken when positive, parked when negative, never more than are parked, and never fewer than minus those running. It weighs how long the next step would take with each count of workers against the measured cost of waking one, and against what keeping an idle worker running costs in power when it would be woken again a step later. Splitting a step costs too: its parts are taken out to the workers, gathered back, and folded on them, and for a light step that is more than the split saves. So the plan also decides how many of the workers awake the step is split among: the count it takes least time on, with what the split costs, or none, when the step takes least time run whole on the thread that steps the engine. The workers kept awake stay awake for the steps after it. The host measures what a split costs as it starts, beside what a wake costs, on a rehearsal: an engine in as many parts, with one actor in each part sending itself a piece of mail every step. It times steps of the rehearsal run whole, split between two workers, and split among as many as it can be. What a split step takes beyond the step run whole, but for the time its turns saved, is what the split costs: so much for two workers, and so much more for each worker past two. It is not learned from the steps the engine runs, because what they take beyond their plans mixes what the split costs with how far the plan's estimate of their turns was off, and with the work of folding their records. One actor's turns run on one worker, so a step takes no less than its most costly actor's turns, and no more workers are woken than the step's expected work divided by that cost, or than there are actors to run.

**Each part of the views is folded by itself, on the workers.** A part depends only on the records of its own keys, so at the end of a step each part some record reached is taken out with every worker's bucket for it and folded by one of the workers that ran the step, view by view; its watches settle, and the worker sums what the part's next turns are expected to cost. A part no record reached is not touched. What the watches hand on, the endings for the actors that watch, is put in their streams on one thread after, and is rare. Measured at 100,000 actors on 16 workers, applying a step took about 1.2 ms where it took 4.5, and a piece of mail cost about 52 ns where it cost about 103.

**A step planned for one worker runs whole, where its parts lie.** Taking a part out for a worker and putting it back pays only when a step is shared, so a step on one worker, the thread that steps the engine, takes nothing out: it runs each part's turns and folds each part some record reached in place. Measured with two actors passing one piece of mail back and forth, a piece of mail cost about 965 ns where it cost about 1,715; with 120 actors each passing mail to a neighbour, about 215 ns where it cost 260 to 370 on one and four workers.

**Parts are given to workers by their expected cost**, the most costly first, each to the worker with the least so far, and a worker runs only the parts it was given. A worker owns each of its parts for the step: the part's items, its actors' lives and seats, and the actors themselves are taken out of the engine and put back when the step is applied. A turn reads and changes only its own actor's part, so the worker hands out the part's items, takes each actor from its seat, runs it, and puts it back with nothing shared, and the thread that plans the step sorts the parts and not every actor: measured at 100,000 actors on 16 workers, planning a step took 1.3 ms where it took 11, and a piece of mail cost about 105 ns where it cost about 195. A part's expected cost is what each item that has arrived in it is expected to cost, by its actor's kind, summed by the worker that folded it. A worker seats the children its turns spawn in every so many parts of all of them, and not only in the ones it runs, so a family spreads across parts however few run, except a child kept in its parent's part while that part has room (ADR-0013). A worker that finishes early taking actors from one still running was measured against this and not kept. Run on 4, 8 and 16 workers over 64, 256 and 2,000 actors, with costs that were even, uneven per actor, uneven and changing every step, and a few actors costing a hundred times the rest, it was at best even with packing and mostly slower: taken one actor at a time, each actor cost it a share of its own and a place in a queue, and a worker that found its queue empty searched every other. In the same runs the fold and the plan, on one thread, took most of each step: about 2.6 of 3.2 milliseconds a step at 2,000 actors on 16 workers.

**The measured times are kept beside the steps, and not as a view**, under the kind of actor and what its turn reacted to: the kind of a piece of mail, an ending, or the actor's closing turn. Actors of one kind share what is learned, and a new one is planned for from its first step. Each worker sums its own measurements while the step runs, and the sums are merged between steps, so no measurement is shared while turns run. A worker times the first turn under each key in a step and every eighth after it, since the costs are an average and reading the clock costs about as much as a small turn: measured at 10,000 to 100,000 actors, timing every turn made a piece of mail 7 to 14 percent dearer. The substrate plans a step and runs a share of it wherever it is asked to; the threads the shares run on, and the clock the turns are timed by, are a native host's (ADR-0001).

## Consequences

- Shared state has one shape. The next view is a fold, and it takes no new argument about threads.
- A view's author cannot get the sharing wrong, because the author never touches it.
- The same turns leave the same views and the same actors, however many workers ran them. A prototype with three views gave one result on one thread and on 32, in every run.
- A turn cannot see what happened in its own step. An actor that must know of something waits for a later step or is told by mail.
- A turn cannot test and take in one move. Two actors that both read a name as free in one step both ask for it, the fold picks one by a fixed rule, and the other is told later.
- Each view costs a fold of each record and a share of the time between steps. In a prototype that folded each record twice, three views cost nothing measurable where a turn takes tens of microseconds, 10 to 17 parts in a hundred where it takes a few, and 23 to 45 where it takes a fraction of one.
- A step ends when its slowest turn ends. One long turn holds back every actor's next step.
- A cost guessed wrong holds the step to the worker the actor was given.
- What limits a step on many workers is what is left on one thread between steps: putting the parts back, seating the children a step stood up, handing out the folds, and putting the endings the watches hand on in the streams of the actors that watch.
- A chain of mail takes one step for each actor it passes through, unless its sends are fused, when it takes one step for each budget's worth of hops (ADR-0013).
- The count of changes in ADR-0008's table goes, and so does a reader holding a number: the step's number is the position.
- ADR-0009 said no worker waits for the others and there is no moment when all of them stop. Between two steps there is such a moment.
- **Not decided here:** domains of actors that never meet, each with steps of its own (ADR-0013 works out each step's domains, and leaves their steps undecided), so that a slow turn in one does not hold back another; how the cost of a wake is kept true when few workers are being woken; and how much power an idle worker kept spinning costs, which the plan does not yet weigh.

## Alternatives considered

- **Numbering every change to one shared table, a reader holding a number.** One structure, built and measured. A number may be read only once every change before it is written, so writers wait for one another: on 32 threads, fewer spawns in a second than on one.
- **The same count with writers noting what they are still writing.** No writer waits. About three times the code of the count it replaced, for one table, and nothing a second view could use.
- **A count for each worker, carried in every piece of mail.** No shared count at all. Every piece of mail grows by a number for each worker, every turn merges them, and a turn sees an actor only once some mail connects it to that actor.
- **Each actor keeping its own view, sent every other actor's effects.** Nothing shared. Explored over a dozen small arrangements of actors: an actor can hold a reference before it knows the actor exists, learn of a close before the spawn, and, if spawned late, never learn that an actor closed.
- **Two copies of each view, one read while the other is folded, changing places at the step.** A fold could then run while the step's turns are still running. Each record is folded twice and each view is kept twice, and the copy being written is shared between threads with no lock to guard it. It gains time only where workers stand idle while a few long turns finish. A view's author would not see the change, so it can be taken up later.
- **No steps, each shared structure built for its use.** The fastest for any one structure. It is the earlier engine's way, and each new structure is a new invention.
