# ADR-0037: MCP

- **Status:** Proposed
- **Date:** 2026-10-31

## Context

An agent drives the engine through MCP. ADR-0035 gave the hub the HTTP it needs (`Serve`, `Handling`, `Request`, `Response`) and left MCP's own rules to MCP: a handler answers each `Request`, and holds it (`turn.hold`, `turn.answer`) while a tool runs. This ADR is the first slice of the hub stack: an MCP server inside a program, whose tools reach that program's own actors. The link to engines is a later ADR.

The transport asks little. MCP's revision `2026-07-28` is stateless: it has no handshake and no sessions, and each request carries its own version and capabilities. Streamable HTTP has the client POST one JSON-RPC message, and the server answer with one JSON body, or `202 Accepted` for a notification. A GET or a DELETE, which that revision has no use for, is answered `405`.

Three things decide the shape:

- **`Mcp` cannot know the tools.** They are defined in other crates, by capabilities and games that a server must not name. Core never names a capability's things, and nor does `Mcp`: a capability's tool belongs in the capability's crate (ADR-0034 made the same split for host services).
- **A send names its kind.** A turn sends typed mail, and the engine refuses a send its sender did not declare (`Hosted::send`, `FalseSend`). A handler lists each kind it takes. So `Mcp` cannot ask an actor it knows only by a kind's id.
- **Most useful tools will not be linked into the hub.** One in an engine or another process has kinds the hub was not built with. All that crosses to it is a schema and bytes.

ADR-0007 already reads and writes any plain value from a schema (`from_json`, `to_json`). What is missing is the description of that schema an agent is given: JSON Schema.

## Decision

**`aethereal-mcp` holds `Mcp`, which forwards calls, and `Toolbox`, which stands up the tools a program lists. A tool is written in the crate it belongs to.** `Mcp` holds a table of what was offered, and it names no tool and no capability.

### A tool is a worker that takes bytes

```rust
// aethereal-mcp
pub struct Tooling;                                   // what a tool's worker speaks
impl Protocol for Tooling { type Kinds = (Call,); }
impl Carries<Call> for Tooling { type Answers = (Called,); }

pub struct Call { pub tool: String, pub input: Vec<u8> }           // `input` is a value of the tool's input schema
pub enum Called { Output(Vec<u8>), Refused(String) }               // `Output` is one of its output schema

pub struct ToolSheet {
    pub name: String,
    pub description: String,
    pub input: SchemaNodes,
    pub output: SchemaNodes,
}

pub struct Offer { pub tools: Vec<ToolSheet>, pub worker: ProtocolRef<Tooling> }
pub enum Offered { Yes, Taken, Full, NotAnObject, BadName, Unwritable }
pub struct Withdraw { pub tool: String, pub worker: ProtocolRef<Tooling> }
```

- **`Tooling` is the seam, and it is ordinary typed mail.** `Mcp` declares `Asks<Tooling, Call, _>` and nothing else, so it needs no erased send, and the engine's checks stay as they are. What is untyped is two byte fields, which the schemas in the sheet describe.
- **`Call` names the tool,** since one worker may serve many: a proxy for an engine serves a batch of them through one actor.
- **`Offer` takes a batch,** for the same reason, and is refused whole. `Offered::Taken` is a name already held, `Offered::Full` is past the setting `most_tools`, `Offered::NotAnObject` is an input schema whose JSON form is not an object, since a call's arguments are one: its root must be a struct with named fields or none, as a struct with positional fields is written as a value or an array (ADR-0007). `Offered::BadName` is a name outside what MCP asks of one: 1 to 128 of ASCII letters, digits, `_`, `-`, and `.`. `Offered::Unwritable` is a schema with no JSON Schema, as it is too deep or writes too much; each is written as it is offered, so `tools/list` cannot fail.
- **Tools come and go while the program runs.** Any actor may ask `Offer` at any time. `Withdraw` takes one out, when the worker it names holds it, so it never takes a name another holds. `Mcp` watches each worker (`ProtocolRef` is `Watchable`), and when one ends, drops its tools.
- `Offer` and `Offered` are bound, not plain, as they carry a reference.

### A tool is written where it belongs

A tool is a concrete actor, written in the crate that owns the work it fronts, and it says what it offers:

```rust
// aethereal-mcp
pub trait Tool: Actor<Key = (), Config: Default> + ChildOf<Parent = Anywhere> {
    fn sheets() -> Vec<ToolSheet>;
    fn worker(me: ActorRef<Self>) -> ProtocolRef<Tooling>;  // `me.protocol()`, which builds only when it speaks `Tooling`
}

// aethereal-files, behind its `tools` feature
#[derive(Debug, Plain)]
#[kind(name = "aether.files.read_tool")]
pub struct ReadTool;

impl ChildOf for ReadTool { type Parent = Anywhere; }

impl Actor for ReadTool {
    type Handles = (Call, Answer<FileRead, Calling>);
}

impl Tool for ReadTool {
    fn sheets() -> Vec<ToolSheet> { .. }
    fn worker(me: ActorRef<Self>) -> ProtocolRef<Tooling> { me.protocol() }
}

impl Handles<Call> for ReadTool {
    type Sends = (Asks<Path<Files>, ReadFile, Calling>, ToSender<Called>);
    // Decodes `ReadFile` from `input`, or replies `Called::Refused`; holds the call, and asks `Files`.
}
// Its answer handler makes `FileContents` of `FileRead`, encodes it, and answers `Called::Output`.
```

- **The work stays in the ordinary handler.** A tool call is an ask of a kind its owner already handles. `Files` does not change for it, in code or in its `begin`, and a test or another actor asks the same thing the same way. The tool turns bytes into that ask and the answer back into bytes.
- **A tool's input and output are plain kinds of its own when its owner's are not.** `FileRead` holds a `BlobRef`, which is bound and has no JSON form (ADR-0007), so the tool answers a plain `FileContents`. That is why a tool is a piece of code and not a table row: it decides what the agent sees.
- **A tool that combines several actors is the same thing:** an actor that asks each of them.
- **A capability's `tools` feature depends on `aethereal-mcp`,** so it brings in HTTP and TCP. It only makes the tool types available, and spawns nothing, so a feature turned on by `--all-features` changes no program. It is off by default.

**A worker need not be in a toolbox.** Whatever speaks `Tooling` may ask `Offer` at any time: a tool spawned at runtime, the link's proxy for an engine, or one for another process. `Mcp` treats them alike.

### A program lists its tools

```rust
Headless::program()
    .with_cycle::<(Tick,)>()
    .root::<Tcp>()
    .root_with::<Http>(http)
    .root::<Mcp>()
    .root::<Files>()
    .root::<Toolbox<(ReadTool, WriteTool)>>()
```

```rust
// aethereal-mcp
pub struct Toolbox<L> { /* .. */ }

impl<L: ToolList> ChildOf for Toolbox<L> { type Parent = Top; }

impl<L: ToolList> Actor for Toolbox<L> {
    type Key = ();
    type BeginSends = (Asks<Path<Mcp>, Offer, Offering>,);
    type Handles = (Answer<Offered, Offering>,);
    // Its `begin` spawns each tool of `L` beneath itself, and asks `Offer` for each.
}
```

- **`Toolbox` is sugar over `Offer`.** It adds nothing to the design: it spawns each tool and offers it, which any actor may do. A program with no tools lists none.
- **A program chooses tool by tool.** A hub can list a read tool and leave out a write tool in the same crate.
- **`Mcp` is checked at build.** `Toolbox` declares a send at `path::<Mcp>`, so a program that lists it before `Mcp`, or has no `Mcp`, does not build (ADR-0022: `MadeAfter`, `Ordered`).
- **A tool's own reach is checked at boot.** It is a child, and the setup's check sees only roots. A tool that reaches a root not yet live has its spawn refused with `Refused::Missing`, and `Toolbox` fails its `begin`, which stops the program as it starts.
- **Two tools of one name in a list are refused at boot.** `Toolbox` compares the sheets of `L` in its `begin`, and fails it, which stops the program as it starts.
- **An `Offered` other than `Yes` fails `Toolbox`'s turn.** The answer comes after boot, for a name something else offered first or a sheet `Mcp` refuses. A fault ends the actor, not the program (ADR-0009), so the toolbox ends, and as it ends it withdraws all it offered. The program runs on without those tools, with the fault in the log. The tools themselves stand on, as a child outlives its parent (ADR-0009), holding nothing and reached by nothing.
- **A tool stands beneath the toolbox,** at `aether.mcp.toolbox/aether.files.read_tool`, so its parent is `Anywhere`. Nothing reaches it by path: `Mcp` holds its reference. A tool's name and crate say what it belongs to, and its path does not.
- A program has one toolbox, as `Toolbox<L>` has one name whatever `L` is, and its list is flat.

### `Mcp` forwards

```rust
#[derive(Debug, Default, PartialEq, Eq, Plain)]
#[kind(name = "aether.mcp.settings")]
#[settings]
pub struct McpSettings {
    pub port: u16,
    pub most_tools: u32,
    pub most_calls: u32,
    /// Origins allowed besides this machine's, each compared exactly.
    pub origins: Vec<String>,
}
```

`Mcp` asks `Http` to `Serve` on its port with itself as the handler, and answers each `Request`:

It speaks `2026-07-28`, and only that. Each row is checked in the order written, and the first that holds answers:

| Request | Answer |
|---|---|
| An `Origin` header that is neither this machine's nor in `origins` | `403` |
| A path other than `/mcp` | `404`, with no body |
| `GET`, `DELETE`, or any other method but `POST` | `405` |
| A body that is not one JSON-RPC request or notification: a batch, a response, or a null `id` | `400` |
| A notification | `202` |
| `initialize` | `400`, `-32022`, naming `2026-07-28` |
| An `MCP-Protocol-Version` header of another version | `400`, `-32022`, naming `2026-07-28` |
| An `MCP-Protocol-Version` or `Mcp-Method` header missing, a `tools/call` with no `Mcp-Name`, or a header that disagrees with the body | `400`, `-32020` |
| `_meta` without its protocol version or client capabilities | `400`, `-32602` |
| `server/discover` | `2026-07-28` as the one supported version, and the `tools` capability |
| `tools/list` with a `cursor` | A JSON-RPC error, `-32602`, as `Mcp` never issues one |
| `tools/list` | The whole table, by name, each with its input and output as JSON Schema |
| `tools/call` with no `name`, or a name not held | A JSON-RPC error, `-32602` |
| `tools/call` with arguments that are not its input | A result with `isError` true, with `JsonError`'s path |
| `tools/call` | `from_json` on its input schema, then `Call`, holding the `Request` |
| Any other method | `404`, `-32601` |

- **`Origin` is checked on every request.** MCP requires it, since a page in a browser on this machine can otherwise POST to a server on loopback. The listener stays on loopback (ADR-0033: `TcpSettings::interface`). An absent `Origin` is taken: it is a client that is no browser.
- **Every header is checked against the body.** The revision requires it, so that nothing routing on a header sees other than what runs. `Mcp-Name` may be Base64, in the form the revision gives, and is decoded before it is compared.
- **Every result says what it is.** Each has `resultType` `"complete"` and `io.modelcontextprotocol/serverInfo` in its `_meta`. `server/discover` and `tools/list` have `ttlMs` 0 and `cacheScope` `"public"`: the table changes as tools come and go, and it is the same for every caller. The capability has no `listChanged`.
- **A tool result is text, and structured.** `Called::Output` becomes JSON by `to_json` on the output schema, carried as a text block and as `structuredContent`, which may be any JSON value, and every tool lists an `outputSchema`.
- **A tool that could not do it is a result, not a protocol error.** Arguments that are no value of the input, `Called::Refused`, and an ask answered `Unanswered` are a result with `isError` true, which the agent reads and can act on. `Mcp` is bounded by `most_calls` calls out at a time, past which a call is that result too.
- **There are no sessions.** `Mcp` issues no `Mcp-Session-Id` and ignores one sent, and a request depends on no earlier one.

### JSON Schema, from a schema

```rust
// aethereal-data, in `json`
pub fn json_schema(schema: &SchemaNodes, budget: &mut Budget) -> Result<String, JsonError> { .. }
```

It describes what `from_json` reads, form for form with ADR-0007. A value `from_json` reads always meets it. The reverse holds but for what JSON Schema cannot say here: that a 64-bit integer or a map's integer key is in range, that a float fits its width, and that an integer has no fraction or exponent. `from_json` still refuses those, so they are a result with `isError` true.

| Shape | JSON Schema |
|---|---|
| Boolean | `boolean` |
| Integer of 8, 16, or 32 bits | `integer` with its `minimum` and `maximum` |
| Integer of 64 bits | `string` with a `pattern` of its decimal digits |
| Float | a `number`, or one of the three strings |
| String | `string` |
| Bytes, or an array of `U8` | `string` with a `pattern` of lowercase hexadecimal, and its length when it has one |
| Option | the value or `null`; or `null` or a one-element array, where ADR-0007 writes it so |
| Sequence | `array` |
| Array | `array` with `minItems` and `maxItems` |
| Map | `object` with `propertyNames` and `additionalProperties` |
| Struct | `object` with `additionalProperties` false, and every field `required` but an option's |
| Tuple | `array` with `prefixItems` |
| Enum | `oneOf` over each variant's form |

Positional fields follow ADR-0007's rule: one is its value alone, and several are an array. The walk inlines each node, as a schema has no recursion (ADR-0003), follows the depth limit of 128, and charges its budget.

### A tool call

```
agent ─POST /mcp─▶ Exchange ─ask Request─▶ Mcp ─ask Call─▶ ReadTool ─ask ReadFile─▶ Files
agent ◀─ Response ◀─ Exchange ◀─ answer ◀─ Mcp ◀─ Called ◀─ ReadTool ◀─ FileRead ◀──┘
```

## Consequences

- `aethereal-mcp` depends on `aethereal-http`, and its program runs `Tcp`, `Http`, and `Mcp` in that order, then what its tools reach, then `Toolbox`.
- **`Toolbox` is the first generic actor.** `#[derive(Bootstrap)]` refuses a type with parameters, so its `Kind`, its encoding, and its `Bootstrap` are written by hand, and `ToolList` walks a tuple, of up to eight tools.
- **Each tool writes its own decode, ask, and encode.** A helper can reduce that later, as can a generic adapter over a kind. It is sugar: it changes neither `Tooling` nor `Offer`.
- **A client learns of a tool added later only when it next asks `tools/list`.** The notice that a list changed needs the stream of `subscriptions/listen`, and HTTP writes whole responses (ADR-0035). So there is no `listChanged`, and `subscriptions/listen` is a method `Mcp` does not have. `ttlMs` 0 tells a client its list is stale at once, and the revision lets it fetch again when a call fails, so it should not miss one for long, though that is a hint and not a promise. Streaming is its own slice.
- **A client of an earlier revision cannot connect.** One that speaks only the handshake stops at the `400`, which names the version it would need. A client of both tries this revision first and stays on it. Answering the handshake too would be `initialize`, `notifications/initialized`, and `ping` beside this, and can come later: a request's `_meta` says which it is.
- **`Mcp` reads a request's envelope with no schema,** as `_meta` and a client's capabilities are open-ended and `arguments` has its tool's shape. `aethereal-data` has the tree `from_json` reads through, private to it; `aethereal-mcp` needs it exported, with a way to read a value of it by a schema.
- **Two turns' worth of hops sit on every call:** `Mcp` to the tool, and the tool to its owner. Mail within a step chains (ADR-0013), so they should cost little beside the `Tick` of TCP polling on each side. The first slice measures it, as ADR-0033 and ADR-0035 ask.
- **A program must make mail as large as what it serves.** A request, an offer, and a tool's answer are each one piece of mail, and mail a turn cannot read within the engine's `read_limit`, 1024 bytes by default, fails the turn, which ends `Mcp`. `Http` refuses to start where a request it would take is past the limit, so no client can do that. An offer or a tool's answer past it is the program's to size, and is not checked: a tool that answers more should answer with a blob, once tools can.
- **The output schema is the tool's word.** `Mcp` holds bytes it did not make, and `to_json` refuses those that are no value of the schema, which is then a result with `isError` true.
- **A tool in an engine has nothing to offer to in that engine.** `path::<Mcp>` holds nothing there. The link ADR decides what it offers to, and what delivers a call on the far side. That may move `Tool`, `Tooling`, `Offer`, and `Toolbox` to a crate without HTTP, for an engine with no TCP, and what `Toolbox` offers to, and leaves the tools as they are.
- Whether a guest can offer a tool is left with the question ADR-0033 left for `Tcp`: asking a root at its path needs that root's handlers to build in a guest.
- It is tested over real HTTP with the harness (ADR-0036), as `tests/http.rs` is: a client on its own thread, and the test the worker through `Harness::protocol::<Tooling>()`.

Follow-on work, in order: `json_schema` in `aethereal-data`; `aethereal-mcp` with `Mcp`, `Offer`, and `Tooling`; `Toolbox`; `ReadTool` as the first tool, with its latency measured.

## Alternatives considered

- **An erased ask in `Turn`,** `ask_raw(kind, bytes)`, with an answer of any kind. `Mcp` would need no worker. It adds untyped verbs to the core, a wildcard in the send check, and a handler for every kind of answer, to do what `Tooling` does with ordinary mail.
- **A generic `Tool<T, K, A>` adapter as the design.** It needs `T`, `K`, and `A` linked in, so it cannot reach anything outside the build, and `Mcp` could not spawn one. It may come back as sugar.
- **Tools as children of `Mcp`.** Only a type's parent may spawn it (ADR-0022), so `Mcp` would have to name the type. A plain child that it can name would only forward.
- **A tool as a child of its owner, spawned in the owner's `begin`.** Its path says what it belongs to (`aether.files/aether.files.read_tool`), but the spawn is hidden from the program's types, so a missing `Mcp` is found only at runtime, the owner's code changes, and a program takes all of a capability's tools or none.
- **A `.child::<ReadTool>()` on the program,** which keeps that path and the check. It needs a spawn by something that is not the parent, which ADR-0022 rules out.
- **A concrete root for each capability's tools.** No generics, but a root for each capability. It is the fallback if an actor cannot be generic.
- **A root for each tool.** A program's list grows a root for what one line can hold.
- **A `Tools` registry root, apart from `Mcp`, in a crate with no HTTP.** It keeps a capability's feature from bringing in HTTP, which a program with `Mcp` has anyway, and it would serve a front nobody needs. The link may bring it back for engines.
- **`Handles<Call>` on the capability itself.** Its handler would take bytes and pick a tool by its name, and the capability would know about MCP. It is the right shape for a proxy, and for nothing else.
- **Sessions.** Nothing here needs state between requests.
- **Revision `2025-06-18`, with its handshake.** More clients speak it today, but it is a superseded revision, and it holds a version and capabilities for the life of a client that this design has no use for.
