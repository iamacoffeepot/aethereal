# ADR-0018: Jobs: work that takes time, run outside the steps

- **Status:** Proposed
- **Date:** 2026-10-19

## Context

A turn does not block (ADR-0001: a pumped, single-threaded mode in which nothing waits; ADR-0009). Some work takes far longer than a turn should: a fetch over the network, a file read, decoding an image, a long computation. A turn that did that work itself would hold back its step, and a step ends when its slowest turn ends (ADR-0011), so every actor would wait for it. A browser host cannot wait on such work at all: a fetch there is a promise.

ADR-0010 left this open ("how an actor asks a resource for work that takes time, such as a fetch, and how that work is cancelled"), and ADR-0017 left "a request that times out, which needs time in a turn".

What the engine already has to build on:

- A turn asks and is answered (ADR-0017: `turn.to(target).ask`, `Answer<A, C>`, `Answered`, `Unanswered`): the engine keeps the asker's context in its seat and hands it back with what came of the request, exactly once.
- What comes from outside the engine is brought in between steps, as mail from an actor to itself (ADR-0010: `Feed::push`, `Engine::bring`).
- The engine runs guests through one seam each host implements (ADR-0015: `Guests`), and a blob is put, pinned, and freed at folds (ADR-0014: `BlobRef`, `Puts`).
- A step carries the time the host passes in (ADR-0011), which is decided and not yet built: today `Engine::step` is handed a `Clock` and reads it only to time turns.

The earlier engine ran blocking work on offload threads beside a work-stealing scheduler, and its callers waited for answers by blocking. Neither ports to a browser (ADR-0001).

## Decision

**A job is work the host runs outside the steps: bytes in, bytes out.** A turn submits it, and the engine answers the turn's actor with its result in a later step. A job touches no engine state while it runs and is given no resource, so it runs wherever its host can run it: on another thread, on an event loop, or in a browser's Web Worker. What it makes it answers with: bytes, blobs, and resources (below).

```rust
pub trait Job: Kind + Encode<Actors> + Decode<Actors> + 'static {
    type Done: Kind + Encode<Actors> + Decode<Actors>;    // what it answers with
    const RUNNER: Runner;                                  // Runner::Compute | Runner::Io

    async fn run(self, job: &mut Running) -> Result<Self::Done, Fault>;
}

impl Running {
    pub fn read(&self, blob: &BlobRef) -> &[u8];           // a blob the job refers to
    pub fn put(&mut self, bytes: Vec<u8>) -> BlobRef;      // a blob the engine puts when the job is answered
    pub fn hand<R: Resource>(&mut self, value: R) -> Given<R>;   // a resource the engine keeps when the job is answered
    pub fn until(&self, at: Time) -> Until<'_>;            // waits until `at` on the host's timer
}
```

- **A job's code is native code linked into the program**, in each build of it: the native host's, and in a browser the module its Web Workers load. **A native turn's job carries its code:** `turn.run::<J>` knows `J`, so the job is handed out with its type (`JobType::of::<J>()`, its kind, where it runs, and the function that drives it), and a runner runs every job it is handed with no list of its own. A runner is made with its host's services alone, once the program's roots have bootstrapped (ADR-0029: `Engine::set_jobs`). A function's address stays good in each build that runs it: natively one process, in a browser the page's own instance, and Web Workers that load the same module hold the same table of functions, so a worker reads the same address as the page.
- **A guest's job carries only its kind**, as a guest cannot hand its host code. The program lists the job types its guests may run (`with_guest_jobs::<(Sum,)>()`), as a native host is handed the native types a guest may spawn (ADR-0015: `Links`), and the engine runs a guest's job with the type of its kind listed there, with `Sleep`, which every guest may run. A guest's job of a type not listed is answered `Faulted` with `NoRunner`, by the engine, and never handed out.
- **`run` is a future, and the host drives it, never the engine.** ADR-0001 rule 4 says the engine drives no future to completion; the host's runner does, as a browser's fetch is a promise and a native read waits on a reactor. A compute job's future is ready the first time it is polled.
- **A job declares where it runs, as a constant.** `Compute` runs on threads for computing, and `Io` on a reactor for waiting, so a job that waits on a socket never holds a thread a computation could use.
- **A job holds data, and blobs, and nothing else.** A job and its result cross `Actors`, as mail does, so either may hold a `BlobRef`. A job that holds a `Given` is refused where it is written, as a `Given` written into a second piece of mail is (ADR-0010).
- **A job's result may hold a resource the job made, and no other.** Work that takes time sometimes ends in a value that is not data: a connection, once the handshake is done. The job makes the value with its own code and hands it with `Running::hand`, which boxes it, as the engine keeps every resource (`Kept`: its type's name and a `Box<dyn Any + Send>`), and answers with a `Given` numbered in the job, as `put` numbers a blob. The `Given` goes in the result. At `bring` the engine keeps each value the job handed, as `Engine::hand` keeps one, and writes the resource's own ticket over the job's number where it lies in the result, as it writes a blob's reference. The answer then carries the resource to the actor that ran the job, as mail carries a gift, and the actor takes it in the handler of the answer (ADR-0010: `turn.take`). One the actor does not take is dropped and recorded in its log, as any `Given` not taken is. The writer of a result refuses a `Given` that the job did not hand, and one written twice. **This departs from this record as first written**, which let a job answer with data and blobs only and gave the reasons kept under Alternatives considered: the engine's keeping is reached at `bring`, between steps, as its store is for `put`; the owner is the actor that ran the job; and `bring` carries a resource since ADR-0019.
- **Only a job run where its host runs the engine may hand.** A value is moved between threads natively, and a resource is `Send` (ADR-0010). A browser's Web Worker passes only bytes back to the page, so a job it runs that hands is answered `Faulted`. A job run on the page's own event loop may hand.
- **A job is read where it runs.** Its runner decodes it from its bytes on the thread or worker that runs it, so a job's value never moves between threads, and a future a browser's promise drives need not be `Send`. A reference the job reads names a blob copied out with it, and `read` hands back those bytes. A reference `put` returns names the job's own bytes, numbered in the job, and means nothing to the engine yet: the engine puts the bytes at `bring` and writes the blob's reference over it where it lies in the result, as the writer at `Actors` knows where each reference it writes lies (ADR-0014). So no reference a job made reaches an actor before its blob is in the store.

**A turn submits a job with `run`, which returns its id.**

```rust
let fetch = turn.run(&Fetch { url }, &Loading { tile })?;     // a JobId, or why it did not run: Unrun
turn.cancel(fetch);                                            // when the actor no longer wants it

impl Handles<Answer<Fetched, Loading>> for Tiles { .. }       // built only when the actor handles the answer
```

- `run` builds only when the actor handles `Answer<J::Done, C>`. A turn's sends list where its mail may go, as `Asks<P, K, C>` lists a request (ADR-0017); a job is mail to no actor, so they do not list it. The job's own type says what it answers with, so no protocol is named. **This departs from ADR-0017, which asks only through a named protocol.** The protocol is there because it says what a kind is answered with, and `J::Done` says it here.
- A job's id is its mail's id: the actor and the next count of what it sends (ADR-0012: `MailId`). So jobs are ordered with the turn's sends, and no other number is made. A job is kept with the turn's mail, in its buffers, so wherever the engine reads how many pieces an actor has sent it counts the jobs too, and a turn that fails, or a child's `begin` taken back, drops its jobs as it drops its mail. A `JobId` crosses `Within` and no other boundary, so it is kept in the actor's state and its contexts and never in mail. It means something only to the actor that ran the job, as a watch's id does.
- The engine keeps the context in the actor's seat until the job is answered, as it keeps an ask's (ADR-0017).
- A turn that fails runs no job, as it sends no mail.
- A `begin` may run a job, filed beside the actor that ran it, as a `begin`'s asks are. A closing turn may not: the actor is gone before an answer could reach it.
- Past the jobs a host lets be in flight, a job waits. The host says how many it lets be, `Jobs::most`, and a job is in flight from when it is handed out until its `Finish` is done or dropped, which the engine counts by a token each `Finish` holds. The engine keeps the jobs past that in a queue of its own, in the order they were run, and hands each out between steps, at a fold or a bring, as one in flight finishes. So `run` is never refused for a full host, and the order jobs are handed out in depends on the turns that ran them, not on how workers interleaved. A waiting job that is cancelled is dropped and never handed out, and the waiting job of an actor that has ended is dropped as well. **This departs from refusing the run, as a put past the budget for blobs is refused (ADR-0014):** an actor refused would have nothing to tell it when to try again, and a timer to try again by is itself a job, refused for the same reason.
- `cancel` is kept with the turn's mail. Once the turn has run, where the contexts of its asks are filed, the job's context is let go of, and with it the pins on the blobs it refers to; then the engine asks the host to stop the job, which it does if it can: natively it drops the future, and in a browser it aborts the fetch. No turn of the actor is handed that job's answer from then on, whether or not the job finished, since an answer with no context runs no turn (ADR-0015): not even one already in the actor's stream behind the turn that cancelled it. A turn that fails cancels nothing. A `cancel` of a job that is no longer in flight, or that another actor ran, does nothing.

**The engine owns the runners through one seam, which each host implements.**

```rust
pub trait Jobs: Send + Sync {
    fn start(&self, id: JobId, kind: KindId, job: Taken);    // the job's bytes, the bytes of each blob it refers to,
                                                             // and the end of the engine's feed it is answered on
    fn stop(&self, id: JobId);                               // best effort
}

impl Finish {
    pub fn done(self, outcome: Result<Produced, Fault>);     // once: it is taken by value; what the job
                                                             // produced is its result's bytes, the pins they hold,
                                                             // the bytes of each blob it put, and each value it handed
}
```

1. At the fold, each job submitted in the step is taken out to the seam: its bytes, and a copy of each blob it refers to. The job's record, the context its actor keeps for it, holds a pin on each of those blobs until the job is answered or cancelled, or its actor ends, so the step a blob is freed in does not depend on when a job ran. A reference the runner reads out of the job is a pin of its own. Each change to a pin the job makes as it is polled or dropped goes onto a queue of its engine's that no one waits on, which the engine sums with its next step's, so a runner takes no lock to change one (ADR-0014).
2. The host runs it, and when it finishes, pushes what it made onto a feed inside the engine, through the `Finish` the job was handed with: the result's bytes, the bytes of each blob it put, each value it handed, or its `Fault`. A host that drops a `Finish` without pushing leaves its job unanswered, so a runner catches its jobs' panics.
3. At `bring`, each finished job is answered: the engine puts each blob the job made, between steps, out of the budget for blobs, keeps each value it handed, and writes in the result the references to them and the resources' tickets, then writes the answer as mail from the actor to itself, tied to the job, as `bring` writes what a feed brings. It is handed to the handler of `Answer<J::Done, C>` with the context.

| | `Compute` | `Io` |
|---|---|---|
| native | a pool of threads, as many as the cores the engine's workers leave free | one thread, polling each job it is woken for, with a timer; a reactor for sockets and files once an `Io` job needs one |
| browser | a set of Web Workers | a Web Worker, or the page's own event loop |
| pumped, single-threaded | run inline between steps | polled between steps, never waited on |

- The engine's own runner, `Inline`, runs each job as it is handed out, polling it once: a job not ready then is answered `Faulted` with `Waits`. A panic is answered with `Panicked`.

**The answer comes from the actor to itself.** A job is not an actor, and what a feed brings is mail from its source's owner to itself (ADR-0010). The answer is told apart by its tie, as an ask's is, so its sender changes nothing for the handler. It is the root of a chain of its own, as what a feed brings is: nothing the actor did in the step it is brought caused it.

**What came of a job is said as an ask's is.** `Answered::Yes(done)` is the result. `Unanswered` gains one case, `Faulted`: the job returned a `Fault`, or its host lost it to a panic, or a blob it made did not fit the budget. The fault is written into the actor's log, where every fault is read (ADR-0009). A native runner catches a job's panic and fails only that job. A browser worker that a panic aborts fails every job it held, and the host starts another. A job whose actor has ended is answered to no one: its result, the blobs it made, and the resources it handed are dropped. So is a job that was cancelled, or answered `Faulted`: a resource is always somewhere (ADR-0010), and one no answer carries is dropped as the job is let go of.

**Nobody sets a job a deadline but whoever ran it.** The engine sets none. A job runs until it finishes, and an actor that wants to stop waiting cancels it. Time to measure against is one more job:

```rust
let fetch = turn.run(&Fetch { url }, &Loading { tile })?;
turn.run(&Sleep { until: turn.now() + Duration::from_secs(5) }, &GiveUp { on: fetch })?;
// in the handler of Answer<Slept, GiveUp>: turn.cancel(on)
```

- `Sleep` is a job of the engine's, an `Io` job every host runs. It waits on the host's timer, which `Running::until` hands every job: `setTimeout` in a browser, the `Io` thread's timer natively, read from the clock the steps' times are. So any job may wait for a time, as one that backs off before it tries again does. **This departs from each host implementing `Sleep` itself:** the host implements the timer, and `Sleep` is a job like any other. A host with no thread to wait on, `Inline`, has a timer that never comes, and answers a sleep for any time past its first `Waits`.
- **A turn reads its step's time with `turn.now()`**, a `Time`: nanoseconds on the host's clock, the clock its timers run on. The host passes it in as it starts the step, as ADR-0011 decides, and every turn of the step reads the same time. A record of a run keeps it beside the step's number.

**An ask is not cancelled** (ADR-0017). A job's work runs on the host, which nothing but `cancel` reaches; an ask's receiver is an actor, and mail reaches it.

**A guest runs jobs as native code does, and its host reads them from its records as it reads its asks (ADR-0015).** A guest's `run` writes the job and keeps its context with the turn's asks, as a native turn's does, and its `cancel` is kept with the turn's mail. After the call, each job is a record among its turn's records: who ran it, the count it took, its kind and the kind it is answered with, and where its bytes and its context lie, each followed by the blob of each reference it holds, as an ask's context is written. Each cancel is a record of the job's id. The host files each job as a native turn's is filed, beside the actor that ran it or the child whose `begin` did, with a pin of its own on each blob the job and its context refer to, and asks the engine to cancel each job the turn's actor or a child it spawned ran. The answer comes into the guest's inbox as the answer to a request does, with the context.

- **A guest's turns count what they send on from the engine's count.** A job's id is the actor and its count, and the guest's code keeps it for `cancel` before its host has read the turn. So `prepare` is lent how many pieces of mail the actor has sent and jobs it has run, the guest's first turn of the batch counts on from it, and each later turn from where the one before left off, as the engine counts them. Mail sent in an earlier turn of the batch lies in the same buffers, so a run joins only a turn's own mail.
- **The host files each job between the sends it ran between.** It hands in the turn's sends in order, and files a job once the next count of the actor that ran it is the job's: so the job takes the count the guest's id names. A job whose count no send leaves it does not read back.
- A job whose runner's type does not handle its answer, or that a closing turn ran, fails the turn as a send its declaration does not allow does (ADR-0013): what a guest's library would not have built.

The ask path already does what a job needs beside its turn: a context kept by its asker, blobs pinned by the host from what the guest wrote, and an answer handed back in with what was kept. So a guest's job adds two records and no new way through the engine.

## Consequences

- Async work has one verb, and its answer is handled the way an ask's is: the handler always runs once, unless the actor cancelled, with what it kept.
- Work that takes time never holds back a step, and never blocks a thread an actor runs on. A job in flight does not keep anything else waiting: a step does not wait for it, and since its answer starts a chain of its own, nothing that waits for a chain to finish waits for it.
- Each job's bytes and the bytes of every blob it refers to are copied out once at the fold. Its result is copied back once. In a browser, wasm memory cannot be handed to a worker without a copy, so each crossing to a Web Worker is a copy each way.
- Large results do not ride in mail. A job puts them, and the engine puts them into the store at `bring`, so a fetched image arrives as a `BlobRef` and its bytes are written once.
- A job holds its blobs' pins until it is answered or cancelled, so a job that hangs holds them until its actor cancels it or ends.
- Nothing bounds how many jobs an actor has waiting, as nothing bounds the mail it sends; each keeps its context and its blobs' pins while it waits.
- Which step a job is answered in depends on how long it took. The same turns no longer always leave the same views once a job is answered, so a record of a run keeps each answer a `bring` delivered, beside its step, so the run can be replayed.
- A job type is one more thing linked into each build: the browser's worker module must link every job type the program runs.
- A host that has no thread to spare, the pumped single-threaded mode, runs compute jobs inline between steps, so their time comes out of the pump. They are still answered in a later step, never in the turn that ran them.
- The native pool shares the machine with the engine's pinned workers (ADR-0011). It takes the cores they leave free; what that costs a step is not measured.
- A window, a GPU device, or an audio output is still not a job's to make. A native window can be made only inside the windowing library's own callbacks, and in a browser most such values cannot leave the page's thread. They are made by the chassis and handed to the actors that own them (ADR-0019). A job makes a resource that its own code can make on the thread it runs on, which can move to the actor's: a connection, an open file.
- A guest's job is written twice before it runs: once by the guest into its memory, and once as its host copies it out, as a guest's mail is.
- ADR-0017's open timeout question has its rule: the engine sets no deadline, and the asker decides when to stop waiting.

## Alternatives considered

- **A blocking call in a turn, run on an offload thread.** What the earlier engine did. It blocks a thread, and a browser cannot block at all.
- **A job given resources, as an owner.** A fetch could reuse a connection it was given. The job would hold a resource while it runs, outside every step and every actor, and a job is not an actor, so it cannot own one (ADR-0010); a resource given to a job could not be opened by the actor while the job held it. A job still makes a resource and answers with it (above): making and answering need no owner but the actor answered. As first written this record rejected making too, because a running job would reach the engine's tickets outside a step, because the owner would not be an actor, and because `bring` carried no resource. `hand` reaches no ticket until `bring`, the actor answered is the owner, and ADR-0019 has `bring` carry a resource.
- **A thread as a resource an actor owns.** An actor borrows a whole thread from a set the chassis makes. One actor's jobs then queue on its own thread while others stand idle, and a shared pool already spreads work across threads without an owner.
- **Jobs given to a pool actor by mail.** Nothing new in the engine. The pool actor runs in steps, so every job and every answer costs a hop through it, and the work still has to run somewhere outside the steps.
- **A deadline on every job, by default.** Nothing could hang forever. A default is a guess for every job, and the engine would be choosing a policy the actor that ran the job knows better.
- **A deadline only when asked, `run_by`.** Explicit. It adds a second verb for what `Sleep` and `cancel` already do.
- **One runner for all jobs.** Simpler. A job waiting on a socket holds a thread a computation could have used.
- **A job answered on the chain of the turn that ran it.** Its chain would not finish until the job did, so whatever waits for a chain to finish would wait on work outside the steps.
- **A guest's job counted by its host after the turn's sends, its id fixed then.** The guest's code would hold an id the engine does not file the job under, since it keeps the id in its state before its host reads the turn.
- **A guest's job asked of its host in a call out, which answers with its id.** A call out is for what a turn must have answered within the turn (ADR-0015); the count is known without one, and a call out for each job costs a crossing.
- **A guest's job written as one more kind of send.** It would be counted with the turn's sends where it ran, with no count of its own in the record, but a resource a guest gives goes with a piece of mail named by its place among the call's sends (ADR-0010), and a job among them would move every piece after it.
- **Results only as bytes in mail.** No blobs made at `bring`. A large result would be written into an arena, bounded by the read limit, and copied out again by an actor that keeps it.
