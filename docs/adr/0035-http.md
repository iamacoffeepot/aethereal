# ADR-0035: HTTP

- **Status:** Proposed
- **Date:** 2026-10-28

## Context

The hub's MCP endpoint is HTTP. MCP's Streamable HTTP transport asks very little of it. The client POSTs one JSON-RPC message, and the server answers with one JSON body, or with `202 Accepted` for a notification. A GET, which would open a stream of the server's own messages, may be answered `405`. So the first HTTP the engine needs is an HTTP/1.1 server that reads whole requests and writes whole responses. A client, streamed bodies, and TLS can come later.

What the engine already decides:

- **TCP is a capability, and HTTP sits on it** (ADR-0033: `Tcp`, `Listen`, `Listener`, `Accepted`). A connection reads `Framing::Chunks` and leaves where a request ends to HTTP. The frames come on a `Reading` stream, paced by the reader's credit, and a write is a `Write` ask answered `Sent`, `Full`, or `HungUp`. A connection whose reader ends shuts itself.
- **A stream is a request held open, paced by the asker's credit** (ADR-0017: `Stream`, `Streams`, `Serving`, `More`). It is the engine's one form of backpressure. `Streams::part` grants one more part for each part taken.
- **A reference that travels in mail is a typed `ActorRef<T>`** (ADR-0008). A `ProtocolRef<P>` does not cross mail, and the cast that makes one at runtime is to a tuple of tells, whose answers are not read (ADR-0016: `turn.cast`). So an actor cannot be handed, in mail or in a config, something it can *ask* of an actor whose type it does not know. It can be streamed to, since parts are tells.
- **A request is answered exactly once, and is not cancelled** (ADR-0017). An asker that gives up passes over the answer when it comes.
- **A capability is a root asked at a typed path** (ADR-0022: `ChildOf`, `path::<L>`, `Carries`), and **a root that needs nothing of its host is bootstrapped for every host** (ADR-0029: `impl<H: Host> Bootstrap<H>`).
- **No actor ends another** (ADR-0009). It is sent `Shut`, and closes itself.

Input on a listening socket is untrusted. Its size, its shape, and how slowly it arrives all have to be bounded before anything reaches the program.

## Decision

**One capability, `Http`, in the crate `aethereal-http`, a server on `Tcp`. It parses and writes HTTP/1.1 itself, with no third-party parser.**

```
Http                 root, singleton, asked at path::<Http>(())
 └─ Server:port      listens through Tcp; serves `Requests`
     └─ Exchange:n   reads one accepted connection; parses each request; writes each response
```

```rust
impl ChildOf for Http     { type Parent = Top; }
impl ChildOf for Server   { type Parent = Http; }     // keyed by its port, as a u64
impl ChildOf for Exchange { type Parent = Server; }   // keyed by the server's count
```

- **An exchange is the server's side of one TCP connection.** Its config carries the `ActorRef<Accepted>` the listener made. It opens `Reading` on that connection in its `begin`, and writes to it through `Writing`. HTTP holds no socket: every byte goes through `Tcp`.
- **The crate builds for every host, and is bootstrapped for every host** (`impl<H: Host> Bootstrap<H> for Http`). It needs nothing of its host but `Tcp`. A program without `Tcp` builds, and its `Serve` is answered `Unavailable`.

### Serving is asked of the root

```rust
impl Carries<Serve> for Http { type Answers = (Served,); }

pub struct Serve { pub port: u16 }                             // port 0: any free port

pub enum Served {
    Bound { server: ActorRef<Server>, port: u16 },             // the port bound, which is the server's key
    Taken,                                                     // something holds the port
    Full,                                                      // the root holds its most servers
    Refused,                                                   // the host refused the bind
    Unavailable,                                               // no Tcp in this program
}
```

- **A serve is held until `Tcp` answers its listen.** The root asks `Tcp` to `Listen` with `Framing::Chunks`, and keeps the held `Serve` as the ask's context. On `Listening::Bound` it spawns the `Server` at that port, with the `ActorRef<Listener>` in its config, and answers `Bound`. Every other answer maps to its case of `Served`, and an ask that finds no `Tcp` is answered `Unavailable`.
- **The root watches whoever asked** (`turn.watch`). When that actor ends, the root sends `Shut` to the servers it bound for it, as `Tcp` does for its listeners (ADR-0033).

### Requests are a stream the handler opens on the server

```rust
pub struct Requests;
impl Stream for Requests { type Open = Take; type Part = Incoming; type Done = Stopped; }

pub struct Take;
pub struct Incoming { pub request: Request, pub exchange: ActorRef<Exchange> }
pub enum Stopped { Shut, Unbound, Busy }

pub struct Request {
    pub method: Method,
    pub path: String,                 // the target's path, as sent
    pub query: String,                // after the `?`, empty when there is none
    pub headers: Vec<Header>,         // in the order sent, duplicates kept
    pub body: Vec<u8>,
    pub peer: SocketAddress,
}
pub struct Header { pub name: String, pub value: String }     // names lowercased by the parser
pub enum Method { Get, Head, Post, Put, Delete, Patch, Options }
```

- **The handler is whoever opens `Requests` on the server.** It is usually the actor that asked `Serve`, which then opens the stream on the server it was answered. This mirrors `Accepting` on a listener (ADR-0033), and for the same reason: the handler cannot be named to the server in mail. A `ProtocolRef` does not cross mail, and a cast reaches only tells (ADR-0016), so neither the root nor the server could *ask* a handler whose type it does not know. A stream's parts are tells, and the stream library holds the asker's reference for the receiver.
- **The handler's credit is how many requests it takes at once.** The server sends an `Incoming` only while the handler has credit. Until then the server keeps the parsed requests, in the order they were parsed. There are at most as many as it has exchanges, since each exchange has at most one request out.
- **One handler per server.** A second `Take` while one is served is finished at once with `Busy`. The stream's answer is how it ended. `Shut` means the server was sent `Shut`, and `Unbound` means `Tcp`'s accept stream ended. A server whose handler ends shuts itself, since nothing is left to answer.
- **The request reaches the handler in two hops.** An exchange sends what it parsed to its server, which sends it on as the stream's part. An exchange cannot hold the handler's reference: it would have to come in the exchange's config, which is mail.

### A response is sent to the exchange

```rust
pub struct Respond { pub response: Response }                  // a tell, to the exchange the request came from

pub struct Response {
    pub status: u16,
    pub headers: Vec<Header>,
    pub body: Vec<u8>,
}
```

- **The handler answers by sending `Respond` to `Incoming::exchange`,** in the turn it took the request or in any later one, as MCP does once an engine has answered. Holding the reference is the authority to respond, as holding a connection's is to write it (ADR-0033).
- **It is a tell, not an ask's answer.** A request reaches the handler as a stream's part, and a part has no answer of its own. So the exchange keeps a deadline for the response itself (below).
- **An exchange that is not waiting for a response drops a `Respond`,** and records it in its log: a second response, one after the deadline, or one to an exchange already closed.
- **The exchange writes the framing headers itself.** It writes the status line, the handler's headers, `Content-Length` from the body, and `Connection: close` when it will close. A `Content-Length`, `Transfer-Encoding`, or `Connection` among the handler's headers is dropped and recorded in the log. A response to `HEAD` has its body dropped and keeps its `Content-Length`.

### An exchange parses as chunks arrive, one request at a time

```
Accepted ─Frame─▶ Exchange: Head { buffer } ─▶ Body { head, body, remaining } ─▶ Answering { since } ─Parsed─▶ Server ─Incoming─▶ handler
                                                                                       │
Accepted ◀─Write─ Exchange ◀───────────────────────────────── Respond { response } ────┴──────────────────────────────── handler
```

- **The exchange keeps what it has decoded, not the raw bytes.** In `Head` it buffers until the blank line that ends the head, then parses it in one pass. In `Body` it gathers exactly `Content-Length` bytes. Bytes past the end of the request stay in its buffer for the next one.
- **While a request is out, the exchange grants no credit.** It takes the `Frame`s still in flight without granting more, and grants what it held back once its response is written. So a client that sends requests back to back, pipelining, waits in the kernel, and TCP slows it down. What the exchange holds meanwhile is bounded by the `Reading` window times its chunk size. This needs two methods on `Streams` (ADR-0017): `part_held`, which takes a part without granting for it, and `grant`, which grants a stream a number of parts.
- **Connections are kept alive,** HTTP/1.1's default. The exchange closes after its response is written (`Wrote::Sent`) when the request said `Connection: close` or was HTTP/1.0. It also closes when the write is answered `Full` or `HungUp`, or the read stream ends.
- **`Expect: 100-continue` is answered `100 Continue`** once the head has passed every check, before the body is read.

### Limits on untrusted input

| The request | The exchange's answer |
|---|---|
| a head past `most_head_bytes` | `431`, then close |
| a body past `most_body_bytes`, by its `Content-Length` | `413`, then close, before the body is read |
| a request line or header that does not parse; a bare LF; a folded header; a header that is not visible ASCII | `400`, then close |
| `Content-Length` sent more than once, or not a number | `400`, then close |
| any `Transfer-Encoding` | `501`, then close |
| a method not in `Method` | `501`, then close |
| a target not in origin form (`/path?query`) | `400`, then close |
| a head not whole within `head_within_millis` of its first byte | close, no answer |
| no request within `idle_within_millis` of the last response | close, no answer |
| no `Respond` within `answer_within_millis` | `504`; a later `Respond` is dropped |

- **Refusing `Transfer-Encoding` refuses chunked request bodies,** and with them the request smuggling that comes from a `Content-Length` and a `Transfer-Encoding` that disagree. MCP's clients send `Content-Length`.
- **Deadlines are checked each `Tick`** against `turn.now()`. An exchange subscribes to `Tick` (`On<Tick>`), as a TCP connection does, so a program that serves HTTP already runs a cycle that holds it (ADR-0033).
- **A refused request still writes a response where one is owed,** then the exchange closes. The server never sees it, and neither does the handler.

### Ending is by mail

| Type | Ends when |
|---|---|
| `Server` | it is sent `Shut`: by the root when the asker of `Serve` ends, or by whoever holds it. It also ends when its handler ends, or when `Tcp`'s accept stream ends. It sends `Shut` to its listener and to each exchange, finishes `Requests`, and closes, all in the turn that handles `Shut` |
| `Exchange` | it is sent `Shut`, or it closes the connection as above, or its read stream ends |

When an exchange closes, its read stream's asker is gone, so the TCP connection beneath it shuts itself (ADR-0033). An exchange does not send `Shut` to it.

### Settings

```rust
#[settings]
pub struct HttpSettings {
    pub most_servers: u32,
    pub most_exchanges: u32,           // per server; past it, an accepted connection is shut at once
    pub most_head_bytes: u32,          // 16 KiB
    pub most_body_bytes: u32,          // 8 MiB
    pub chunk_bytes: u32,              // the `Chunks` framing's `most_bytes`
    pub window: u32,                   // the parts an exchange's read stream is granted
    pub head_within_millis: u32,
    pub idle_within_millis: u32,
    pub answer_within_millis: u32,
}
```

The section is `http`. Where listeners bind, loopback by default, is `Tcp`'s setting (ADR-0033: `TcpSettings::interface`).

### A tool call through the hub

```
agent ─POST /mcp─▶ Accepted ─Frame─▶ Exchange ─Parsed─▶ Server ─Incoming─▶ Mcp ─ask─▶ tool
                                         ▲                                    │
agent ◀───────────── Accepted ◀─Write── └──────────── Respond ◀───────────────┘
```

## Consequences

- MCP gets an endpoint by asking `Serve`, opening `Requests` on the server, and sending `Respond`. It reads `path`, `method`, and `mcp-session-id` from the request. Sessions, and what `202` and `405` mean to MCP, are MCP's business.
- **A request is copied more than in a bare parser.** It is copied from the frames into the exchange's buffer, then into `Parsed`, then into `Incoming`, then by each actor that keeps it. A hop through the server and a `Tick` of TCP polling sit on the way in, and another `Tick` on the way out. That is fine for tooling, and is measured with ADR-0033's hops on the first MCP slice.
- **The server is the one actor every request crosses.** Its work per request is a forward, so it is not where a hub's time goes. If it ever is, a handler per exchange is the change, and it needs a typed reference to the handler in each exchange's config.
- **A handler cannot learn that its client hung up.** The exchange closes, and the later `Respond` is dropped. A handler that should stop work on a hang-up needs a notice it can watch for, and none is designed here.
- Every limit is enforced before a request reaches the server, so memory per exchange is bounded by `most_head_bytes` plus `most_body_bytes` plus the read window. The number of exchanges is bounded by `most_exchanges`.
- `Streams` gains `part_held` and `grant`, a reader's way to stop granting while it is busy. TCP's connections do not need them, and any stream asker that works on one part at a time can use them.
- **Not decided here:** streamed responses, server-sent events and chunked bodies, which come as a stream from the handler to the exchange when a tool needs to report progress; chunked request bodies; routing, while a server has one handler that matches on `path`; an HTTP client; TLS; `Date` headers, which the exchange does not write.

## Alternatives considered

- **The handler named in `Serve`, asked `Request` and answering `Response`.** The answer would be the correlation, and a handler that ended would be answered for by the engine. But the root and the server could only cast the handler to a tuple of tells, which cannot be asked (ADR-0016). An `Http` generic over the handler's type would make one root per handler type.
- **A handler reference in each exchange's config, so requests skip the server.** One hop less. A config is mail, and a `ProtocolRef` does not cross mail.
- **The `Respond` carries a number the exchange gave the request, sent to the server.** The server would keep a table from numbers to exchanges. The exchange's own reference is that table.
- **HTTP's framing in `Tcp`,** as a third `Framing` case. Rejected in ADR-0033: TCP would know HTTP's rules.
- **A third-party parser** (`httparse`). Less code to write. The hub stack is in-house by choice, and a request head is a small grammar with limits that have to be ours anyway.
- **Accepting chunked request bodies now.** No MCP client needs them, and accepting them is where request smuggling comes from.
- **Answering pipelined requests concurrently.** Responses must go out in request order, so the exchange would queue responses behind slower ones. One request at a time, with credit withheld, keeps the order and the bound.
