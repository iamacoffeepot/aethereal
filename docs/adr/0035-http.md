# ADR-0035: HTTP

- **Status:** Proposed
- **Date:** 2026-10-28

## Context

The hub's MCP endpoint is HTTP. MCP's Streamable HTTP transport asks very little of it. The client POSTs one JSON-RPC message, and the server answers with one JSON body, or with `202 Accepted` for a notification. A GET, which would open a stream of the server's own messages, may be answered `405`. So the engine needs an HTTP/1.1 server that reads whole requests and writes whole responses. The hub also reaches Docker's Engine API, which is HTTP/1.1 over a Unix socket (ADR-0057), so the engine needs a client as well: one that asks over TCP or a Unix socket, keeps its connection between requests, streams a response it should not hold whole, and hands the connection over when Docker switches it to a raw stream. The hub also takes `git push` over git's smart HTTP, whose request bodies run to gigabytes, so a server must be able to hand a request's body to its handler as it arrives rather than gathered whole. A fetch over the same smart HTTP is answered with a pack that runs to gigabytes, made as `git upload-pack` writes it, so a server must also be able to write a response's body as it is made rather than hold it whole. TLS can come later.

The hub serves git's smart HTTP on the port its sessions reach its MCP endpoint on, so one port is served to several actors, each under a path of its own, and each request has to arrive knowing who sent it: the owner, or which session. Who sent a push has to be known before its body is read, so that a push of gigabytes from no one is refused before it is sent. Routing and who sent a request are not the hub's alone: any program that serves HTTP has both, so `Http` offers them in general, and the hub is one user of them.

What the engine already decides:

- **TCP is a capability, and HTTP sits on it** (ADR-0033: `Tcp`, `Listen`, `Listener`, `Accepted`, `Connect`, `ConnectUnix`, `Dialed`). A connection reads `Framing::Chunks` and leaves where a request ends to HTTP. The frames come on a `Reading` stream, paced by the reader's credit, and a write is a `Write` ask answered `Sent`, `Full`, or `HungUp`. A connection whose reader ends shuts itself.
- **A stream is a request held open, paced by the asker's credit** (ADR-0017: `Stream`, `Streams`, `Serving`, `More`). It is the engine's one form of backpressure. `Streams::part` grants one more part for each part taken.
- **A protocol reference crosses mail, and an actor can make one to itself** (ADR-0016: `ProtocolRef`, `ActorRef::protocol`; `Turn::me`). A named protocol says what each of its kinds is answered with, so whoever holds a `ProtocolRef<P>` can ask through it without knowing the actor's type.
- **A request is answered exactly once, and is not cancelled** (ADR-0017: `turn.hold`, `turn.answer`, `Unanswered`). A receiver that ends, fails, or lets a request go is answered for by the engine. An asker that gives up passes over the answer when it comes.
- **A capability is a root asked at a typed path** (ADR-0022: `ChildOf`, `path::<L>`, `Carries`), and **a root that needs nothing of its host is bootstrapped for every host** (ADR-0029: `impl<H: Host> Bootstrap<H>`).
- **No actor ends another** (ADR-0009). It is sent `Shut`, and closes itself.
- **An actor is handed each kind it lists, and an answer only of the kind its ask declared** (ADR-0013, ADR-0017: `Answer<A, C>`). A fallback is handed mail of a kind its actor does not list, and never an answer. **A kind's id is its name and its layout** (ADR-0006), so a generic kind is as many kinds as its layouts.

Input on a listening socket is untrusted. Its size, its shape, and how slowly it arrives all have to be bounded before anything reaches the program.

## Decision

**One capability, `Http`, in the crate `aethereal-http`, a server and a client on `Tcp`. It parses and writes HTTP/1.1 itself, with no third-party parser. Its ports are the listeners its settings name. Actors mount path prefixes on them while the program runs, each mount naming a guard that says who sent a request and a handler that answers it, and each request reaches its handler with its sender's principal, typed by the mount's scheme.**

```
Http                    root, singleton, asked at path::<Http>(())
 ├─ Server:listener     binds one listener through Tcp; holds its mounts; spawns an exchange for each connection
 │   └─ Exchange:n      reads one accepted connection; routes each request, asks its guard, then its handler; writes each response
 └─ Client:n            one connection Tcp dialed for it; writes each request it is asked; reads each response
```

```rust
impl ChildOf for Http     { type Parent = Top; }
impl ChildOf for Server   { type Parent = Http; }     // keyed by its listener's name
impl ChildOf for Exchange { type Parent = Server; }   // keyed by the server's count
impl ChildOf for Client   { type Parent = Http; }     // keyed by the root's count
```

- **An exchange is the server's side of one TCP connection.** Its config carries the `ActorRef<Accepted>` the listener made. It opens `Reading` on that connection in its `begin`, as the server opens `Accepting` on its listener in its own, and writes to it through `Writing`. HTTP holds no socket: every byte goes through `Tcp`. A `begin` asks as a turn does (ADR-0017), so `Streams::open` takes a `begin` as it takes a turn. A stream opened on the actor's first `Tick` would cost every connection a cycle before it was read.
- **The crate builds for every host, and is bootstrapped for every host** (`impl<H: Host> Bootstrap<H> for Http`). It needs nothing of its host but `Tcp`. A program without `Tcp` builds, and its `Mount` and `Connect` are answered `Unavailable`.

### A port is a listener the settings name

```rust
pub struct Listener {
    pub name: String,                                          // what a mount names it by
    pub port: u16,                                             // 0: any free port
    pub interface: Interface,
}
```

- **The root spawns a server for each listener as it begins,** keyed by the listener's name, and the server asks `Tcp` to `Listen` with `Framing::Chunks` in its own `begin`. Until `Tcp` answers, the server holds the mounts it is asked. On `Listening::Bound` it answers each, and every later one, with the port bound; on any other answer it logs why, and answers each `Unbound`. Two listeners of one name fail the root's `begin`.
- **No actor serves a port.** Which ports a program takes, and where each is reached, is the program's, set as its other settings are (ADR-0028), so no mounting actor owns a port the others mount on: the hub's MCP and its git share the sessions' port, and neither binds it. A listener's name says what it is for, as a namespace's does for `Files` (ADR-0032).

### A mount is asked of the root, and held by its listener's server

```rust
impl<S: Scheme> Carries<Mount<S>> for Http { type Answers = (Mounted,); }
impl Carries<Unmount> for Http { type Answers = (Unmounted,); }

pub struct Mount<S: Scheme> {
    pub listener: String,
    pub prefix: String,                                        // `/mcp`, `/git/`
    pub body: Body,
    pub guard: Guard<S>,
    pub handler: ProtocolRef<Routing<S>>,
}
pub enum Body { Whole { most_bytes: u32 }, Streamed { most_bytes: u64 } }

pub enum Mounted {
    Yes { port: u16 },                                         // the port its listener bound
    Taken,                                                     // a mount of the listener overlaps it
    Unbound,                                                   // its listener could not be bound
    NoListener,                                                // the settings name no listener of that name
    BadPrefix,                                                 // not a `/` and then a path
    TooLarge,                                                  // a whole body past the settings' `most_body_bytes`
    Full,                                                      // the listener holds its most mounts
    Unavailable,                                               // no Tcp in this program
}
pub struct Unmount { pub listener: String, pub prefix: String }
pub enum Unmounted { Yes, NotHeld }
```

- **The root hands a mount to its listener's server,** holding the asker's request until the server answers. Mounts change while the program runs: any actor may ask one at any time. One asked in a `begin` is answered on `Boot`'s chain, so an asker that quits on a refusal fails the boot (ADR-0020), as `Toolbox` does on a refused offer (ADR-0037).
- **A prefix matches a path at a segment's edge:** the path is the prefix, or goes on past it at a `/`, which a prefix that ends in `/` has already. So `/mcp` takes `/mcp` and `/mcp/x`, and not `/mcpx`. It is matched against the path as sent, with no normalising.
- **Mounts of one listener never overlap.** A mount whose prefix matches another's, or that the other's matches, is refused `Taken`. Each path is under one mount at most, and the order mounts were asked in never decides which. A path under none is answered `404`.
- **The server watches whoever holds each mount,** its asker, which need not be its handler, and drops the mounts of a holder that ends. `Unmount` takes out a mount its asker holds, and never one another holds.
- **A mount's handler is not watched.** A request asked of a handler that has ended is answered `Ended` by the engine, and the exchange writes `503`.
- **A body is gathered whole, or streamed to the handler,** as the mount says, and bounded by its `most_bytes`. A whole body is one blob in the mail (ADR-0042), so its limit is at most the settings' `most_body_bytes`, which `Http` checks against the engine's limits as it starts. A streamed body is never held whole, so its limit weighs nothing against the engine's blobs, and it is a `u64`, as a pushed pack runs past what a `u32` counts.

### A guard says who sent a request, before its body is read

```rust
pub trait Scheme: 'static { type Principal: Plain + 'static; }   // who a request may come from

pub enum Guard<S: Scheme> {
    As(S::Principal),                                          // fixed by where the mount is served
    By(ProtocolRef<Authenticating<S>>),                        // asked of an authenticator, for each request
}

pub struct Authenticating<S>(PhantomData<fn() -> S>);
impl<S: Scheme> Protocol for Authenticating<S> { type Kinds = (Authenticate,); }
impl<S: Scheme> Carries<Authenticate> for Authenticating<S> { type Answers = (Authentication<S>,); }

pub struct Authenticate {                                      // the head's part a guard reads; never the body
    pub method: Method,
    pub path: String,
    pub credentials: Credentials,
    pub peer: SocketAddress,
}
pub enum Credentials {                                         // read from the one `Authorization` header
    None,
    Bearer { token: String },                                  // RFC 6750
    Basic { user: String, password: String },                  // RFC 7617
    Other { scheme: String, parameters: String },
}
pub enum Authentication<S: Scheme> {
    Allowed(S::Principal),
    Challenged { scheme: String, realm: String },              // 401, with `WWW-Authenticate`
    Forbidden,                                                 // 403
}

pub struct Public;                                             // the scheme of a mount anyone may reach
impl Scheme for Public { type Principal = Anonymous; }
pub struct Anonymous;

pub struct AnyOf<P>(PhantomData<fn() -> P>);                   // every scheme whose principal is `P`, as a handler lists it
impl<P: Plain + 'static> Scheme for AnyOf<P> { type Principal = P; }
```

- **A scheme names who may send.** Its `Principal` is what a request arrives with: the hub's `Caller` for its sessions and its owner (ADR-0057). It is plain data (ADR-0004). It names a sender, and carries no reference or blob.
- **A handler states its principal, and not its scheme.** What it reads of a request is the principal, so it takes `Routed<S>` for every `S` whose principal is its own, in one generic impl, and is mounted under whatever scheme its mount's guard answers. Its declaration lists the impl once, at `AnyOf<P>`, as the root lists every `Mount<S>` at `Mount<Carried>` (see below). The scheme is named where a principal is decided: by an authenticator, which answers `Authentication<S>`, and by whoever asks the mount.
- **`Guard::As` fixes the principal by where the mount is served.** The hub's own listener is on the loopback, so every request on it is the owner's, and its mounts are guarded `As(Caller::Owner)`. **`Guard::By` asks an authenticator,** any actor that takes `Authenticating<S>`, with the request's head and its credentials.
- **A public mount is of the scheme `Public`,** guarded `As(Anonymous)`. Nothing in the exchange tells an open mount from another, and the handler's type says it takes anyone; a third guard would be one more path through the exchange for what a principal already says. A scheme that takes anyone and known senders alike puts an anonymous case in its own principal, which its authenticator answers to `Credentials::None`.
- **The exchange parses the credentials,** from the one `Authorization` header (RFC 7235), its scheme named in any case: `Bearer` and its token; `Basic` and its user and password, decoded from Base64 and split at the first `:`; any other scheme as `Other`, lowercased, with the rest as sent; and no header, `None`. An `Authorization` header sent more than once, or `Basic` credentials that do not decode, is `400`. A credential is a secret: the `Debug` of `Credentials` names its scheme and no more.
- **The credentials go to the guard, and nowhere else.** The exchange takes the `Authorization` header out of the request it asks the handler, whatever the guard, so no handler holds a bearer or a password, and an `As` guard leaves them unread.
- **`Challenged` is written `401` with `WWW-Authenticate: <scheme> realm="<realm>"`,** so a client that holds credentials sends them again: git's credential helper answers a `401` with `Basic`. `Forbidden` is `403`. A scheme that is not a token, or a realm holding `"`, `\`, or a control byte, is the authenticator's fault, and is `500`.
- **What a sender may do is the handler's to decide.** The guard says who sent a request, and nothing more: `Mcp` refuses a session's call of a session tool (ADR-0057) by the principal it is handed.

### Each request is routed, guarded, and then read

1. **The head is parsed,** and every limit on it checked, as the table below says.
2. **The server routes it.** The exchange asks its server which mount the path is under (`Match`, answered `Matched::Under` with the mount, or `Matched::Unmounted`), so each request is routed by the mounts as they stand when its head is parsed. A request under none is `404`.
3. **The guard answers.** `As` passes at once, with its principal. `By` asks the authenticator `Authenticate`, `within` `answer_within_millis`: `Allowed` carries on with its principal, `Challenged` is `401`, and `Forbidden` is `403`. An authenticator that has ended is `503`; one whose turn failed or that let the request go, `500`; and one past the deadline, `504`.
4. **Only then is the body read.** The mount's `most_bytes` is checked against the `Content-Length`, `413` before a byte is read; `Expect: 100-continue` is answered `100 Continue`; and the body is gathered whole, or streamed, as the mount says.
5. **The handler is asked `Routed<S>`,** the request and its principal.

- **No byte of a body is read before the guard allows it, and no `100 Continue` is sent.** While the route and the guard are out, the exchange grants its connection nothing, as while a request is out, so what the client sends waits in the kernel and TCP slows it: a push of gigabytes refused `401` costs what one read window holds. A request refused with its body unread is answered, then the connection closes, since where its body ends cannot be known without reading it.
- **The guard is asked for every request.** A connection kept alive is not a session: each request bears its own credentials, and nothing a guard answered is kept for the next.

### The principal crosses the exchange sealed

- **The exchange is one actor for every scheme, so it cannot be typed by one.** An asker handles the one kind its ask is answered with, as `Answer<A, C>`, and its ask is declared with it (ADR-0017: `Asks`, `DeclaredBy`); a fallback is handed mail, and never an answer (ADR-0013: `Others`); and a send is of a kind its sender names (ADR-0016). So an exchange could neither take an authenticator's `Authentication<S>` nor ask a handler `Routed<S>` of a scheme it does not name, and naming every scheme would be naming the hub. An erased ask, answered with any kind, was ruled out for `Mcp` (ADR-0037).
- **So the principal is written sealed:** its plain bytes, as a sequence of bytes. A kind's id is its name and its layout (ADR-0006), and a scheme enters `Mount<S>`, `Authentication<S>`, and `Routed<S>` only through the principal, so each of them has one layout, and one id, whatever `S`, as a `ProtocolRef<P>` is written as one erased reference whatever `P` (ADR-0016). The root, the servers, and the exchanges read them at a scheme of the crate's own, `Carried`, whose principal is the sealed bytes, unread. The exchange takes those bytes from the mount's `As` or from `Allowed`, and writes them into the `Routed` it asks.
- **Users see only `S`.** The asker writes a `Mount<S>`, the authenticator answers `Authentication<S>`, and the handler is handed `Routed<S>`, its `S::Principal` read. A `Mount<S>` ties its guard and its handler to one `S`, so the bytes an exchange carries to a handler were written as the principal that handler reads. A mount of any scheme is asked at `path::<Http>(())`, as the root handles every `Mount<S>` in one generic impl, `impl<S: Scheme> Handles<Mount<S>> for Http`, which its declaration lists once, as `Mount<Carried>`, the id they all share.
- **One actor serves one principal.** `Routed<A>` and `Routed<B>` are one kind, which a type lists once (ADR-0013), so a type that would read two principals does not build, as one that takes two streams of one part does not (ADR-0017). Every scheme of its one principal reaches it through its one generic impl, listed at `AnyOf<P>`. An authenticator answers one scheme, for the same reason, and names it, as its handler of `Authenticate`, a kind of no scheme, cannot be generic over one.

### A handler takes its request only from an exchange

```rust
impl Actor for Mcp { type Handles = (Routed<AnyOf<Caller>>, /* .. */); }

impl<S: Scheme<Principal = Caller>> Handles<Routed<S>> for Mcp {
    type Sends = (/* .. */);
    type From = ActorRef<Exchange>;                       // who may ask it a request

    fn handle(&mut self, routed: Routed<S>, turn: &mut Turn<'_, Self, Self::Sends, Self::From>) -> Result<(), Fault> { /* .. */ }
}

impl Actor for Bearers { type Handles = (Authenticate, /* .. */); }

impl Handles<Authenticate> for Bearers {
    type Sends = (/* .. */);
    type From = ActorRef<Exchange>;

    fn handle(&mut self, ask: Authenticate, turn: &mut Turn<'_, Self, Self::Sends, Self::From>) -> Result<(), Fault> { /* .. */ }
}
```

- **A principal is believable because only an exchange sends one.** A handler states `type From = ActorRef<Exchange>;` on its `Handles<Routed<S>>` impl, and an authenticator on its `Handles<Authenticate>` impl (ADR-0058), so no other actor can hand a handler a principal, or try an authenticator's credentials one by one. The kind is listed as itself, and its sender check is ADR-0058's library form, `ActorRef<T>`; HTTP writes no sender check of its own. That check is a sender guard of ADR-0058 (`Guard<A>`), not a mount's `Guard<S>`, which says who sent the request over HTTP.
- **The check is made where the request is delivered.** The exchange asks through the `ProtocolRef` its mount names, which names no receiver type, so no build check sees the ask, and the one that holds is delivery's, which covers a guest as well (ADR-0058).
- **Neither needs the exchange it is handed.** `turn.from()` answers the `ActorRef<Exchange>`, but a handler answers the request it was asked, with `turn.reply` or a `Held`, and an authenticator answers its ask, so neither reads it.
- **An ask from any other sender goes to the handler's `refused`,** whose default logs the sender and answers `Unanswered::Unreadable`. Neither `Mcp` nor `Bearers` overrides it.
- **An exchange stands only where a server spawned it.** `Exchange`'s parent is `Server`, and `Server`'s is `Http` (ADR-0022), so an actor of the type is one this program's HTTP made, for a connection it accepted.

### Each request is asked of its mount's handler

```rust
pub struct Routing<S>(PhantomData<fn() -> S>);
impl<S: Scheme> Protocol for Routing<S> { type Kinds = (Routed<S>,); }
impl<S: Scheme> Carries<Routed<S>> for Routing<S> { type Answers = (Response,); }

pub struct Routed<S: Scheme> { pub request: Inbound, pub principal: S::Principal }
pub enum Inbound { Whole(Request), Streamed(StreamedRequest) }

pub struct Request {
    pub method: Method,
    pub path: String,                 // the target's path, as sent
    pub query: String,                // after the `?`, empty when there is none
    pub headers: Vec<Header>,         // in the order sent, duplicates kept, but `Authorization`
    pub body: Bytes,
    pub peer: SocketAddress,
    pub port: u16,
}
pub struct Response {
    pub status: Status,               // a closed enum of the final statuses HTTP names: Ok, NotFound, ..
    pub headers: Vec<Header>,
    pub body: ResponseBody,           // Whole(Bytes), or Streamed from a source
}
pub struct Header { pub name: String, pub value: String }     // names lowercased by the parser
pub enum Method { Get, Head, Post, Put, Delete, Patch, Options }
```

- **An exchange asks the handler `Routed<S>` directly,** through the `ProtocolRef<Routing<S>>` its mount names. The request crosses no other actor. The handler is any actor that takes `Routing<S>`, usually the mount's asker itself: `handler: turn.me().protocol()`.
- **The handler answers in the turn it is asked (`turn.reply`), or holds the request and answers in a later one** (`turn.hold`, `turn.answer`), as MCP does once an engine has answered. The ask is the correlation: the exchange keeps no table, and the handler keeps nothing but the `Held` it chose to keep.
- **A request the handler does not answer is answered for it.** When the handler has ended the exchange writes `503`. When its turn failed, it let the request go, or it never answered, the exchange writes `500`.
- **The exchange writes the framing headers itself.** It writes the status line, the handler's headers, `Content-Length` from the body, or `Transfer-Encoding: chunked` for a streamed body of no known length, and `Connection: close` when it will close. A `Content-Length`, `Transfer-Encoding`, or `Connection` among the handler's headers is dropped and recorded in the log. A response to `HEAD` has its body dropped and keeps its `Content-Length`.
- **Many requests are out at once, one per connection.** The handler takes them as they come; how many it holds at once is bounded by the servers' `most_exchanges`.

### A streamed mount hands its handler the body as it arrives

```rust
pub struct StreamedRequest {
    pub method: Method,
    pub path: String,
    pub query: String,
    pub headers: Vec<Header>,
    pub length: BodyLength,                            // Known(n) by its Content-Length, 0 for none; or Chunked
    pub body: ProtocolRef<Streamed<RequestBody>>,      // the exchange, which serves the body's stream
    request: u64,                                      // which of the exchange's requests it is
    pub peer: SocketAddress,
    pub port: u16,
}
impl StreamedRequest { pub fn read_body(&self) -> ReadBody; }

pub struct RequestBody;                                // one request's body, streamed as it arrives
impl Stream for RequestBody { type Open = ReadBody; type Part = BodyBytes; type Done = BodyRead; }
pub struct BodyBytes { pub bytes: Bytes }              // what one read brought, decoded
pub enum BodyRead { Whole, TooLarge, Malformed, Stalled, HungUp(HungUp), Busy, Cut }
```

- **The mount's `most_bytes` is checked as a whole body's is:** by its `Content-Length` once the guard has allowed it, `413` from the head alone, or as a chunked body is decoded.
- **The exchange asks the head, and the handler reads the body.** Once the guard has allowed the request, the exchange asks the handler `Routed<S>` with `Inbound::Streamed`, and enters `Inflow`: the handler opens a `RequestBody` stream on `body`, with `read_body()`, and the exchange serves it with `Serving`, as a client serves `Receiving` (ADR-0017). Bytes that come before the stream is open wait in the exchange's buffer, and the connection is granted nothing, so they are bounded by the read window. The open names the request it reads; an open of a body that another stream reads, that has been read, or that is not the request out is answered `Busy` at once, so a stale stream never reads the next request's body.
- **The handler's credit paces the connection.** The exchange takes each chunk without granting for it (`part_held`), decodes what its buffer holds while the stream has credit (`Serving::has_credit`), sends it as one `BodyBytes`, and grants the connection what it withheld only once more bytes are all the body needs. A handler that falls behind stops the exchange reading, and TCP slows the client.
- **The stream is ended once, with `BodyRead`:** `Whole` where the framing ends; `TooLarge` past the mount's limit, with `413`; `Malformed` for chunked framing that breaks, with `400` (`413` for a chunk's line past `most_head_bytes`); `Stalled` when the body has not moved for `stall_within_millis`, and the exchange closes with no answer; `HungUp(how)` when the connection hangs up or the exchange is shut; `Busy` as above; and `Cut` when the handler answers before the body has ended, when the rest is not read and the connection closes once the response is sent. A handler that stops the stream with `Enough`, or ends, leaves the body unread too: the exchange waits for the answer and closes once it is written.
- **The streamed request is asked `within(Due::Never)`.** A body may take as long as it keeps moving, so the ask cannot carry `answer_within_millis` from its head, and a stream the handler opens in the turn it is asked inherits the same `Never` (ADR-0041), so nothing cuts a long body off. The stall limit bounds the body instead: the exchange sleeps until `stall_within_millis` after it last moved, and when the sleep comes and it has moved since, sleeps again until it would be late. Once the body is read, or will not be, the exchange is in `Awaiting`, and sleeps until `answer_within_millis` after it; then it writes `504` and closes, and the answer, when it comes, is passed over. What the handler asks on the request's behalf states its own deadlines.
- **Pipelining holds.** The body's decoder stops where its framing ends, so the bytes after it stay in the buffer for the next request, which is parsed once the handler has answered and the credit withheld is granted, as after a whole request.

### A response's body may be streamed from a source

```rust
pub enum ResponseBody { Whole(Bytes), Streamed(StreamedBody) }
pub struct StreamedBody {
    pub source: ProtocolRef<Streamed<ResponseSource>>, // the actor that makes the body
    pub body: u64,                                     // the handler's number for it, which the stream opens with
    pub length: ResponseLength,                        // Known(n), or Unknown
}

pub struct ResponseSource;                             // one response's body, streamed as it is made
impl Stream for ResponseSource { type Open = SendBody; type Part = ResponseBytes; type Done = SourceEnd; }
pub struct SendBody { pub body: u64 }
pub struct ResponseBytes { pub bytes: Bytes }
pub enum SourceEnd { Whole, Failed, Stopped }
```

- **A handler may stream its response,** whether its mount's body is whole or streamed: it answers with `ResponseBody::Streamed`, naming a source, which may be itself or an actor it started for the request, such as a pipe to a child process. The exchange writes the head, opens a `ResponseSource` stream on the source with `SendBody`, and enters `Outflow`. `body` lets one source tell the bodies it is asked for apart. The open is made in the turn that handles the handler's answer, which is no request, so it carries no deadline (ADR-0041).
- **The framing follows what is known.** A `Known(n)` length is written as `Content-Length: n`, and its parts as they are. An `Unknown` length is written in chunks to an HTTP/1.1 client, each part one chunk, its size line a small blob of its own and its data the part itself, passed on without being copied; the body ends with the last chunk once the source ends it `Whole`. An HTTP/1.0 client reads no chunks, so its body has no length header and ends with the connection's close. A part of no bytes is granted back and writes nothing, since an empty chunk would end the body.
- **What the connection has sent paces the source.** The exchange takes each part without granting for it (`part_held`), queues it, and keeps one write out at a time, of everything queued, each part pinned until its write is answered `Sent`; then it grants the source as many parts as the write carried. So the source runs at most `window` parts ahead of what the kernel has taken, a client that reads slowly fills the kernel's buffers and stops the writes, and nothing of the body is held but the window. A write answered `Full` was taken whole or not at all, so it is written again, its first part alone; with nothing else of the response unsent, a part the connection still will not take never fits, and the connection closes. A part is best kept well under TCP's `most_unsent_bytes`.
- **Failure after the head closes the connection.** The status is written before the body, so a body that breaks cannot be answered otherwise: when the source ends `Failed`, ends without answering, or sends more or fewer bytes than its `Known` length, its stream is stopped and the exchange closes without ending the body. A chunked body then lacks its last chunk and a sized one its last bytes, so the client sees it cut short, and a close-delimited body, to HTTP/1.0, cannot be told from a whole one.
- **The client's hang-up stops the source.** When the connection hangs up, a write is answered `HungUp`, or the exchange is shut, the exchange sends the source `Enough` before it closes, and the source ends the stream `Stopped` and stops making the body.
- **A long body is not timed as a whole.** A response may stream for as long as it keeps moving, so `Outflow` is timed by `stall_within_millis`, as a request's streamed body is: the exchange sleeps until that long after the body last moved, a part taken or a write sent, and once the sleep comes and it has not moved since, the source is stopped and the connection closes.
- **A response with no body enters no `Outflow`.** A response to `HEAD`, or of a status with no body, is written as its head alone, with its `Content-Length` when its length is known. Its stream is opened and stopped in the same turn, so a source that waits for its open, or holds a child process for it, is told at once it will not be read.
- **Pipelining holds.** A request is out until its response is written, so while `Outflow` lasts the exchange grants its connection nothing, and the request after is parsed once the last chunk is written, never interleaved with the body.

### An exchange parses as chunks arrive, one request at a time

```
Accepted ─Frame─▶ Exchange: Idle ─▶ Head ─▶ Matching ──ask Match──▶ Server
                                              └▶ Guarding ──ask Authenticate──▶ guard        (By; As passes at once)
                                                   └▶ Body { head, body } ─▶ Answering ──ask Routed<S>──▶ handler
                                                                                 │
Accepted ◀─Write─ Exchange ◀──────────────── answer Response ────────────────────┴──────────────── handler

a streamed mount:         Guarding ─▶ Inflow ──ask Routed<S>──▶ handler ──open RequestBody──▶ Exchange
                                        │ BodyBytes, as credit allows ──────▶
                                        └▶ Awaiting ◀── answer Response ─────

a streamed response:      answer Response { Streamed } ─▶ Outflow ──open ResponseSource──▶ source
                                    │ ◀──────────── ResponseBytes, as credit allows ──
                                    └ Write each part ─▶ Accepted ── Sent ─▶ More to the source
```

- **The exchange keeps what it has decoded, not the raw bytes.** In `Head` it buffers until the blank line that ends the head, then parses it in one pass. In `Body` it decodes the body as its head frames it, into one buffer: exactly `Content-Length` bytes, or chunks up to the empty line that ends the last chunk's trailer, decoded wherever the reads cut them. The decoder is the one the client reads a response's body with, in the crate's `body` module. Bytes past the end of the request stay in its buffer for the next one.
- **While a request is out, the exchange grants no credit,** but what a streamed body needs to go on. It takes the `Frame`s still in flight without granting more, and grants what it held back once its response is written. So a client that sends requests back to back, pipelining, waits in the kernel, and TCP slows it down. What the exchange holds meanwhile is bounded by the `Reading` window times its chunk size. This needs two methods on `Streams` (ADR-0017): `part_held`, which takes a part without granting for it, and `grant`, which grants a stream a number of parts.
- **Connections are kept alive,** HTTP/1.1's default. The exchange closes after its response is written (`Wrote::Sent`) when the request said `Connection: close` or was HTTP/1.0, or when its streamed body ends with the close. It also closes when the write is answered `Full` or `HungUp`, or the read stream ends.
- **`Expect: 100-continue` is answered `100 Continue`** once the guard has allowed the request and its `Content-Length` is within the mount's limit, before the body is read, when the request has a body, by its `Content-Length` or in chunks. It is never sent before the guard has answered.

### Limits on untrusted input

| The request | The exchange's answer |
|---|---|
| a head past `most_head_bytes` | `431`, then close |
| a path under no mount of its listener | `404`; then close when it has a body, which is not read |
| an `Authorization` header sent more than once, or `Basic` credentials that do not decode | `400`, then close |
| a guard that answers `Challenged` | `401` with `WWW-Authenticate`; then close when it has a body, which is not read |
| a guard that answers `Forbidden` | `403`; then close when it has a body, which is not read |
| a guard that has ended; one whose turn failed or that let the request go; one past `answer_within_millis` | `503`, `500`, or `504`, then close |
| a whole body past its mount's `most_bytes`, by its `Content-Length` | `413`, then close, before the body is read |
| a chunked whole body decoded past its mount's `most_bytes`, or a chunk's size line or trailer field past `most_head_bytes` | `413`, then close, as soon as it is decoded that far |
| a chunk's size line, its data's line ending, or a trailer field that does not parse | `400`, then close |
| a request line or header that does not parse; a bare LF; a folded header; a header that is not visible ASCII | `400`, then close |
| `Content-Length` sent more than once, or not a number | `400`, then close |
| a `Transfer-Encoding` beside a `Content-Length`, or in an HTTP/1.0 request | `400`, then close |
| a transfer coding other than `chunked` alone (`gzip`, `gzip, chunked`, two `chunked`) | `501`, then close |
| a method not in `Method` | `501`, then close |
| an HTTP version other than 1.0 and 1.1 | `505`, then close |
| a target not in origin form (`/path?query`) | `400`, then close |
| a request, head and body, not whole within `request_within_millis` of its first byte | close, no answer |
| a streamed body past its mount's `most_bytes`, by its `Content-Length` | `413`, then close, before the handler is asked |
| a streamed chunked body decoded past its mount's `most_bytes` | `413`, then close; its stream ends `TooLarge` |
| a streamed body that has not moved for `stall_within_millis`: no bytes came, or the handler opened no stream or granted no credit | close, no answer; its stream ends `Stalled` |
| a streamed body read, and no answer within `answer_within_millis` after | `504`, then close |
| no request within `idle_within_millis` of the last response | close, no answer |
| a streamed response that has not moved for `stall_within_millis`: the source sent nothing, or the client read nothing | close, the body cut short; its source is stopped |
| no answer within `answer_within_millis` | `504`, then close; the answer, when it comes, is passed over (ADR-0041: the handler is asked `within` this deadline, and the `504` is written when the ask is answered `Expired`) |

- **A request's body is framed one way, or refused.** Request smuggling comes from a body that two readers frame differently, so a `Transfer-Encoding` beside a `Content-Length`, or in HTTP/1.0, which has no transfer codings (RFC 9112 §6.1), is `400`, never settled in favour of one. `chunked` alone is decoded; any other coding, which the exchange does not decode, is `501`. A chunked body is gathered whole, as one with a `Content-Length` is, and since it has no length to check before it is read, its decoded length is checked against its mount's `most_bytes` as it is decoded.
- **Each deadline is a `Sleep`** (ADR-0018). As an exchange enters a phase that has one, it runs a `Sleep` until that phase's deadline, its context naming the phase, and cancels the last one it ran. A sleep answered for a phase the exchange has left is passed over. Nothing in HTTP subscribes to `Tick`, so a program that serves HTTP runs no cycle for it (ADR-0033). No deadline is checked against `turn.now()` on each `Tick`.
- **A refused request still writes a response where one is owed,** then the exchange closes, but for a `404`, `401`, or `403` of a request with no body, after which the connection is kept. The handler never sees it.
- **A request whose deadline passes is still out.** Requests are not cancelled (ADR-0017), so the handler's answer still comes, and the exchange, closing or closed, passes over it.

### A client asks other servers

```rust
impl Carries<Connect> for Http { type Answers = (Connected,); }
impl Carries<Fetch> for Client { type Answers = (Fetched,); }

pub struct Connect { pub peer: Peer }
pub enum Peer { Tcp { host: String, port: u16 }, Unix { path: SocketPath } }
pub enum Connected { Open { client: ActorRef<Client> }, Unreached(Unreached), Full, Unavailable }

pub struct Outgoing { pub method: Method, pub path: String, pub query: String, pub headers: Vec<Header>, pub body: Bytes }
pub struct Fetch { pub request: Outgoing }                       // answered once the body is whole
pub enum Fetched { Whole(Reply), Failed(Failure) }
pub struct Reply { pub status: u16, pub headers: Vec<Header>, pub body: Bytes }

pub struct Receiving;                                            // one response, streamed as it arrives
impl Stream for Receiving { type Open = Follow; type Part = Received; type Done = Finished; }
pub struct Follow { pub request: Outgoing, pub switch: Switch }  // Switch::{Stay, To { protocol }}
pub enum Received { Head(ReplyHead), Switched { head: ReplyHead, writing: ProtocolRef<Writing> }, Bytes(Bytes) }
pub enum Finished { Whole, Closed(HungUp), Failed(Failure) }
pub enum Failure { Busy, Unwritable(Unwritable), Full, Malformed, TooLarge(Limit), HungUp(HungUp), NoRoom }
```

- **The root dials, and a client stands beneath it.** The root asks `Tcp` to `Connect` or `ConnectUnix` with
  `Framing::Chunks`, holding the `Connect`, and on `Open` spawns a `Client` on the `ActorRef<Dialed>`; otherwise
  `Unreached` carries `Tcp`'s reason. It watches whoever asked and shuts their clients when they end, and holds at
  most `most_clients`.
- **One request at a time, and the connection kept.** A request while one is out is `Busy`. A response whose body
  ended where its framing said leaves the connection for the next request. The client closes when a response said
  `Connection: close`, was HTTP/1.0, or ran until the connection closed; when the connection hangs up; when a response
  breaks a rule or a limit; or when sent `Shut`. A request asked of it after that is answered `Ended` by the engine.
- **The client writes the framing.** `Host` (the host and port dialed, `localhost` for a Unix socket), `Content-Length`
  when there is a body or the method expects one, and `Connection: upgrade` with `Upgrade` for a switch. A request
  that names one of these, has a header that is not a token or holds a control byte, or a target not in origin form, is
  `Unwritable`, and nothing is sent. It sends no `Expect` and pipelines nothing.
- **A response is parsed by the pieces a request is,** shared in one module: where the head ends within its limit, its
  lines, its headers, and its `Content-Length`; a status line takes the place of the request line, with any reason
  phrase (Docker writes `101 UPGRADED`). Informational heads other than `101` are passed over. The body is framed as
  RFC 9112 §6.3 says: none for a `HEAD`, an informational status, `204`, or `304`; `chunked` alone; a
  `Content-Length`; or, with neither, until the connection closes. Any other coding, or a coding beside a
  `Content-Length`, is `Malformed`.
- **Whole or streamed is the asker's choice.** `Fetch` gathers the body, refusing one past `most_reply_body_bytes`, by
  its length before it is read when it has one. `Receiving` sends the head, then what each read brought of the body,
  decoded wherever the reads cut a chunk, its size line, or its line ending; a streamed body has no limit, as it is
  never held whole. A chunk's size line or a trailer's field past `most_reply_head_bytes` is too large.
- **The asker's credit paces the connection.** The client takes each chunk its connection reads without granting for it
  (`part_held`), and grants the credit back only once more bytes are all it needs. While its asker has no credit it
  grants nothing, so the connection stops reading and the socket holds the server back. What the client holds
  meanwhile is bounded by its window of chunks.
- **A switch hands the connection over raw.** A `Follow` that asks to switch, answered `101`, or `2xx` with a body that
  runs until the connection closes (what Docker writes when it takes over an attach asked without `Upgrade`), is sent
  `Switched` with a `ProtocolRef<Writing>` to the `Dialed`, and every later part is the connection's own bytes, those
  that came in the read with the head first. HTTP is no longer read. The client goes on reading and relaying, since a
  connection has one reader and one whose reader ends hangs up (ADR-0033); writes go to the connection directly. The
  stream finishes `Closed(how)` when the connection hangs up. An asker that stops a stream with `Enough`, or ends,
  leaves a connection mid-response, and the client closes.
- **The client times nothing.** An asker that will not wait asks within a deadline (ADR-0041), and the answer that
  comes later is passed over.

### Ending is by mail

| Type | Ends when |
|---|---|
| `Server` | it is sent `Shut`, by whoever holds it, or `Tcp`'s accept stream ends. It sends `Shut` to its listener and to each exchange, and closes, and its mounts go with it |
| `Exchange` | it is sent `Shut`, or it closes the connection as above, or its read stream ends |
| `Client` | it is sent `Shut`: by the root when the asker of `Connect` ends, or by whoever holds it. It also ends when its connection's read stream ends, when a response closes the connection or breaks a rule or a limit, and when the asker of the stream it serves stops it or ends |

When an exchange closes, its read stream's asker is gone, so the TCP connection beneath it shuts itself (ADR-0033). An exchange does not send `Shut` to it.

### Settings

```rust
#[settings]
pub struct HttpSettings {
    pub listeners: Vec<Listener>,      // the ports the program serves; none by default
    pub most_mounts: u32,              // per listener
    pub most_exchanges: u32,           // per server; past it, an accepted connection is shut at once
    pub most_head_bytes: u32,          // 16 KiB
    pub most_body_bytes: u32,          // 8 MiB: the most a whole mount's `most_bytes` may be
    pub chunk_bytes: u32,              // the `Chunks` framing's `most_bytes`
    pub window: u32,                   // the parts an exchange's read stream is granted
    pub request_within_millis: u32,    // a streamed body is timed by the stall limit instead, from its head
    pub stall_within_millis: u32,      // 60 s: the longest a streamed body, or a streamed response, may go without moving
    pub idle_within_millis: u32,
    pub answer_within_millis: u32,
    pub most_clients: u32,
    pub most_reply_head_bytes: u32,    // 16 KiB: a response's head, and each line of a chunked body
    pub most_reply_body_bytes: u32,    // 8 MiB: a body read whole; one streamed has none
}
```

The section is `http`. A listener of `Interface::Settings` binds where `Tcp`'s setting says, loopback by default (ADR-0033: `TcpSettings::interface`).

### A tool call through the hub

```
agent ─POST /mcp─▶ Accepted ─Frame─▶ Exchange ─ask Match──────────────▶ Server: `/mcp` on the sessions' listener
                                         │ ─ask Authenticate─────────▶ Bearers: the bearer names session 3
                                         │ ─ask Routed<SessionBearer>▶ Mcp ─ask─▶ tool, as Caller::Session { session: 3 }
                                         ▲                               │ (holds the request until the tool answers)
agent ◀───────────── Accepted ◀─Write── └── answer Response ◀───────────┘
```

On the owner's listener the mount is guarded `As(Caller::Owner)`, and no authenticator is asked. Both mounts are asked by the hub's program, which names `Mcp` and `Bearers` where neither names the other (ADR-0057).

## Consequences

- MCP gets an endpoint by mounting `/mcp` with itself as the handler, and answering each `Routed`. It reads `path`, `method`, and its headers from the request, and who sent it from the principal. What `202` and `405` mean to MCP are MCP's business.
- **Routing and who sent a request are `Http`'s, and the hub is one user of them.** A handler names no port and checks no credential, so the hub's tools and its git share a port without either knowing of the other, and a program with one public page mounts it `As(Anonymous)`.
- **A request crosses one actor on its way to the handler,** the exchange that parsed it, which asks its server for the route and may ask a guard: two small asks, which chain within the step (ADR-0013). It is copied from the frames into the exchange's buffer, into the ask, and by each actor that keeps it. Nothing on the way waits on a cycle: the request is read in the step the host wakes for its bytes, and the response written in the handler of its `Write` (ADR-0033).
- **A handler that fails or forgets is caught at once,** by the engine's answer for it, and not by a deadline.
- **The handler does not pace how many requests it takes.** Each connection has at most one out, so they are bounded by `most_exchanges` for each server. A handler that must take fewer holds what it cannot start, or the limit is set lower.
- **A handler cannot learn that its client hung up.** The exchange closes, and the answer that comes later is passed over. A handler that should stop work on a hang-up needs a notice it can watch for, and none is designed here.
- Every limit is enforced before a request reaches the handler, so memory per exchange is bounded by `most_head_bytes` plus `most_body_bytes` plus the read window. A streamed body is never held: what an exchange holds of it is its read window and one part. The number of exchanges is bounded by `most_exchanges`.
- **A guard is asked for every request, and holds nothing for the next.** The hub's guard compares a few dozen bearers; a guard that is costly to ask keeps what it learned itself.
- **A handler's trust in its principal rests on the sender it states,** `type From = ActorRef<Exchange>;` (ADR-0058), which this ADR uses and does not define.
- **A handler names its principal and no scheme, and an authenticator no handler.** What ties them is the mount, asked by whoever names both: a program's own root, as the hub's is (ADR-0057).
- **A principal is plain, and travels sealed.** It cannot carry a reference or a blob, and the schema of `Routed<S>` shows it as bytes; the handler reads it typed.
- **A streamed mount's handler holds its request for as long as the body moves.** The stall limit, not a deadline, frees it from a client that stops sending; a handler that keeps reading a body it will never accept says so by answering, which ends the stream `Cut` and closes the connection.
- `Streams` gains `part_held` and `grant`, a reader's way to stop granting while it is busy. TCP's connections do not need them, and any stream asker that works on one part at a time can use them.
- **A streamed response holds its source for as long as the client reads.** The stall limit frees both from a client that stops reading, and the source learns of a hang-up by `Enough`. What a source holds meanwhile is its own: a pipe to a child process is paced by the same credit, so the child blocks on its full pipe while the client is slow.
- **Not built, by choice:** a chain of middleware, as a mount has one guard, and one guard says who; authorization beyond the guard's answer, which is the handler's; and mounts that overlap, with the longest prefix winning, as one mount for each path never needs an order.
- **Not decided here:** server-sent events, whose source is a streamed response once a tool needs to report progress, and which would want a write of each event at once rather than a stall limit; routing finer than a prefix, while a handler matches on `path`, or hands requests on to others; TLS; `Date` headers, which the exchange does not write. For the client: TLS, HTTP/2, redirects, cookies, pipelining, codings other than `chunked`, and a pool of connections.

## Alternatives considered

- **Routing and who sent a request inside `Mcp`,** as the hub first had them: one actor bound both ports, held the bearers, and stamped each call's caller. Git on the same port would go through the tool router, and HTTP's routing would be shaped to the hub.
- **An `Origin` type in `http` naming the owner or a session.** It types the principal without generics, but `http` would name the hub's callers, and every other program would carry them.
- **A string principal, as CGI's `REMOTE_USER`.** One kind, no generics, but every typed user parses it back, and a principal that does not parse is found by each handler rather than refused by a type.
- **An erased principal, its bytes decoded by each handler.** The same bytes cross the exchange as now, but every handler decodes them and checks the scheme itself. Sealed, the codec does it once, and a handler is handed `S::Principal`.
- **A general chain of middleware.** Machinery with no second use: one guard per mount says who sent a request, and what a handler does with it is its own.
- **A third guard, `Open`, for a public mount.** One more path through the exchange, where a scheme whose principal is `Anonymous` says the same with none.
- **A generic actor for each scheme between the exchange and the handler,** typed by `S`, taking the authenticator's answer and asking the handler. No principal sealed, but it needs a spawn by something that names `S`, which only the mount's asker does, a hop on every request, and a table of principals between the guard's answer and the body's end.
- **Erased verbs in `Turn`,** an ask answered with any kind and a send of bytes as any kind. Ruled out for `Mcp` (ADR-0037): untyped verbs in the core, and a wildcard in the send check, where sealing changes no verb.
- **Trust from the form of `Routed` alone,** whose constructor only `http` has. It holds against native code, which must build a value to send it, and not against a guest, which writes bytes.
- **Each exchange holding its server's mounts.** A request would save an ask, but each copy would be told of every change, and a request parsed between a change and its telling would go to the wrong handler. The server holds the one table, and is asked.
- **A port served by whoever asks `Serve`, and mounted on by naming that server.** The asker would own the port for every mount on it, as `Mcp` owned the hub's, and a mount asked before the bind was answered would have nothing to name. A listener the settings name exists from the root's `begin`.
- **The streamed request asked within `answer_within_millis`, and its stream opened with a deadline of its own.** The stream would live, but the request it belongs to would expire under it, and the client would be answered `504` while its body was still being read. The ask carries no deadline, and the exchange times the body by its stall and the answer from the body's end.
- **The body sent to the handler unasked, as parts of the request.** The handler could not pace it, and an exchange would hold whatever the handler had not yet taken. A stream the handler opens is paced by its credit, and is ended once with how the body was read.

- **Requests as a stream the handler opens on the server,** each part an `Incoming { request, exchange }`, answered by a `Respond` tell sent to the exchange. The handler's credit would pace how many requests it takes. But every request would cross the server, which would keep a queue; the answer would be a tell the exchange could not tie to a request, so a handler that failed or forgot would be found only by the deadline; and it needs five kinds where an ask needs two. It rests on a false premise, that the handler cannot be named in mail: a `ProtocolRef` crosses mail, with a codec written as an `ErasedActorRef`'s is (ADR-0016).
- **The server asks the handler, and forwards the answer to the exchange.** One actor would see every request, for no gain: the exchange can ask the handler itself.
- **HTTP's framing in `Tcp`,** as a third `Framing` case. Rejected in ADR-0033: TCP would know HTTP's rules.
- **A third-party parser** (`httparse`). Less code to write. The hub stack is in-house by choice, and a request head is a small grammar with limits that have to be ours anyway.
- **Refusing every `Transfer-Encoding`.** It shuts out smuggling with no decoder to write, but it also refuses every client that sends a body whose length it does not know up front, and the client already decodes chunks. Refusing a body framed two ways shuts out the smuggling as well.
- **A switched connection handed to its asker as the `Dialed` itself.** One hop less for each read. But a connection
  has one reader, and one whose reader ends hangs up (ADR-0033), so `Tcp` would need a way to hand its reader over, and
  the chunks already granted to the client would reach it after the handover. The client relays what it reads; writes
  go to the connection directly.
- **A switch as an ask of its own, answered once.** Its bytes would still need a stream, opened after the answer, with
  the bytes that came with the head held in between. The stream that streams a body carries a switched connection's
  bytes the same way.
- **A client for each request, closing the connection once it is answered.** Nothing to keep between requests, but
  every request to Docker would dial again.
- **A streamed response's body as parts the handler sends unasked, after its answer.** The exchange could not pace them, and would hold whatever the client had not yet read. A stream the exchange opens is paced by its credit, and is ended once with how the body was made.
- **Each part of a streamed response written as it comes, several writes out at once.** Fewer turns between parts, but a write answered `Full` would be followed by later ones the connection took, so the body would go out of order, and the parts already handed on could not be written again. One write out at a time, of everything queued, keeps the order, and lets a write the connection would not take be written again.
- **A streamed response timed by `answer_within_millis`.** A pack of gigabytes to a slow client would be cut off while it was still moving. The stall limit bounds a response that stops, not one that is long.
- **Answering pipelined requests concurrently.** Responses must go out in request order, so the exchange would queue responses behind slower ones. One request at a time, with credit withheld, keeps the order and the bound.
