# ADR-0035: HTTP

- **Status:** Proposed
- **Date:** 2026-10-28

## Context

The hub's MCP endpoint is HTTP. MCP's Streamable HTTP transport asks very little of it. The client POSTs one JSON-RPC message, and the server answers with one JSON body, or with `202 Accepted` for a notification. A GET, which would open a stream of the server's own messages, may be answered `405`. The hub also reaches Docker's Engine API, which is HTTP/1.1 over a Unix socket (ADR-0057), so the engine needs a client as well: one that asks over TCP or a Unix socket, keeps its connection between requests, streams a response it should not hold whole, and hands the connection over when Docker switches it to a raw stream. The hub will also take `git push` over git's smart HTTP, whose request bodies run to gigabytes, so a request's body must reach whoever reads it as it arrives rather than gathered whole; and a fetch is answered with a pack of gigabytes, made as `git upload-pack` writes it, so a response's body must be written as it is made. TLS can come later.

The hub serves two ports: the owner's, on the loopback, and the sessions', where the containers reach it. On each, a request has to arrive at its handler knowing who sent it: the owner, or which session. Who sent a push has to be known before its body is read, so a push of gigabytes from no one is refused before it is sent. And one port will carry more than one handler: the sessions' port takes MCP now and git later, each under paths of its own. None of this is the hub's alone: any program that serves HTTP routes requests and says who sent them, so the pieces are general, and the hub is one user of them.

What the engine already decides:

- **TCP is a capability, and HTTP sits on it** (ADR-0033: `Tcp`, `Listen`, `Interface`, `Listener`, `Accepted`, `Connect`, `ConnectUnix`, `Dialed`). A connection reads `Framing::Chunks` and leaves where a request ends to HTTP. The frames come on a `Reading` stream, paced by the reader's credit, and a write is a `Write` ask answered `Sent`, `Full`, or `HungUp`. A connection whose reader ends shuts itself.
- **A stream is a request held open, paced by the asker's credit** (ADR-0017: `Stream`, `Streams`, `Serving`, `More`). It is the engine's one form of backpressure. `Streams::part` grants one more part for each part taken.
- **A protocol reference crosses mail, and an actor can make one to itself** (ADR-0016: `ProtocolRef`, `ActorRef::protocol`; `Turn::me`). A named protocol says what each of its kinds is answered with, so whoever holds a `ProtocolRef<P>` can ask through it without knowing the actor's type.
- **A request is answered exactly once, and is not cancelled** (ADR-0017: `turn.hold`, `turn.answer`, `Unanswered`). A receiver that ends, fails, or lets a request go is answered for by the engine. An asker that gives up passes over the answer when it comes. **An ask keeps a context its answer comes back with** (ADR-0017: `Answer<A, C>`).
- **A capability is a root asked at a typed path** (ADR-0022: `ChildOf`, `path::<L>`, `Carries`), and **a root that needs nothing of its host is bootstrapped for every host** (ADR-0029: `impl<H: Host> Bootstrap<H>`).
- **No actor ends another** (ADR-0009). It is sent `Shut`, and closes itself.
- **A handler states who may send it its kind** (ADR-0058: `type From`, `Child<T>`, `Speaks<P>`), checked where the mail is delivered.
- **A kind's id is its name and its layout** (ADR-0006), so a generic kind is as many kinds as its layouts.

Input on a listening socket is untrusted. Its size, its shape, and how slowly it arrives all have to be bounded before anything reaches the program.

## Decision

**A stack is a program's own actor, one for each port. It asks `Tcp` to listen on its port itself, stands an exchange beneath itself for each connection, and passes each request through its stages in order, then a router, whose route ends in a handler; and the response back through its stages in reverse. `aethereal-http` holds the pieces a stack is built from, and the client: the exchange, the stages, and the router. It parses and writes HTTP/1.1 itself, with no third-party parser.**

```
LocalStack                       a program's own actor; asks Tcp to Listen on 127.0.0.1:8890 as it begins
 └─ Exchange<LocalStack>:n       reads one accepted connection; asks its stack each request; writes each response
ContainerStack                   another, on 172.17.0.1:8893
 └─ Exchange<ContainerStack>:n
Http                             root, singleton, asked at path::<Http>(()): the client side
 └─ Client:n                     one connection Tcp dialed for it; writes each request it is asked; reads each response
```

```rust
impl<S: Stack> ChildOf for Exchange<S>  { type Parent = S; }  // keyed by the stack's count
impl ChildOf for Http                    { type Parent = Top; }
impl ChildOf for Client                  { type Parent = Http; } // keyed by the root's count
```

- **A stack owns its port and everything on it.** Several actors never share a port, so no one has to own a port for the others, and no table of ports or routes sits in a central actor. Two handlers on one port are two routes of the one stack's router. A program names its stacks' types, and each is listed as any root is (ADR-0029), or spawned as any actor is.
- **The `Http` root keeps only the client.** It no longer serves: a stack binds through `Tcp` itself, so the root's `Serve`, `Served`, and its `Server` child go. A request that would be streamed to a handler of its own, under a prefix (`Mount`), is a route whose handler reads the body: the router and the body handle say what a mount said.
- **The crate builds for every host.** An exchange holds no socket: every byte goes through `Tcp`.

### A stack is an actor of the program's

```rust
/// What an actor that serves one port is: the parent of its exchanges, which asks it each request.
pub trait Stack: Actor + Handles<Incoming> {}

/// What a stack holds: its listener, its exchanges, its stages and router, and the requests parked in it. Each of the
/// stack's handlers of HTTP's kinds is one call into it.
pub struct Serving<S: Stack> { /* .. */ }

/// A stack's settings: where it listens, and what every exchange of it holds to.
pub struct StackSettings {
    pub port: u16,                     // 0: any free port
    pub interface: Interface,          // ADR-0033: Settings, Loopback, or At(address)
    pub most_exchanges: u32,           // past it, an accepted connection is shut at once
    pub most_head_bytes: u32,          // 16 KiB
    pub chunk_bytes: u32,              // the `Chunks` framing's `most_bytes`
    pub window: u32,                   // the parts an exchange's read stream is granted
    pub head_within_millis: u32,       // a head, from its first byte
    pub stall_within_millis: u32,      // 60 s: the longest a body, read or written, may go without moving
    pub idle_within_millis: u32,
    pub answer_within_millis: u32,     // an actor stage's answer, and the handler's once the body is read
}
```

The hub's local stack, in `link_hub`:

```rust
pub struct LocalStack { serving: Serving<Self> }

impl Actor for LocalStack {
    type Config = StackSettings;       // its section, `local_stack`: 8890, `Interface::Loopback`
    type Handles = (Incoming, Part<Accepting>, Answer<Listening, Bind>, Answer<Response, Parked>, Shut, Ended);

    fn begin(settings: StackSettings, turn: &mut Beginning<'_, Self, Self::BeginSends>) -> Result<Self, Fault> {
        let mcp: ProtocolRef<Handling<Caller, ()>> = /* the root `Mcp`, found by its typed path */;
        let routes = Router::new().route(Method::Post, "/mcp", ActorStage::new(mcp))?;
        let stages = Stages::new().stage(AsOwner).inbound().routes(routes);

        Ok(Self { serving: Serving::listen(turn, &settings, stages)? })
    }
}

impl Stack for LocalStack {}

impl Handles<Incoming> for LocalStack {
    type Sends = Steps<Self>;
    type From = Child<Exchange<Self>>;  // only an exchange of its own (ADR-0058)

    fn handle(&mut self, incoming: Incoming, turn: &mut Turn<'_, Self, Self::Sends, Self::From>) -> Result<(), Fault> {
        self.serving.incoming(incoming, turn)
    }
}
```

- **The stack listens as it begins.** `Serving::listen` asks `Tcp` to `Listen` on the settings' port and interface with `Framing::Chunks`, and opens the listener's `Accepting` stream once `Tcp` answers `Bound`. What it answers otherwise is handed to the stack, which decides: the hub's local stack quits, failing the boot (ADR-0020), and its container stack logs it and serves nothing, so the local port is served without the containers'.
- **For each connection accepted, the stack spawns an `Exchange<S>` beneath itself,** keyed by its count, its config the `ActorRef<Accepted>` and the settings' limits, and watches it. Past `most_exchanges`, the connection is shut at once.
- **Every handler of HTTP's kinds is one line into `Serving`:** `Incoming`, the accept stream's parts, `Tcp`'s answer, each actor stage's answer on the way in and on the way out, `Shut`, and an exchange's ending; and, for a stack with a body stage, the kinds of the bodies it serves and reads. The orphan rule keeps `aethereal-http` from writing them for every stack type, so the stack writes them.
- **A stack checks the engine's limits as it is bootstrapped,** as `Http` did: a head of `most_head_bytes`, as mail, within the engine's `read_limit`, and a chunk within its blobs (ADR-0042).

### Each request passes through the stack's stages

```
Exchange ─ask Incoming─▶ Stack: stage 1 ─▶ stage 2 ─▶ … ─▶ router ─▶ handler ─┐   (the way in: each Inbound stage)
Exchange ◀─answer Response── Stack: stage 1 ◀─ stage 2 ◀─ … ◀──── Response ───┘   (the way out: each Outbound stage)
```

```rust
pub struct Incoming {                                  // what an exchange asks its stack: one request's head
    pub method: Method,
    pub path: String,                                  // the target's path, as sent
    pub query: String,                                 // after the `?`, empty when there is none
    pub headers: Vec<Header>,                          // in the order sent, duplicates kept, but `Authorization`
    pub credentials: Credentials,                      // read from the one `Authorization` header
    pub body: BodyHandle,                              // the exchange, which serves the body
    pub peer: SocketAddress,
}
```

- **The exchange parses a head, and asks its stack `Incoming`, answered with a `Response`.** The stack runs its stages and router over it and answers with the response, which the exchange writes. The request crosses no actor but its stack on the way to its handler, and whatever actor stages the stack names.
- **A stage is a set of halves it opts into:** `Inbound`, handed the request's head on the way in; `Outbound`, handed the response's head on the way out; `InboundBody`, the request's body as it passes; and `OutboundBody`, the response's. A stage is asked only for the halves it implements, so one with nothing to do on the way out implements no `Outbound`, and is not asked there at all. Both ways are the same kind of step: a pure stage runs a half in the stack's turn, and an actor stage asks another actor for it.
- **On the way in a stage passes or answers.** An `Inbound` stage is handed the request's head and what the stages before it attached, and passes it on, attaching something of its own when it has something to say, such as who sent it; or answers it, with a `401`, a `429`, or any response. A request answered by a stage goes no further in: its response turns back at that stage, through the stages before it.
- **On the way out a stage passes or answers too.** Each `Outbound` stage the request passed is handed the response's head, in reverse order, and passes it on, changed as it says, a header added, a status rewritten; or answers in its place, with a response of its own, which goes on out through the stages before it. The stack goes on out only once the stage has stepped: at once for a pure stage, and when its actor answers for an actor stage. The stage that answered a request on the way in is not handed its own response.
- **The stages and routes are fixed when the program is built:** a value built in code, as the stack begins. Nothing adds a stage or a route while the program runs.

```rust
let stages = Stages::new()
    .stage(ActorStage::new(sessions)).inbound()                    // asks `Sessions` who sent each request
    .stage(Gzip::new(most_inflated_bytes)).inbound_body().outbound_body()  // a stage of both body halves
    .routes(routes);
```

- **A stage's halves are named as it is added, and each is checked by its trait.** `stage` adds a stage, and `inbound()`, `outbound()`, `inbound_body()`, and `outbound_body()` each build only when the stage implements that half, an actor stage's head halves when its protocol does; a stage named with no half does not build. So which halves the stack runs is fixed by type when the program is built, and nothing is decided for each request.
- **The stages are typed as they are built.** `Stages::new()` attaches `()`, and `inbound()` takes a stage whose `In` is what the stages attach so far and gives stages that attach its `Out`; so a stage that reads a principal stands after the stage that attaches one, or the stack does not build. The other halves leave what is attached as it is. The router takes routes whose handlers read what all the stages attach.

### A pure stage runs in the stack's turn

```rust
/// The way in: handed the request's head and what the stages before it attached.
pub trait Inbound {
    type In: Plain;                                    // what the stages before it attached
    type Out: Plain;                                   // what it passes on attached

    fn inbound(&mut self, head: &Incoming, attached: Self::In) -> Step<Self::Out>;
}

/// The way out: handed the response's head, which it changes in place.
pub trait Outbound {
    fn outbound(&mut self, head: &Incoming, response: &mut ResponseHead) -> Step<()>;
}

pub enum Step<Out> {
    Pass(Out),                                         // on: in, with `Out` attached; out, with the head as it now is
    Answer(Response),                                  // answered here: in, turned back; out, in place of the response
}

/// The local stack's one stage: its port is on the loopback, so every request on it is the owner's.
pub struct AsOwner;

impl Inbound for AsOwner {
    type In = ();
    type Out = Caller;

    fn inbound(&mut self, _: &Incoming, (): ()) -> Step<Caller> { Step::Pass(Caller::Owner) }
}
```

- **A pure stage is a function over the heads,** run inline, in the turn the stack handles the request in, with no hop. Its state is its own value in the stack, so it is per stack: a rate limit of one port counts that port's requests. `AsOwner` has nothing to do with a response, so it is `Inbound` alone, and the local stack hands it nothing on the way out.
- **Read-only data is copied into each stack's pure stages.** Only state shared beyond one stack needs an actor.

### An actor stage asks another actor

```rust
/// A stage that asks the actor `to` names, through its protocol `P`, and goes on once it answers.
pub struct ActorStage<P> { to: ProtocolRef<P> }

/// The way in, asked: what the stack asks, made from the request's head, and what the answer comes to.
pub trait AskedInbound: Protocol {
    type In: Plain;
    type Out: Plain;
    type Ask: Kind;
    type Answer: Kind;

    fn ask(head: &Incoming, attached: Self::In) -> Self::Ask;
    fn step(answer: Self::Answer) -> Step<Self::Out>;
}

/// The way out, asked: what the stack asks, made from the request's head and the response's, and what the answer
/// comes to, a head changed in place or a response in place of this one.
pub trait AskedOutbound: Protocol {
    type Ask: Kind;
    type Answer: Kind;

    fn ask(head: &Incoming, response: &ResponseHead) -> Self::Ask;
    fn step(answer: Self::Answer, response: &mut ResponseHead) -> Step<()>;
}

pub struct Parked { /* the request, what it has attached, which stage it stands at, and the exchange's ask */ }
pub struct ParkedResponse { /* the response, the request's head, which stage it stands at, and the exchange's ask */ }
```

- **An actor stage is asked in when its protocol is `AskedInbound`, and out when it is `AskedOutbound`.** Its `inbound()` builds only for the one and its `outbound()` only for the other, so an actor stage is asked each way only where its protocol answers that way. The two halves are the two ways of `Inbound` and `Outbound` for a stage whose step is an answer that comes later.
- **The stack asks, and parks the request as the ask's context.** On the way in it asks the actor `ActorStage` names, keeping the request, what it has attached, the stage it stands at, and the exchange's ask it holds, as the context its answer comes back with (`Answer<A, Parked>`). Then it goes on with other requests: one stage that waits holds up no other connection. When the answer comes, the stack goes on in from that stage.
- **On the way out it parks the response the same way.** It asks with what `AskedOutbound::ask` makes of the request's head and the response's, keeping the response, the request's head, the stage it stands at, and the exchange's ask as the context (`Answer<A, ParkedResponse>`), and goes on with other requests. When the answer comes, `step` changes the head in place or answers a response in its place, and the stack goes on out from that stage. `ParkedResponse` is a context of its own beside `Parked`, as an actor takes each answer kind with one kind of context (ADR-0017), and what is parked differs: a request on the way in, a response on the way out.
- **An actor stage is for state shared beyond one stack:** who the bearers are, a limit across ports. The stack holds only a `ProtocolRef<P>`, so it does not care which actor answers, or of what type.
- **An actor stage is asked within `answer_within_millis`, each way.** On the way in, an answer `Expired` is `504`; an actor that has ended is `503`; one whose turn failed or that let the request go is `500`. Each closes the connection after the response, as the body is unread.
- **On the way out the response has not been written yet,** since the exchange writes it only once its stack answers, so the same three still become `504`, `503`, and `500`: each takes the response's place, and goes on out through the stages before that one as a response a stage answered does. The connection closes after it when the request's body is unread, as after any response.
- **No body is being written while a stage is asked on the way out.** A streamed response's source is opened only once the exchange has written its head (below), so a response replaced on the way out, by a stage's answer or by one of the three, has a source no one has opened. The stack opens its stream and stops it in the same turn, as the exchange does for a response to `HEAD`, so the source is told at once it will not be read.
- **The exchange's wait still bounds the whole way back.** Once a request's body is read the exchange waits `answer_within_millis` for its stack's answer (below), and the asks on the way out fall inside that wait: a handler that answers late and a slow stage on the way out together can run past it, when the exchange writes `504` and passes over the stack's answer.

### A stage sees heads, unless it reads the body

```rust
pub struct BodyHandle {
    pub length: BodyLength,                            // Known(n) by its Content-Length, 0 for none; or Chunked
    pub reader: ProtocolRef<Streamed<RequestBody>>,    // the exchange, or the stack when a stage reads the body
    pub gatherer: ProtocolRef<Gathering>,              // the same actor, asked for the body whole
    request: u64,                                      // which of the reader's bodies it is
}

impl BodyHandle {
    pub fn read(&self) -> ReadBody;                    // the body as a stream: a body of any size
    pub fn whole(&self, most_bytes: u32) -> Gather;    // the body in one answer, refused past `most_bytes`
}

/// A stage that reads the request's body as it passes, and writes the body the handler reads.
pub trait InboundBody: Clone {
    fn part(&mut self, part: &[u8], out: &mut Vec<u8>) -> Result<(), Refused>;
    fn end(&mut self, out: &mut Vec<u8>) -> Result<(), Refused>;
}

/// The same over the response's body, as it goes out.
pub trait OutboundBody: Clone {
    fn part(&mut self, part: &[u8], out: &mut Vec<u8>) -> Result<(), Refused>;
    fn end(&mut self, out: &mut Vec<u8>) -> Result<(), Refused>;
}

pub enum Refused { TooLarge, Malformed }               // why a body stage stops a body
```

- **By default a stage sees heads only, and the body handle passes through it untouched.** No stage costs a part of the body anything, and a request refused by a stage is refused before a byte of its body is read: the exchange grants its connection nothing while the stages run, so what the client sends waits in the kernel and TCP slows it, and a push of gigabytes refused `401` costs what one read window holds. No `100 Continue` is sent before the body is opened.
- **A stack reads a body only when one of its stages is a body stage, which its type says.** A stage that decompresses a gzip body, checks its size against a cap, or checks a signature over it implements `InboundBody`; one that compresses a response implements `OutboundBody`. A stack none of whose stages is added with `inbound_body()` hands its handler the exchange's handle as it came, and the parts go from the exchange to the handler with nothing between them; the same holds of `outbound_body()` and the response's body.
- **A stack with an inbound body stage serves the body itself.** The handle it passes to the handler names the stack as the reader and the gatherer, with the length `Chunked`, as the body's length is no longer known. Only once the handler opens or gathers that body does the stack open the exchange's stream, so a stack with a body stage still reads nothing before every stage has passed the request and its handler wants the body. Each part from the exchange is run through each inbound body stage in order, `part` writing what the next one reads, and the last stage's output is sent to the handler as one part. That is one hop for each part, paid only by such a stack; several body stages chain within the stack's turn, with no hop between them. The stack grants the exchange one part for each it can send on, and a part the stages turn into no bytes is granted back at once. Where the exchange's stream ends `Whole`, each stage's `end` runs in order, the last bytes are the last part, and the handler's stream ends `Whole`; a gather is gathered the same way and answered once.
- **A body stage that refuses stops the body.** `Refused::TooLarge` ends the handler's stream `TooLarge`, and `Malformed` ends it `Malformed`, and the stack stops the exchange's stream with `Enough`: the rest is not read, and the connection closes after the response.
- **On the way out a stack with an outbound body stage serves the response's body.** A `Whole` body is run through each outbound body stage in reverse order, `part` then `end`, in the turn the response passes them, and goes on whole with its new length. A `Streamed` body is named on as the stack's own, of `Unknown` length; once the exchange opens it, the stack opens the handler's source and relays each part through the stages in reverse order, granting the source one part for each the exchange grants the stack, and passing on `Enough`. A refusal there comes after the head is written, so it is a failure after the head: the stack stops the source and ends its own stream `Failed`, and the exchange closes with the body cut short.
- **A body stage is cloned for each body.** Its `part` and `end` keep what one body needs across its parts, as a decompressor keeps its window, so the stack clones the stage as it was built for each body it reads, and drops the clone once that body ends. A stage's head halves run on the one value the stack keeps.
- **Only one reader holds a body.** The handle passed on is the only one the stages after see, so the body is read once, by the last that took it.
- **Allocations: nothing is a blob until the last step.** This is the hot path, and its buffers are pooled or reused:
  - the part a body stage reads is the exchange's blob, or the source's, read in place as `&[u8]` (`turn.read`), and never copied out first;
  - between two body stages, what one writes and the next reads is a buffer the stack takes with `turn.buffer(room)` as it takes the last one, and hands back to its pool with `turn.give_back(buffer)` once the part has run through every stage (ADR-0042: a buffer taken and not put returns to the actor's pool under the same rule and budget as one freed); it is never put, and never a blob;
  - only the last stage's output crosses to another actor, so only it is a blob: the stack takes its buffer with `turn.buffer(room)` (ADR-0042, `crates/aethereal-actor/src/turn/mod.rs:2117`), with room for one chunk (`chunk_bytes`), the stage writes into it, and the stack puts it as the part's `Bytes`; once the reader frees the part, its buffer comes back to the stack's pool for the next one;
  - a stack with no body stage makes no blob at all: the exchange's part passes on as it is.

  So once the stack's pool holds buffers of the parts' size, a part costs no allocation, and a body costs one clone of each body stage. Stages never allocate for a part: they write into the buffers they are handed.

### A router picks the handler

```rust
pub struct Router<A> { /* a trie of method and path patterns */ }

impl<A: Plain> Router<A> {
    pub fn route<C: Captures>(self, method: Method, pattern: &str, handler: ActorStage<Handling<A, C>>) -> Result<Self, Unroutable>;
}

pub enum Unroutable {
    Overlaps { pattern: String, other: String },       // a path both match, for one method
    Malformed { pattern: String },                     // not `/` and then segments, a capture not a whole segment
    Uncaptured { pattern: String },                    // its `{names}` are not the names `C` reads
}

/// A route's captures, typed: read from the slices of the path its `{names}` matched.
pub trait Captures: Plain {
    const NAMES: &'static [&'static str];
    fn read(slices: &[&str]) -> Option<Self>;
}
```

```
GET  /git/{repo}/info/refs          ─▶ ActorStage<Handling<Caller, Repo>>   (git, later)
POST /git/{repo}/git-receive-pack   ─▶ ActorStage<Handling<Caller, Repo>>
POST /mcp                           ─▶ ActorStage<Handling<Caller, ()>>
```

- **After the stages, the router matches the method and the path.** A pattern is literal segments and `{name}` captures, each a whole segment, matched against the path as sent, with no normalising. The routes are compiled to a trie as the stack begins, so a request is one walk down it, allocating nothing; its captures are slices of the head, read into the route's captures type, `C`.
- **Routes never overlap.** A route whose pattern matches a path another's does, for the same method, is refused `Overlaps` as the router is built, so the stack fails its `begin` and the program does not start. Each request goes to one route at most, and the order routes were given never decides which.
- **A path that matches with another method is `405`,** with `Allow` naming the methods its routes take. A path no route matches is `404`. A capture that does not read as its type is `404`, as no route matches it. Each is the router's answer, which turns back through every stage.

### A handler is the last stage

```rust
pub struct Handling<A, C>(PhantomData<fn() -> (A, C)>);
impl<A: Plain, C: Captures> Protocol for Handling<A, C> { type Kinds = (Request<A, C>,); }
impl<A: Plain, C: Captures> Carries<Request<A, C>> for Handling<A, C> { type Answers = (Response,); }

pub struct Request<A, C> {
    pub method: Method,
    pub path: String,
    pub query: String,
    pub headers: Vec<Header>,                          // never `Authorization`
    pub attached: A,                                   // what the stages attached: the hub's `Caller`
    pub captures: C,
    pub body: BodyHandle,
    pub peer: SocketAddress,
}
pub struct Response {
    pub status: Status,                                // a closed enum of the final statuses HTTP names: Ok, NotFound, ..
    pub headers: Vec<Header>,
    pub body: ResponseBody,                            // Whole(Bytes), or Streamed from a source
}
pub struct Header { pub name: String, pub value: String }   // names lowercased by the parser
pub enum Method { Get, Head, Post, Put, Delete, Patch, Options }
```

- **A handler is an actor stage at the end of a route, `ActorStage<Handling<A, C>>`, and it always answers.** It is asked `Request<A, C>`, typed by what the stages attach and by its route's captures, and answers a `Response`. There is one concept, the stage: a handler is the stage that answers every request it is handed, and the one that reads the body.
- **The response starts at the handler, which is not asked again on the way out.** `Handling<A, C>` is neither `AskedInbound` nor `AskedOutbound`: the router asks it, and the way out begins with its answer, at the last stage before it.
- **A handler takes its request only from a stack.** It states `type From = FromStack;`, `aethereal-http`'s name for `Speaks<(Incoming,)>`: an actor whose type takes `Incoming`, which is what a stack is (ADR-0058). So no other actor can hand it a request with a principal attached. Its program's stack types are the program's, and a handler's crate cannot name them; `Speaks` names what they take.
- **The handler answers in the turn it is asked (`turn.reply`), or holds the request and answers in a later one** (`turn.hold`, `turn.answer`), as `Mcp` does once a tool has answered.
- **A request the handler does not answer is answered for it.** When the handler has ended the response is `503`. When its turn failed, it let the request go, or it never answered, `500`.
- **What a route alone needs is its handler's.** A limit on a body, a check on a path a capture names, a sender a route refuses: each is its handler's, which knows its route. A stack's stages are the same for every route on its port.
- **One stack per port.** Routes that need different stages belong on different ports, each its own stack.

### Authentication is an actor stage

```rust
pub trait Scheme: 'static { type Principal: Plain + 'static; }   // who a request may come from

pub struct Authenticating<S>(PhantomData<fn() -> S>);
impl<S: Scheme> Protocol for Authenticating<S> { type Kinds = (Authenticate,); }
impl<S: Scheme> Carries<Authenticate> for Authenticating<S> { type Answers = (Authentication<S>,); }

pub struct Authenticate {                              // the head's part an authenticator reads; never the body
    pub method: Method,
    pub path: String,
    pub credentials: Credentials,
    pub peer: SocketAddress,
}
pub enum Credentials {                                 // read from the one `Authorization` header
    None,
    Bearer { token: String },                          // RFC 6750
    Basic { user: String, password: String },          // RFC 7617
    Other { scheme: String, parameters: String },
}
pub enum Authentication<S: Scheme> {
    Allowed(S::Principal),                             // passes, the principal attached
    Challenged { scheme: String, realm: String },      // 401, with `WWW-Authenticate`
    Forbidden,                                         // 403
}

impl<S: Scheme> AskedInbound for Authenticating<S> {
    type In = ();
    type Out = S::Principal;
    type Ask = Authenticate;
    type Answer = Authentication<S>;
    // ..
}
```

- **An authenticator is any actor that takes `Authenticating<S>`.** The stack holds an `ActorStage<Authenticating<S>>`, a `ProtocolRef`, and does not care who answers it: the hub's container stack asks `Sessions` itself, which mints the bearers (ADR-0057). A registry actor that `Sessions` told of each bearer would do as well, since the stage holds only a protocol reference.
- **A scheme names who may send.** Its `Principal` is what an allowed request goes on with: the hub's `Caller` for its sessions and its owner (ADR-0057). It is plain data (ADR-0004), and names a sender; it carries no reference or blob.
- **An authenticator is asked on the way in only.** `Authenticating<S>` is not `AskedOutbound`: who sent a request is settled before its response is made, so a stack adds its stage with `inbound()` alone, and a response passes it with no hop.
- **An authenticator takes its ask only from a stack,** `type From = FromStack;`, so no other actor can try credentials one by one.
- **A principal fixed by where the port is, is a pure stage.** The local stack is on the loopback, so `AsOwner` attaches `Caller::Owner` to every request and asks no one.
- **The exchange parses the credentials,** from the one `Authorization` header (RFC 7235), its scheme named in any case: `Bearer` and its token; `Basic` and its user and password, decoded from Base64 and split at the first `:`; any other scheme as `Other`, lowercased, with the rest as sent; and no header, `None`. An `Authorization` header sent more than once, or `Basic` credentials that do not decode, is `400`. A credential is a secret: the `Debug` of `Credentials` names its scheme and no more.
- **The credentials go to the stages, and never to a handler.** They are a field of `Incoming` beside its headers, and `Request` has no field for them, so no handler holds a bearer or a password.
- **`Challenged` is written `401` with `WWW-Authenticate: <scheme> realm="<realm>"`,** so a client that holds credentials sends them again: git's credential helper answers a `401` with `Basic`. `Forbidden` is `403`. A scheme that is not a token, or a realm holding `"`, `\`, or a control byte, is the authenticator's fault, and is `500`.
- **Authentication is asked for every request.** A connection kept alive is not a session: each request bears its own credentials, and nothing an authenticator answered is kept for the next.
- **What a sender may do is the handler's to decide.** Authentication says who sent a request, and nothing more: `Mcp` refuses a session's call of a session tool (ADR-0057) by the principal it is handed.

### A handler reads the body through its handle

```rust
pub struct RequestBody;                                // one request's body, streamed as it arrives
impl Stream for RequestBody { type Open = ReadBody; type Part = BodyBytes; type Done = BodyRead; }
pub struct BodyBytes { pub bytes: Bytes }              // what one read brought, decoded
pub enum BodyRead { Whole, TooLarge, Malformed, Stalled, HungUp(HungUp), Busy, Cut }

pub struct Gathering;                                  // one request's body, asked for whole
impl Protocol for Gathering { type Kinds = (Gather,); }
impl Carries<Gather> for Gathering { type Answers = (Gathered,); }
pub struct Gather { pub most_bytes: u32, request: u64 }
pub enum Gathered { Whole(Bytes), TooLarge, Malformed, Stalled, HungUp(HungUp), Busy }
```

- **A small body is read whole, with one ask.** `body.whole(most_bytes)` asks the handle's `gatherer` `Gather`, and the reader gathers the body into one buffer and answers once: `Whole(bytes)` once the body ends; `TooLarge` when it runs past `most_bytes`, by the head's `Known` length before a byte is read or once a chunked body runs past, refused and never cut short, so the handler is handed none of it; or why it could not finish, as a stream would end: `Malformed`, `Stalled`, `HungUp(how)`, or `Busy`. The buffer is taken with `turn.buffer` (ADR-0042), with room for the known length, or for a chunk and grown as the body comes, and is put once, as the answer's blob. After `TooLarge` the rest is not read, and the connection closes after the response. The gather is paced by the reader as its stream is, and holds the body and one read window.
- **A body of any size is a stream its reader opens.** The handler opens a `RequestBody` stream on the handle's `reader`, with `read()`, and the exchange serves it with `Serving`, as a client serves `Receiving` (ADR-0017). This is how a body too large to hold is read, such as a git push. A request with no body has a handle of length `Known(0)`, whose stream ends `Whole` once opened, and whose gather answers `Whole` with no bytes. The open and the gather name the request they read; one of a body that another stream or gather reads, that has been read, or that is not the request out is answered `Busy` at once, so a stale stream never reads the next request's body.
- **The gather is asked through a protocol of its own.** `Streams::open` opens on a `ProtocolRef<Streamed<S>>` (`crates/aethereal-actor/src/stream/streams.rs:77`), so the reader's one reference cannot carry `Gather` too; the handle holds a second, to the same actor.
- **`Expect: 100-continue` is answered `100 Continue` as the body's stream is opened, or its gather asked,** when the request has a body: by then every stage has passed it and its handler wants it. A handler that answers without opening the body sends none.
- **A limit on a body is its reader's.** A handler that will take no more than so many bytes gathers it with that as `most_bytes`, or, reading a stream, answers `413` from the head's `length` before it opens the stream, or stops reading and answers `413` once a chunked body runs past it; the stream then ends `Cut`.
- **The reader's credit paces the connection.** The exchange takes each chunk without granting for it (`part_held`), decodes what its buffer holds while the stream has credit (`Serving::has_credit`), sends it as one `BodyBytes`, and grants the connection what it withheld only once more bytes are all the body needs. A reader that falls behind stops the exchange reading, and TCP slows the client.
- **The stream is ended once, with `BodyRead`:** `Whole` where the framing ends; `Malformed` for chunked framing that breaks, with `400` (`413` for a chunk's line past `most_head_bytes`); `Stalled` when the body has not moved for `stall_within_millis`, and the exchange closes with no answer; `HungUp(how)` when the connection hangs up or the exchange is shut; `Busy` as above; and `Cut` when the handler answers before the body has ended, when the rest is not read and the connection closes once the response is sent. A handler that stops the stream with `Enough`, or ends, leaves the body unread too: the exchange waits for the answer and closes once it is written. `TooLarge` ends the stream a stack serves when a body stage refuses a body as too large.
- **The handler is asked within `Due::Never`.** A body may take as long as it keeps moving, so the ask cannot carry `answer_within_millis` from its head, and a stream the handler opens, or a gather it asks, in the turn it is asked inherits the same `Never` (ADR-0041), so nothing cuts a long body off. The stall limit bounds the body instead: the exchange sleeps until `stall_within_millis` after it last moved, and when the sleep comes and it has moved since, sleeps again until it would be late. Once the body is read, or will not be, the exchange is in `Awaiting`, and sleeps until `answer_within_millis` after it; then it writes `504` and closes, and the answer, when it comes, is passed over. What the handler asks on the request's behalf states its own deadlines.
- **Pipelining holds.** The body's decoder stops where its framing ends, so the bytes after it stay in the buffer for the next request, which is parsed once the stack has answered and the credit withheld is granted.

### A response's body may be streamed from a source

```rust
pub enum ResponseBody { Whole(Bytes), Streamed(StreamedBody) }
pub struct StreamedBody {
    pub source: ProtocolRef<Streamed<ResponseSource>>, // the actor that makes the body
    pub body: u64,                                     // the handler's number for it, which the stream opens with
    pub length: ResponseLength,                        // Known(n), or Unknown
}

pub struct ResponseSource;                             // one response's body, streamed as it is made
impl Stream for ResponseSource { type Open = SendBody; type Part = ResponseBytes; type Done = SourceEnd; }
pub struct SendBody { pub body: u64 }
pub struct ResponseBytes { pub bytes: Bytes }
pub enum SourceEnd { Whole, Failed, Stopped }
```

- **A handler may stream its response:** it answers with `ResponseBody::Streamed`, naming a source, which may be itself or an actor it started for the request, such as a pipe to a child process. The response passes back through the stages, its body named and unread, and the exchange writes the head, opens a `ResponseSource` stream on the source with `SendBody`, and enters `Outflow`. `body` lets one source tell the bodies it is asked for apart. The open is made in the turn that handles the stack's answer, which is no request, so it carries no deadline (ADR-0041).
- **The framing follows what is known.** A `Known(n)` length is written as `Content-Length: n`, and its parts as they are. An `Unknown` length is written in chunks to an HTTP/1.1 client, each part one chunk, its size line a small blob of its own and its data the part itself, passed on without being copied; the body ends with the last chunk once the source ends it `Whole`. An HTTP/1.0 client reads no chunks, so its body has no length header and ends with the connection's close. A part of no bytes is granted back and writes nothing, since an empty chunk would end the body.
- **What the connection has sent paces the source.** The exchange takes each part without granting for it (`part_held`), queues it, and keeps one write out at a time, of everything queued, each part pinned until its write is answered `Sent`; then it grants the source as many parts as the write carried. So the source runs at most `window` parts ahead of what the kernel has taken, a client that reads slowly fills the kernel's buffers and stops the writes, and nothing of the body is held but the window. A write answered `Full` was taken whole or not at all, so it is written again, its first part alone; with nothing else of the response unsent, a part the connection still will not take never fits, and the connection closes. A part is best kept well under TCP's `most_unsent_bytes`.
- **Failure after the head closes the connection.** The status is written before the body, so a body that breaks cannot be answered otherwise: when the source ends `Failed`, ends without answering, or sends more or fewer bytes than its `Known` length, its stream is stopped and the exchange closes without ending the body. A chunked body then lacks its last chunk and a sized one its last bytes, so the client sees it cut short, and a close-delimited body, to HTTP/1.0, cannot be told from a whole one.
- **The client's hang-up stops the source.** When the connection hangs up, a write is answered `HungUp`, or the exchange is shut, the exchange sends the source `Enough` before it closes, and the source ends the stream `Stopped` and stops making the body.
- **A long body is not timed as a whole.** `Outflow` is timed by `stall_within_millis`: the exchange sleeps until that long after the body last moved, a part taken or a write sent, and once the sleep comes and it has not moved since, the source is stopped and the connection closes.
- **A response with no body enters no `Outflow`.** A response to `HEAD`, or of a status with no body, is written as its head alone, with its `Content-Length` when its length is known. Its stream is opened and stopped in the same turn, so a source that waits for its open, or holds a child process for it, is told at once it will not be read.
- **Pipelining holds.** A request is out until its response is written, so while `Outflow` lasts the exchange grants its connection nothing, and the request after is parsed once the last chunk is written, never interleaved with the body.
- **The exchange writes the framing headers itself.** It writes the status line, the response's headers, `Content-Length` from the body, or `Transfer-Encoding: chunked` for a streamed body of no known length, and `Connection: close` when it will close. A `Content-Length`, `Transfer-Encoding`, or `Connection` among the response's headers is dropped and recorded in the log. A response to `HEAD` has its body dropped and keeps its `Content-Length`.

### An exchange parses as chunks arrive, one request at a time

```
Accepted ─Frame─▶ Exchange<S>: Idle ─▶ Head ─▶ Inflow ──ask Incoming──▶ S: stages ─▶ router ─▶ handler
                                                  │ ◀────────── open RequestBody ────────────────┘
                                                  │ BodyBytes, as credit allows ─────────────────▶
                                                  └▶ Awaiting ◀── answer Response ── S ◀── Response
Accepted ◀─Write─ Exchange<S> ◀──────────────────────┘

a streamed response:   answer Response { Streamed } ─▶ Outflow ──open ResponseSource──▶ source
                                 │ ◀──────────── ResponseBytes, as credit allows ──
                                 └ Write each part ─▶ Accepted ── Sent ─▶ More to the source
```

- **The exchange keeps what it has decoded, not the raw bytes.** In `Head` it buffers until the blank line that ends the head, then parses it in one pass, and asks its stack. In `Inflow` it decodes the body as its head frames it, as its reader's credit allows: exactly `Content-Length` bytes, or chunks up to the empty line that ends the last chunk's trailer, decoded wherever the reads cut them. The decoder is the one the client reads a response's body with, in the crate's `body` module. Bytes past the end of the request stay in its buffer for the next one.
- **While a request is out, the exchange grants no credit,** but what its body's reader needs to go on. It takes the `Frame`s still in flight without granting more, and grants what it held back once its response is written. So a client that sends requests back to back, pipelining, waits in the kernel, and TCP slows it down. What the exchange holds meanwhile is bounded by the `Reading` window times its chunk size. This needs two methods on `Streams` (ADR-0017): `part_held`, which takes a part without granting for it, and `grant`, which grants a stream a number of parts.
- **Connections are kept alive,** HTTP/1.1's default. The exchange closes after its response is written (`Wrote::Sent`) when the request said `Connection: close` or was HTTP/1.0, or when its body ends with the close. It also closes when the write is answered `Full` or `HungUp`, or the read stream ends.
- **A request answered with its body unread is answered, then the connection closes,** since where its body ends cannot be known without reading it; but for a request with no body, after which the connection is kept.

### Limits on untrusted input

| The request | The answer |
|---|---|
| a head past `most_head_bytes` | `431`, then close |
| a head not whole within `head_within_millis` of its first byte | close, no answer |
| a request line or header that does not parse; a bare LF; a folded header; a header that is not visible ASCII | `400`, then close |
| an `Authorization` header sent more than once, or `Basic` credentials that do not decode | `400`, then close |
| `Content-Length` sent more than once, or not a number | `400`, then close |
| a `Transfer-Encoding` beside a `Content-Length`, or in an HTTP/1.0 request | `400`, then close |
| a transfer coding other than `chunked` alone (`gzip`, `gzip, chunked`, two `chunked`) | `501`, then close |
| a method not in `Method` | `501`, then close |
| an HTTP version other than 1.0 and 1.1 | `505`, then close |
| a target not in origin form (`/path?query`) | `400`, then close |
| a stage that answers | its response; then close when the request has a body, which is not read |
| an actor stage that has ended; one whose turn failed or that let the request go; one past `answer_within_millis`, on the way in | `503`, `500`, or `504`, then close |
| the same, on the way out | `503`, `500`, or `504` in place of the response; then close when the body is unread |
| a body a body stage refuses on the way in | its handler's stream ends `TooLarge` or `Malformed`; close after the response |
| a body a body stage refuses on the way out | close, the body cut short; its source is stopped |
| a path no route matches, or a capture that does not read | `404`; then close when it has a body |
| a path a route matches with another method | `405` with `Allow`; then close when it has a body |
| a chunk's size line, its data's line ending, or a trailer field that does not parse | `400`, then close; its stream ends `Malformed` |
| a chunk's size line or trailer field past `most_head_bytes` | `413`, then close; its stream ends `Malformed` |
| a body that has not moved for `stall_within_millis`: no bytes came, or its reader opened no stream or granted no credit | close, no answer; its stream ends `Stalled` |
| a body read, and no answer within `answer_within_millis` after | `504`, then close; the answer, when it comes, is passed over |
| no request within `idle_within_millis` of the last response | close, no answer |
| a streamed response that has not moved for `stall_within_millis`: the source sent nothing, or the client read nothing | close, the body cut short; its source is stopped |

- **A request's body is framed one way, or refused.** Request smuggling comes from a body that two readers frame differently, so a `Transfer-Encoding` beside a `Content-Length`, or in HTTP/1.0, which has no transfer codings (RFC 9112 §6.1), is `400`, never settled in favour of one. `chunked` alone is decoded; any other coding, which the exchange does not decode, is `501`; an `InboundBody` stage may decode a `Content-Encoding`, which is the body's, not its framing's.
- **Each deadline is a `Sleep`** (ADR-0018). As an exchange enters a phase that has one, it runs a `Sleep` until that phase's deadline, its context naming the phase, and cancels the last one it ran. A sleep answered for a phase the exchange has left is passed over. Nothing in HTTP subscribes to `Tick`, so a program that serves HTTP runs no cycle for it (ADR-0033).
- **A request whose deadline passes is still out.** Requests are not cancelled (ADR-0017), so the stack's answer still comes, and the exchange, closing or closed, passes over it.

### A client asks other servers

```rust
impl Carries<Connect> for Http { type Answers = (Connected,); }
impl Carries<Fetch> for Client { type Answers = (Fetched,); }

pub struct Connect { pub peer: Peer }
pub enum Peer { Tcp { host: String, port: u16 }, Unix { path: SocketPath } }
pub enum Connected { Open { client: ActorRef<Client> }, Unreached(Unreached), Full, Unavailable }

pub struct Outgoing { pub method: Method, pub path: String, pub query: String, pub headers: Vec<Header>, pub body: Bytes }
pub struct Fetch { pub request: Outgoing }                       // answered once the body is whole
pub enum Fetched { Whole(Reply), Failed(Failure) }
pub struct Reply { pub status: u16, pub headers: Vec<Header>, pub body: Bytes }

pub struct Receiving;                                            // one response, streamed as it arrives
impl Stream for Receiving { type Open = Follow; type Part = Received; type Done = Finished; }
pub struct Follow { pub request: Outgoing, pub switch: Switch }  // Switch::{Stay, To { protocol }}
pub enum Received { Head(ReplyHead), Switched { head: ReplyHead, writing: ProtocolRef<Writing> }, Bytes(Bytes) }
pub enum Finished { Whole, Closed(HungUp), Failed(Failure) }
pub enum Failure { Busy, Unwritable(Unwritable), Full, Malformed, TooLarge(Limit), HungUp(HungUp), NoRoom }
```

- **The root dials, and a client stands beneath it.** The root asks `Tcp` to `Connect` or `ConnectUnix` with
  `Framing::Chunks`, holding the `Connect`, and on `Open` spawns a `Client` on the `ActorRef<Dialed>`; otherwise
  `Unreached` carries `Tcp`'s reason. It watches whoever asked and shuts their clients when they end, and holds at
  most `most_clients`. A program without `Tcp` builds, and its `Connect` is answered `Unavailable`.
- **One request at a time, and the connection kept.** A request while one is out is `Busy`. A response whose body
  ended where its framing said leaves the connection for the next request. The client closes when a response said
  `Connection: close`, was HTTP/1.0, or ran until the connection closed; when the connection hangs up; when a response
  breaks a rule or a limit; or when sent `Shut`. A request asked of it after that is answered `Ended` by the engine.
- **The client writes the framing.** `Host` (the host and port dialed, `localhost` for a Unix socket), `Content-Length`
  when there is a body or the method expects one, and `Connection: upgrade` with `Upgrade` for a switch. A request
  that names one of these, has a header that is not a token or holds a control byte, or a target not in origin form, is
  `Unwritable`, and nothing is sent. It sends no `Expect` and pipelines nothing.
- **A response is parsed by the pieces a request is,** shared in one module: where the head ends within its limit, its
  lines, its headers, and its `Content-Length`; a status line takes the place of the request line, with any reason
  phrase (Docker writes `101 UPGRADED`). Informational heads other than `101` are passed over. The body is framed as
  RFC 9112 §6.3 says: none for a `HEAD`, an informational status, `204`, or `304`; `chunked` alone; a
  `Content-Length`; or, with neither, until the connection closes. Any other coding, or a coding beside a
  `Content-Length`, is `Malformed`.
- **Whole or streamed is the asker's choice.** `Fetch` gathers the body, refusing one past `most_reply_body_bytes`, by
  its length before it is read when it has one. `Receiving` sends the head, then what each read brought of the body,
  decoded wherever the reads cut a chunk, its size line, or its line ending; a streamed body has no limit, as it is
  never held whole. A chunk's size line or a trailer's field past `most_reply_head_bytes` is too large.
- **The asker's credit paces the connection.** The client takes each chunk its connection reads without granting for it
  (`part_held`), and grants the credit back only once more bytes are all it needs. While its asker has no credit it
  grants nothing, so the connection stops reading and the socket holds the server back. What the client holds
  meanwhile is bounded by its window of chunks.
- **A switch hands the connection over raw.** A `Follow` that asks to switch, answered `101`, or `2xx` with a body that
  runs until the connection closes (what Docker writes when it takes over an attach asked without `Upgrade`), is sent
  `Switched` with a `ProtocolRef<Writing>` to the `Dialed`, and every later part is the connection's own bytes, those
  that came in the read with the head first. HTTP is no longer read. The client goes on reading and relaying, since a
  connection has one reader and one whose reader ends hangs up (ADR-0033); writes go to the connection directly. The
  stream finishes `Closed(how)` when the connection hangs up. An asker that stops a stream with `Enough`, or ends,
  leaves a connection mid-response, and the client closes.
- **The client times nothing.** An asker that will not wait asks within a deadline (ADR-0041), and the answer that
  comes later is passed over.

### Ending is by mail

| Type | Ends when |
|---|---|
| a stack | it is sent `Shut`, or `Tcp`'s accept stream ends. It sends `Shut` to its listener and to each exchange, and closes |
| `Exchange<S>` | it is sent `Shut`, or it closes the connection as above, or its read stream ends |
| `Client` | it is sent `Shut`: by the root when the asker of `Connect` ends, or by whoever holds it. It also ends when its connection's read stream ends, when a response closes the connection or breaks a rule or a limit, and when the asker of the stream it serves stops it or ends |

When an exchange closes, its read stream's asker is gone, so the TCP connection beneath it shuts itself (ADR-0033). An exchange does not send `Shut` to it. A handler that ends is not watched: a request asked of it after is answered `Ended` by the engine, and is `503`.

### Settings

A stack's settings are its own section, `StackSettings` above, named by its `Bootstrap`: the hub's `local_stack` and `container_stack`. The `Http` root's are the client's:

```rust
#[settings]
pub struct HttpSettings {
    pub most_clients: u32,
    pub chunk_bytes: u32,              // the `Chunks` framing a client's connection reads
    pub window: u32,                   // the parts a client's read stream is granted
    pub most_reply_head_bytes: u32,    // 16 KiB: a response's head, and each line of a chunked body
    pub most_reply_body_bytes: u32,    // 8 MiB: a body read whole; one streamed has none
}
```

The section is `http`.

### A tool call through the hub

```
agent ─POST /mcp─▶ Accepted ─Frame─▶ Exchange<ContainerStack> ─ask Incoming─▶ ContainerStack
  ContainerStack: ActorStage<Authenticating<SessionBearer>> ─ask Authenticate─▶ Sessions: the bearer is session 3's
                    ◀── Allowed(Caller::Session { session: 3 }) ──────────┘
                  router: POST /mcp ─▶ ActorStage<Handling<Caller, ()>> ─ask Request<Caller, ()>─▶ Mcp
                                                       Mcp ─ask Gather─▶ Exchange: the JSON-RPC body, whole
                                                       Mcp ─ask Call─▶ tool, as Caller::Session { session: 3 }
                    ◀────────────────────────── answer Response ──────────┘ (held until the tool answers)
  ContainerStack, on the way out: no stage is Outbound (Authenticating is asked in only), so the response goes straight on
agent ◀───── Accepted ◀─Write── Exchange ◀─answer Response── ContainerStack
```

A stack whose stages answer on the way out runs them in reverse once the handler answers, each before the exchange writes a byte:

```
handler answers ─▶ ActorStage<P: AskedOutbound> ─ask─▶ its actor ─answer─▶ a pure Outbound stage ─▶ exchange writes it
```

On the local stack, `AsOwner` attaches `Caller::Owner`, and no one is asked before `Mcp`; `AsOwner` is not `Outbound`, so `Mcp`'s answer goes straight to the exchange. Both stacks are the hub's program's (`link_hub`), which names `Mcp` and `Sessions` where neither names the other (ADR-0057).

## Consequences

- **A stack is written by its program,** as an actor type of its own: its settings, its stages and routes, and a handler of each of HTTP's kinds that calls into `Serving`. The MCP program's stack, the hub's two, and a test's are each a few dozen lines.
- **Who owns a port is never a question.** A stack owns its port and every route on it; a program with two ports has two stacks, and their handlers share no table.
- **A stack knows its stages' types,** so a principal travels typed from the stage that attaches it to the handler that reads it, as `Request<A, C>`'s `A`. Nothing is sealed or carried as bytes on the way.
- **A handler knows nothing of ports, routes, or authentication.** It is asked a `Request<A, C>` by a stack, reads who sent it from `attached`, and answers. `Mcp` serves any program's stacks without naming one.
- **A request crosses its stack on the way to its handler,** and each actor stage it names on the way in; its response crosses each `AskedOutbound` actor stage it passed again on the way out. That is one hop more than an exchange asking a handler directly, which chains within the step (ADR-0013), and one each way for each actor stage. A pure stage costs no hop, and a stage is asked only for the halves it implements, so one with nothing to do on the way out costs nothing there.
- **A stack with a body stage relays every part of the body it reads or writes,** one hop for each part, however many body stages it chains. A stack with none adds nothing to a body, and makes no blob of it.
- **Every body is read by its reader's ask,** a gather for a small body such as MCP's JSON, answered once with one blob, or a stream for a body of any size; so no limit on a body is the stack's, nothing of a body is read before every stage has passed it, and a push of gigabytes is read as a stream.
- **A handler that fails or forgets is caught at once,** by the engine's answer for it, and not by a deadline.
- **The handler does not pace how many requests it takes.** Each connection has at most one out, so they are bounded by each stack's `most_exchanges`. A handler that must take fewer holds what it cannot start, or the limit is set lower.
- **A handler cannot learn that its client hung up.** The exchange closes, and the answer that comes later is passed over. A handler that should stop work on a hang-up needs a notice it can watch for, and none is designed here.
- **What an exchange holds is bounded:** its head, by `most_head_bytes`, and of the body its read window and one part, or, for a body gathered whole, the `most_bytes` its handler names. The number of exchanges is bounded by `most_exchanges`.
- **A stage is asked for every request, and an actor stage holds nothing for the next on the stack's behalf.** The hub's authenticator compares a few dozen bearers; one that is costly to ask keeps what it learned itself.
- **A handler's trust in what is attached rests on the sender it states,** `type From = FromStack;` (ADR-0058), which admits an actor whose type takes `Incoming`.
- `Streams` gains `part_held` and `grant`, a reader's way to stop granting while it is busy. TCP's connections do not need them, and any stream asker that works on one part at a time can use them.
- **A streamed response holds its source for as long as the client reads.** The stall limit frees both from a client that stops reading, and the source learns of a hang-up by `Enough`. What a source holds meanwhile is its own: a pipe to a child process is paced by the same credit, so the child blocks on its full pipe while the client is slow.
- **Not built, by choice:** stages for one route, as a route's own concerns are its handler's, and routes that need other stages are another port's; routes that overlap, settled by order or by the longest pattern; stages changed while the program runs.
- **Not decided here:** a stack a guest builds, or one changed while the program runs, for guests later; the routes the git module adds to the hub's container stack; server-sent events, whose source is a streamed response once a tool needs to report progress, and which would want a write of each event at once rather than a stall limit; TLS; `Date` headers, which the exchange does not write. For the client: TLS, HTTP/2, redirects, cookies, pipelining, codings other than `chunked`, and a pool of connections.

## Open questions

- **The way out inside the exchange's wait.** The asks on the way out share the exchange's `answer_within_millis` with the handler's answer, so a slow handler leaves the stages on the way out less time. The way out could have a budget of its own, which the exchange would have to learn of.
- **A body stage whose output outgrows its part.** The stack hands the last stage a buffer with room for one chunk, and a stage that writes more grows it; ADR-0042's pool keeps a buffer only at most twice the room asked, so a stage that inflates far past its input, as a gzip request body can, allocates for each such part. `part` could write at most the room it is handed and keep the rest for the next call, which its shape does not allow.
- **A stage's halves are named where it is added.** A program that adds a stage with fewer halves than it implements runs only those; the compiler refuses a half the stage lacks, not one left out. Finding the halves from the stage's impls alone would need Rust to ask whether a type implements a trait, which it cannot without specialization.
- **`FromStack` admits any actor whose type takes `Incoming`,** where the library's `ActorRef<Exchange>` once admitted one type. A handler cannot name its program's stack types; a handler generic over the guard its program gives it would name them exactly.
- **Writing a stack's handlers.** Each is one line into `Serving`, and a stack writes six of them, more with an actor stage asked on the way out or a body stage; a derive could write them.

## Alternatives considered

- **A central `Http` that owns the ports and routes,** with listeners named in its settings and path prefixes mounted on them while the program runs, each mount naming a guard and a handler. It answers who owns a port that several actors share, which a stack that owns its port never asks. The exchange, one type for every program, could not be typed by a program's principal, so the principal crossed it sealed as bytes, under a scheme of the crate's own; and mounts that change while the program runs need a table the exchanges ask, and a holder each mount is dropped with.
- **A port served by whoever asks `Serve` of `Http`.** The asker owns the port for every handler on it, as `Mcp` owned the hub's two, and a second handler on the port has to go through the first. A stack that binds through `Tcp` itself needs no root between them.
- **A guard per mount, fixed (`As`) or asked (`By`).** Two shapes of one thing: a principal fixed by where the port is, is a pure stage that attaches it, and one asked is an actor stage. Stages need no third shape for a public port, which attaches nothing.
- **Stages for each route.** Every request would be matched before it was checked, and a route's stages would differ from its neighbour's on one port. What one route needs is its handler's; a port's stages are the same for every route on it.
- **First-match routing, or the longest pattern winning.** The order routes were given, or a rule a reader must apply, would decide where a request goes. Routes that never overlap leave one answer, found by one walk.
- **Routing by prefix alone, the handler matching the rest.** Each handler would parse its path again, and a wrong method would be each handler's `405` to write.
- **A handler asked by the exchange directly, the stack only routing.** An actor stage's answer would come back to an exchange that parks nothing and runs no stages; the stack is where the stages live and their state is kept.
- **One stage trait with both ways,** a stage with nothing to do on a way writing a step that passes. Every stage would be run, or every actor stage asked, on both ways, a hop each way for an actor stage that has nothing to say; a stage that opts into each half by its trait is asked only where it acts, and its type says so.
- **An actor stage that may skip its ask on the way out, deciding for each response.** A default that skips is a stage that does nothing on a way, said at run time where its protocol could say it once by type.
- **An actor stage told the response on the way out, not asked.** The response would be written before the stage had a say in it, so a stage could not change it, and the way out would not be the way in's equal.
- **A small body gathered by its handler from a stream's parts.** Each handler of a small body would gather it the same way, as `Mcp` once did; one ask answered once with one blob does it in the reader, which already holds the bytes.
- **A body stage that reads and serves the body as an actor of its own.** Each part would take a hop for each body stage; in the stack, stages chain within one turn, and the only hop is the one to the handler.
- **A body stage's output put as a blob after every stage.** Each step would be a put, and each blob a buffer of the pool for bytes that never leave the stack; only what crosses to another actor needs a blob.
- **A stage for each request, spawned as an actor.** One actor per request per stage, where a function in the stack's turn does the same with no hop.
- **The body gathered whole before the stages, by a limit of the stack's.** A refusal would come after the body was read, and the limit would be the port's, where it is the route's.
- **The body sent to the handler unasked, as parts of the request.** The handler could not pace it, and an exchange would hold whatever the handler had not yet taken. A stream the reader opens is paced by its credit, and is ended once with how the body was read.
- **Requests as a stream the handler opens on the stack,** each part an `Incoming`, answered by a tell sent to the exchange. The handler's credit would pace how many requests it takes. But the answer would be a tell the exchange could not tie to a request, so a handler that failed or forgot would be found only by a deadline, and it needs more kinds than an ask does.
- **HTTP's framing in `Tcp`,** as a third `Framing` case. Rejected in ADR-0033: TCP would know HTTP's rules.
- **A third-party parser** (`httparse`). Less code to write. The hub stack is in-house by choice, and a request head is a small grammar with limits that have to be ours anyway.
- **Refusing every `Transfer-Encoding`.** It shuts out smuggling with no decoder to write, but it also refuses every client that sends a body whose length it does not know up front, and the client already decodes chunks. Refusing a body framed two ways shuts out the smuggling as well.
- **A switched connection handed to its asker as the `Dialed` itself.** One hop less for each read. But a connection
  has one reader, and one whose reader ends hangs up (ADR-0033), so `Tcp` would need a way to hand its reader over, and
  the chunks already granted to the client would reach it after the handover. The client relays what it reads; writes
  go to the connection directly.
- **A switch as an ask of its own, answered once.** Its bytes would still need a stream, opened after the answer, with
  the bytes that came with the head held in between. The stream that streams a body carries a switched connection's
  bytes the same way.
- **A client for each request, closing the connection once it is answered.** Nothing to keep between requests, but
  every request to Docker would dial again.
- **A streamed response's body as parts the handler sends unasked, after its answer.** The exchange could not pace them, and would hold whatever the client had not yet read. A stream the exchange opens is paced by its credit, and is ended once with how the body was made.
- **Each part of a streamed response written as it comes, several writes out at once.** Fewer turns between parts, but a write answered `Full` would be followed by later ones the connection took, so the body would go out of order, and the parts already handed on could not be written again. One write out at a time, of everything queued, keeps the order, and lets a write the connection would not take be written again.
- **A streamed response timed by `answer_within_millis`.** A pack of gigabytes to a slow client would be cut off while it was still moving. The stall limit bounds a response that stops, not one that is long.
- **Answering pipelined requests concurrently.** Responses must go out in request order, so the exchange would queue responses behind slower ones. One request at a time, with credit withheld, keeps the order and the bound.
