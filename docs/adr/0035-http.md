# ADR-0035: HTTP

- **Status:** Proposed
- **Date:** 2026-10-28

> **Amended (2026-10-28), before it was implemented.** The first text had the handler open a stream of requests on
> the server and answer each by sending a tell to its exchange. That rested on a claim that a `ProtocolRef` does not
> cross mail, which is false: it has a codec, written as an `ErasedActorRef` is (ADR-0016). The handler is now named
> in `Serve` and asked `Request` by each exchange, as below, and the stream design is among the alternatives.

## Context

The hub's MCP endpoint is HTTP. MCP's Streamable HTTP transport asks very little of it. The client POSTs one JSON-RPC message, and the server answers with one JSON body, or with `202 Accepted` for a notification. A GET, which would open a stream of the server's own messages, may be answered `405`. So the first HTTP the engine needs is an HTTP/1.1 server that reads whole requests and writes whole responses. A client, streamed bodies, and TLS can come later.

What the engine already decides:

- **TCP is a capability, and HTTP sits on it** (ADR-0033: `Tcp`, `Listen`, `Listener`, `Accepted`). A connection reads `Framing::Chunks` and leaves where a request ends to HTTP. The frames come on a `Reading` stream, paced by the reader's credit, and a write is a `Write` ask answered `Sent`, `Full`, or `HungUp`. A connection whose reader ends shuts itself.
- **A stream is a request held open, paced by the asker's credit** (ADR-0017: `Stream`, `Streams`, `Serving`, `More`). It is the engine's one form of backpressure. `Streams::part` grants one more part for each part taken.
- **A protocol reference crosses mail, and an actor can make one to itself** (ADR-0016: `ProtocolRef`, `ActorRef::protocol`; `Turn::me`). A named protocol says what each of its kinds is answered with, so whoever holds a `ProtocolRef<P>` can ask through it without knowing the actor's type.
- **A request is answered exactly once, and is not cancelled** (ADR-0017: `turn.hold`, `turn.answer`, `Unanswered`). A receiver that ends, fails, or lets a request go is answered for by the engine. An asker that gives up passes over the answer when it comes.
- **A capability is a root asked at a typed path** (ADR-0022: `ChildOf`, `path::<L>`, `Carries`), and **a root that needs nothing of its host is bootstrapped for every host** (ADR-0029: `impl<H: Host> Bootstrap<H>`).
- **No actor ends another** (ADR-0009). It is sent `Shut`, and closes itself.

Input on a listening socket is untrusted. Its size, its shape, and how slowly it arrives all have to be bounded before anything reaches the program.

## Decision

**One capability, `Http`, in the crate `aethereal-http`, a server on `Tcp`. It parses and writes HTTP/1.1 itself, with no third-party parser.**

```
Http                 root, singleton, asked at path::<Http>(())
 └─ Server:port      listens through Tcp; spawns an exchange for each connection
     └─ Exchange:n   reads one accepted connection; asks the handler each request; writes each response
```

```rust
impl ChildOf for Http     { type Parent = Top; }
impl ChildOf for Server   { type Parent = Http; }     // keyed by its port, as a u64
impl ChildOf for Exchange { type Parent = Server; }   // keyed by the server's count
```

- **An exchange is the server's side of one TCP connection.** Its config carries the `ActorRef<Accepted>` the listener made and the handler. It opens `Reading` on that connection on its first `Tick`, since a stream is opened in a turn and a `begin` is not one (`Streams::open` takes a `Turn`), as the server opens `Accepting` on its listener, and writes to it through `Writing`. HTTP holds no socket: every byte goes through `Tcp`.
- **The crate builds for every host, and is bootstrapped for every host** (`impl<H: Host> Bootstrap<H> for Http`). It needs nothing of its host but `Tcp`. A program without `Tcp` builds, and its `Serve` is answered `Unavailable`.

### Serving is asked of the root, naming the handler

```rust
impl Carries<Serve> for Http { type Answers = (Served,); }

pub struct Serve { pub port: u16, pub handler: ProtocolRef<Handling> }   // port 0: any free port

pub enum Served {
    Bound { server: ActorRef<Server>, port: u16 },             // the port bound, which is the server's key
    Taken,                                                     // something holds the port
    Full,                                                      // the root holds its most servers
    Refused,                                                   // the host refused the bind
    Unavailable,                                               // no Tcp in this program
}
```

- **The handler is any actor that takes `Handling`,** usually the asker itself: `Serve { port, handler: turn.me().protocol() }`. It may be another actor the asker holds a reference to.
- **A serve is held until `Tcp` answers its listen.** The root asks `Tcp` to `Listen` with `Framing::Chunks`, and keeps the held `Serve` as the ask's context. On `Listening::Bound` it spawns the `Server` at that port, with the `ActorRef<Listener>` and the handler in its config, and answers `Bound`. Every other answer maps to its case of `Served`, and an ask that finds no `Tcp` is answered `Unavailable`.
- **The root watches whoever asked** (`turn.watch`). When that actor ends, the root sends `Shut` to the servers it bound for it, as `Tcp` does for its listeners (ADR-0033). **A server watches its handler,** and shuts itself when the handler ends, since nothing is left to answer.

### Each request is asked of the handler

```rust
pub struct Handling;
impl Protocol for Handling { type Kinds = (Request,); }
impl Carries<Request> for Handling { type Answers = (Response,); }

pub struct Request {
    pub method: Method,
    pub path: String,                 // the target's path, as sent
    pub query: String,                // after the `?`, empty when there is none
    pub headers: Vec<Header>,         // in the order sent, duplicates kept
    pub body: Vec<u8>,
    pub peer: SocketAddress,
}
pub struct Response {
    pub status: Status,               // a closed enum of the final statuses HTTP names: Ok, NotFound, ..
    pub headers: Vec<Header>,
    pub body: Vec<u8>,
}
pub struct Header { pub name: String, pub value: String }     // names lowercased by the parser
pub enum Method { Get, Head, Post, Put, Delete, Patch, Options }
```

- **An exchange asks the handler `Request` directly,** through the `ProtocolRef<Handling>` in its config. The request crosses no other actor.
- **The handler answers in the turn it is asked (`turn.reply`), or holds the request and answers in a later one** (`turn.hold`, `turn.answer`), as MCP does once an engine has answered. The ask is the correlation: the exchange keeps no table, and the handler keeps nothing but the `Held` it chose to keep.
- **A request the handler does not answer is answered for it.** When the handler has ended the exchange writes `503`. When its turn failed, it let the request go, or it never answered, the exchange writes `500`.
- **The exchange writes the framing headers itself.** It writes the status line, the handler's headers, `Content-Length` from the body, and `Connection: close` when it will close. A `Content-Length`, `Transfer-Encoding`, or `Connection` among the handler's headers is dropped and recorded in the log. A response to `HEAD` has its body dropped and keeps its `Content-Length`.
- **Many requests are out at once, one per connection.** The handler takes them as they come; how many it holds at once is bounded by the servers' `most_exchanges`.

### An exchange parses as chunks arrive, one request at a time

```
Accepted ─Frame─▶ Exchange: Idle ─▶ Head ─▶ Body { head, body } ─▶ Answering ──ask Request──▶ handler
                                                                       │
Accepted ◀─Write─ Exchange ◀──────────── answer Response ──────────────┴──────────────────── handler
```

- **The exchange keeps what it has decoded, not the raw bytes.** In `Head` it buffers until the blank line that ends the head, then parses it in one pass. In `Body` it gathers exactly `Content-Length` bytes. Bytes past the end of the request stay in its buffer for the next one.
- **While a request is out, the exchange grants no credit.** It takes the `Frame`s still in flight without granting more, and grants what it held back once its response is written. So a client that sends requests back to back, pipelining, waits in the kernel, and TCP slows it down. What the exchange holds meanwhile is bounded by the `Reading` window times its chunk size. This needs two methods on `Streams` (ADR-0017): `part_held`, which takes a part without granting for it, and `grant`, which grants a stream a number of parts.
- **Connections are kept alive,** HTTP/1.1's default. The exchange closes after its response is written (`Wrote::Sent`) when the request said `Connection: close` or was HTTP/1.0. It also closes when the write is answered `Full` or `HungUp`, or the read stream ends.
- **`Expect: 100-continue` is answered `100 Continue`** once the head has passed every check, before the body is read.

### Limits on untrusted input

| The request | The exchange's answer |
|---|---|
| a head past `most_head_bytes` | `431`, then close |
| a body past `most_body_bytes`, by its `Content-Length` | `413`, then close, before the body is read |
| a request line or header that does not parse; a bare LF; a folded header; a header that is not visible ASCII | `400`, then close |
| `Content-Length` sent more than once, or not a number | `400`, then close |
| any `Transfer-Encoding` | `501`, then close |
| a method not in `Method` | `501`, then close |
| an HTTP version other than 1.0 and 1.1 | `505`, then close |
| a target not in origin form (`/path?query`) | `400`, then close |
| a request, head and body, not whole within `request_within_millis` of its first byte | close, no answer |
| no request within `idle_within_millis` of the last response | close, no answer |
| no answer within `answer_within_millis` | `504`, then close; the answer, when it comes, is passed over |

- **Refusing `Transfer-Encoding` refuses chunked request bodies,** and with them the request smuggling that comes from a `Content-Length` and a `Transfer-Encoding` that disagree. MCP's clients send `Content-Length`.
- **Deadlines are checked each `Tick`** against `turn.now()`. An exchange subscribes to `Tick` (`On<Tick>`), as a TCP connection does, so a program that serves HTTP already runs a cycle that holds it (ADR-0033).
- **A refused request still writes a response where one is owed,** then the exchange closes. The handler never sees it.
- **A request whose deadline passes is still out.** Requests are not cancelled (ADR-0017), so the handler's answer still comes, and the exchange, closing or closed, passes over it.

### Ending is by mail

| Type | Ends when |
|---|---|
| `Server` | it is sent `Shut`: by the root when the asker of `Serve` ends, or by whoever holds it. It also ends when its handler ends, or when `Tcp`'s accept stream ends. It sends `Shut` to its listener and to each exchange, and closes |
| `Exchange` | it is sent `Shut`, or it closes the connection as above, or its read stream ends |

When an exchange closes, its read stream's asker is gone, so the TCP connection beneath it shuts itself (ADR-0033). An exchange does not send `Shut` to it.

### Settings

```rust
#[settings]
pub struct HttpSettings {
    pub most_servers: u32,
    pub most_exchanges: u32,           // per server; past it, an accepted connection is shut at once
    pub most_head_bytes: u32,          // 16 KiB
    pub most_body_bytes: u32,          // 8 MiB
    pub chunk_bytes: u32,              // the `Chunks` framing's `most_bytes`
    pub window: u32,                   // the parts an exchange's read stream is granted
    pub request_within_millis: u32,
    pub idle_within_millis: u32,
    pub answer_within_millis: u32,
}
```

The section is `http`. Where listeners bind, loopback by default, is `Tcp`'s setting (ADR-0033: `TcpSettings::interface`).

### A tool call through the hub

```
agent ─POST /mcp─▶ Accepted ─Frame─▶ Exchange ─ask Request─▶ Mcp ─ask─▶ tool
                                         ▲                    │ (holds the request until the tool answers)
agent ◀───────────── Accepted ◀─Write── └── answer Response ◀─┘
```

## Consequences

- MCP gets an endpoint by asking `Serve` with itself as the handler, and answering each `Request`. It reads `path`, `method`, and `mcp-session-id` from the request. Sessions, and what `202` and `405` mean to MCP, are MCP's business.
- **A request crosses one actor on its way to the handler,** the exchange that parsed it. It is copied from the frames into the exchange's buffer, into the ask, and by each actor that keeps it. A `Tick` of TCP polling sits on the way in, and another on the way out. That is fine for tooling, and is measured with ADR-0033's hops on the first MCP slice.
- **A handler that fails or forgets is caught at once,** by the engine's answer for it, and not by a deadline.
- **The handler does not pace how many requests it takes.** Each connection has at most one out, so they are bounded by `most_exchanges` for each server. A handler that must take fewer holds what it cannot start, or the limit is set lower.
- **A handler cannot learn that its client hung up.** The exchange closes, and the answer that comes later is passed over. A handler that should stop work on a hang-up needs a notice it can watch for, and none is designed here.
- Every limit is enforced before a request reaches the handler, so memory per exchange is bounded by `most_head_bytes` plus `most_body_bytes` plus the read window. The number of exchanges is bounded by `most_exchanges`.
- `Streams` gains `part_held` and `grant`, a reader's way to stop granting while it is busy. TCP's connections do not need them, and any stream asker that works on one part at a time can use them.
- **Not decided here:** streamed responses, server-sent events and chunked bodies, which come as a stream from the handler to the exchange when a tool needs to report progress; chunked request bodies; routing, while a server has one handler that matches on `path`, or hands requests on to others; an HTTP client; TLS; `Date` headers, which the exchange does not write.

## Alternatives considered

- **Requests as a stream the handler opens on the server,** each part an `Incoming { request, exchange }`, answered by a `Respond` tell sent to the exchange. The handler's credit would pace how many requests it takes. But every request would cross the server, which would keep a queue; the answer would be a tell the exchange could not tie to a request, so a handler that failed or forgot would be found only by the deadline; and it needs five kinds where an ask needs two. It was the first text of this ADR, on the false premise that the handler could not be named in mail.
- **The server asks the handler, and forwards the answer to the exchange.** One actor would see every request, for no gain: the exchange can ask the handler itself.
- **HTTP's framing in `Tcp`,** as a third `Framing` case. Rejected in ADR-0033: TCP would know HTTP's rules.
- **A third-party parser** (`httparse`). Less code to write. The hub stack is in-house by choice, and a request head is a small grammar with limits that have to be ours anyway.
- **Accepting chunked request bodies now.** No MCP client needs them, and accepting them is where request smuggling comes from.
- **Answering pipelined requests concurrently.** Responses must go out in request order, so the exchange would queue responses behind slower ones. One request at a time, with credit withheld, keeps the order and the bound.
