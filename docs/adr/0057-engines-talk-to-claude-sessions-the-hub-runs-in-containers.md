# ADR-0057: Engines talk to Claude sessions the hub runs in containers

- **Status:** Proposed
- **Date:** 2026-11-13

## Context

The engine's owner works with Claude from outside the engine today: Claude drives engines through the hub's MCP tools (ADR-0037, ADR-0038: `EngineTools`), and the owner reads the conversation somewhere else. The aim is for the owner to sit in an engine and work with Claude from its dev overlay (ADR-0053), with Claude's sessions running beside the hub on the build host.

Constraints:

- **The owner's Claude subscription, not the API.** Claude Code's print mode, `claude -p`, runs on a subscription token from `claude setup-token`. A subscription is one person's, so the hub is a local tool for one person on one machine.
- **The engine stays thin.** An engine shows a session and sends what its owner does; it never runs Claude, holds a credential, or knows how a session is hosted.
- **Sessions outlive engines.** Engines are restarted, republished, and closed all the time, and a conversation must not end with one.
- **Sessions are long-standing.** The owner works in a few sessions kept for days, each compacted over and over, rather than one per task. What a session is worth is its conversation and its history, which must outlast every container it runs in, and an engine shows the few sessions the owner is working in there, not every one the hub holds.
- **A session runs whatever it wants, within limits.** It builds, runs tests, and spawns engines, so it needs its own files and a share of the build host that the hub can cap.

What is already decided:

- **Only tools cross the link** (ADR-0038: `Up::{Hello, Sheets, Called}`, `Down::{Refused, Call}`, `REVISION`). The hub calls an engine's tools, and an engine never asks the hub for anything.
- **The hub spawns engines from its store** (ADR-0039, ADR-0040: `CheckIn`, `Launch`, `Spawned`, `MintFor`). `check_in` reads a path on the hub's machine.
- **The dev overlay's console reads a typed line into one of the engine's tools** (ADR-0053: `CommandLine`, `print_value`).
- **HTTP serves on the TCP capability** (ADR-0035: a stack, its layers; ADR-0033: `Tcp`). There is no client and no Unix socket.
- **Files are read and written through `Files`, in named namespaces whose places are the host's** (ADR-0032, ADR-0039: `ReadFile`, `WriteFile`, `Save`). An actor never learns where a namespace is, and any actor may read one.

What a probe on the build host established, with Claude Code 2.1.310 in a container reached through Docker's Engine API over its Unix socket:

- `claude -p --input-format stream-json --output-format stream-json --verbose` runs headless on a subscription token passed as `CLAUDE_CODE_OAUTH_TOKEN`. Two containers ran at once, and a container reached the hub's MCP server.
- **Attach upgrades.** `POST /containers/{id}/attach?stream=1&stdin=1&stdout=1&stderr=1` with `Upgrade: tcp` is answered `101 UPGRADED`, and the connection is then the process's stdin and stdout, each output chunk behind an 8-byte header naming its stream and length.
- **Stdin outlives an attach.** With `OpenStdin` set and `StdinOnce` clear, a detached and re-attached connection reaches the same process, which remembers the conversation.
- **A turn finishes with nobody attached,** and `GET /containers/{id}/logs?since=` returns all of it.
- **Interrupt is a line on stdin:** `{"type":"control_request","request_id":…,"request":{"subtype":"interrupt"}}` is answered by a `control_response`, the running tool is stopped, the turn ends as `error_during_execution`, and the process takes the next turn.
- **Subagents run in the session's process.** Their events carry `parent_tool_use_id`, with `system` events `task_started`, `task_progress`, `task_updated`, and `task_notification`.
- **A background subagent outlives its turn, and when it finishes, Claude starts a turn by itself:** `init`, the assistant's message, and a `result`, with no input sent.
- **`/compact` sent as a message compacts:** `system` `status: compacting`, then `compact_boundary` with `trigger`, `pre_tokens`, and `post_tokens`. The conversation carries on from the summary.
- **`--resume <id>` in a new container** with the same home volume continues the session.
- Print mode chose Sonnet by default, so the model must be stated.

## Decision

**The hub keeps each Claude session as a permanent record, its transcript, its conversation, and its home, and connects it to Claude only while it is awake, in a Docker container of its own, made only from the hub's config and reached through Docker's Engine API over its Unix socket. A session idle long enough hibernates: it is told, compacted, and its container shut down, until a line said to it or `wake_session` wakes it. A new capability, `Sessions`, holds the sessions, writes the owner's lines to an awake session's stdin, reads its events from its stdout, and keeps each session's events as one numbered transcript, readable whether the session is awake, hibernating, or archived. Trusted engines, the ones the owner starts, gain chat frames on the link: each shows as tabs the sessions it chose, opens one to read its transcript from any point, types to it, interrupts, hibernates, or wakes it, and answers what it asks. Untrusted engines, the ones a session spawns, keep the link as it is. The dev overlay's drop-down console becomes the chat: a line goes to Claude, and in `!` mode a line runs the engine's own tool, as the console's own tab always does.**

```
console line ──> Up::Say ──> hub: Engine(37) tags it ──> Session: numbered transcript
                                                            └──> attach stream (stdin) ──> claude -p in the container
claude -p ──> stdout events ──> logs, followed ──> Session: numbered transcript ──> Down::Show to every engine with the tab open
claude -p ──> hub MCP (its session's route) ──> check_in, spawn_engine, call_tool on its work engines
console line in ! mode ──> the engine's own tool, now ──> Up::Ran ──> transcript, and written as a line of its own
```

### A session is a record, and its container the connection

- **A session is a record.** What makes a session is permanent: its name, its numbered transcript, Claude's conversation id, and its home volume. Its container is only its connection to Claude, made as it wakes and removed as it hibernates or is archived. Any session, archived ones included, is opened and read in full from its transcript with no container and no Claude running.
- **A session's state is about its conversation:**
  - `Idle`: nothing runs in it, and it waits for a line;
  - `Working`: a turn runs, the notice's turn of a wind-down included, or a background task of its does, from `task_started` until its `task_notification`;
  - `Waiting`: a turn waits on the owner's answer to an ask (see the link, below);
  - `Compacting`: it is being compacted;
  - `Hibernating`: it has no container, and is ready to be picked up again;
  - `Archived`: it never wakes again, and its record stays readable.

  Its container's state is a detail beneath that: `None`, `Starting` (its record saying so written, then its volumes, credential, and container made and started), `Attached` (it runs, and its stdin is attached), or `Lost` (it ended without the hub ending it: its process exited, the kernel killed it for its memory, or it was gone when the hub came back to it). A session is **awake** from its container's `Starting` until Docker has removed it. A session whose container is lost is hibernating, without the compaction, and wakes as any other; until it does, it shows as lost, so the owner knows its last turn may have been cut short. As it wakes, the hub first writes it a line of its own, tagged in the transcript as the hub's, whose text is a setting, `lost`: its last container ended without warning, so its last turn may have been cut short; its work tree at `/session/home/work` is as that container left it; and it should check the tree and push what is worth keeping. The line that woke it, if one did, comes after. A container whose start script failed its bootstrap is not lost (see Code reaches a session through the hub's repository, below): it never ran Claude Code, so it cut nothing short, and its session hibernates with no container, never told it was lost.

- **One container per awake session.** Its command is the image's start script, `/usr/local/bin/aethereal-session-start`, followed by `/usr/bin/claude -p --input-format stream-json --output-format stream-json --verbose --model <model> --dangerously-skip-permissions --append-system-prompt <prompt>`, with `--resume <id>` once Claude has named its conversation: the script readies the session's work tree (see Code reaches a session through the hub's repository, below) and then `exec`s the rest of its command, so Claude Code keeps the container's stdin and stdout. It lives while the session is awake: a long build or a background subagent keeps running between turns. The id is read from the `session_id` Claude's events carry, and is passed on only when it is a UUID.
- **Each container of a session is a run,** numbered from 1 and named for the hub's label, the session, and the run. A session that hibernates and wakes runs in a new container on the same home, which is how `--resume` finds the conversation.
- **A session's volumes are Docker named volumes,** each named for the hub's label, so two hubs on one daemon never share one, and Docker keeps where each lives, so the hub names no path of the build host for one:
  - its home, `aethereal-session-<label>-<n>`, at `/session/home`, its `HOME` and working directory;
  - its cargo target directory, `aethereal-session-<label>-<n>-target`, at `/session/target`, its `CARGO_TARGET_DIR`, so a session's builds are kept between its runs and never mixed with another's;
  - the cargo home every session of the hub shares, `aethereal-cargo-<label>`, at `/session/cargo`, its `CARGO_HOME`, so a crate is fetched once for all of them. Cargo locks its registry and git caches with file locks, which hold across containers on one volume, so concurrent sessions share it safely. What else a cargo home holds, a `cargo install`'s binaries and a `config.toml`, is shared too.

  Before each container of a session, the hub asks Docker to make each volume, one at a time, labelled as its containers are, a session's own with its number and the shared one with the hub's labels alone; Docker answers a volume already made as made. A session's container runs as the settings' user, as Claude Code refuses to skip its permission checks as root, and a volume Docker makes is root's. The session image holds the three directories owned by that user, and as a container is made on a volume that is still empty, Docker copies the image's directory at its target into it, that directory's owner with it, so each volume is the user's from its first container, and nothing runs as root. A volume is never mounted with `NoCopy`, which would leave it root's.

  Docker's local volumes take no size limit, so the volumes are bounded by use, not by Docker: cargo's own cleaning of its global cache removes downloads and sources unused for months; a session's target holds what that session built, and the session is told to keep its builds to what it changed; archiving keeps every volume, and the owner removes what an archived session no longer needs.
- **The container is built only from the capability's config.** Its image, its mounts, its limits, its network, and its labels all come from `Sessions`' settings and the session's number and run. Nothing is passed through from a tool call, a frame, or Claude, so no one can ask for another image or another mount: a session's name is only shown, and Claude's conversation id is passed on only as a UUID. Access to the socket is access to the build host, and this rule is what keeps it the hub's.
- **Every container carries two labels:** `aethereal.sessions`, whose value names the hub, which a list and the events are filtered by, and `aethereal.session`, the session's number. The settings may add more, as a test's runs add `aethereal.test=1`.
- **What a container holds:**
  - its three volumes, each written as one of `HostConfig.Mounts` of type `volume`, named only by a name Docker takes for a volume, which never spells a path;
  - its drop box, the one directory of the build host it is given, bound read and written at `/session/drop` (see below);
  - the credential, from a file of `KEY=VALUE` lines whose path the capability's settings name, read as each container is made and given as its environment. Aethereal has no store of secrets yet (ADR-0028 leaves them to a record of their own), so the host serves the capability one service, `Credential`, whose one method reads the file, and a job turns its lines into the container's variables. It is never kept in `Files`, whose namespaces any actor may read, and never a setting's value, an argument, a log line, or a record. The Engine API has no environment file, so the value is in the create's body, which crosses the engine as the job's answer and the `Create` to the Docker client; a variable's `Debug` names it without its value;
  - its session's number, `AETHEREAL_SESSION`; the hub's repository's URL, the setting `git_url`, as `AETHEREAL_GIT_URL`, left out when the setting is empty; and the limit of each step of its start script, the setting `bootstrap_secs`, as `AETHEREAL_BOOTSTRAP_SECS`. The hub's own variables come after the credential's, so a line of its file never stands in for one;
  - the bearer of its route to the hub's tools, `AETHEREAL_HUB_BEARER`, in its environment beside the credential and kept as the credential is (see the route, below). The same job readies all three, `Provision`: it reads the credential, draws the bearer from the host's randomness, and has the store's stockroom make the drop box, and a session whose container cannot be given one of them is refused, naming which.
- **The session image** is made by `cargo xtask create-session-image --claude <version | latest | stable>` from `crates/aethereal-sessions/image/`, beside the capability that runs it, when the owner chooses. The hub never builds an image: its setting `image` names the tag the verb printed, and that is its only choice of image. The verb assumes only Docker on the machine. It writes the image's directory as a build context under the target directory; resolves `latest` or `stable` to the exact version Anthropic's release site names for it; refuses a version that Claude Code's apt repository does not list; builds with Docker; prints `claude=<version>`, with `channel=<name>` when a channel was named, then `image=<tag>`, the tag `aethereal-session:cc-<version>` unless `--tag` names one; and removes the context either way. `--uid` and `--gid`, `1000` by default to match the setting `user`, make the user `session`, which owns `/session/home`, `/session/target`, and `/session/cargo`; `--rust` names the Rust version, the repository's `rust-toolchain.toml` by default.
- **Every part of the image is fetched in its build and verified against something pinned,** never copied from the machine that builds it, and a part added later is added the same way. What is pinned is in one place, `xtask/src/session_image/pins.rs`, handed to the Dockerfile as build arguments, beside the release key committed with the Dockerfile:
  - the base image, `rust:<version>-slim`, pulled by the digest of its multi-platform index, which fixes the Debian inside it; a Rust version with no pinned digest is refused;
  - `git`, `ca-certificates`, `ripgrep`, `jq`, and `python3`, installed by apt and verified against the Debian archive keys in the pinned base;
  - the start script, `aethereal-session-start`, git's credential helper, `git-credential-aethereal`, both in `/usr/local/bin`, and git's system config, `/etc/gitconfig`, which names the helper: three short files committed beside the Dockerfile, copied from the build's context, and fetched from nowhere;
  - the toolchain's `clippy`, `rustfmt`, `rust-src`, and `wasm32-unknown-unknown`, installed by rustup and verified against the checksums of its channel's manifest, so rustup never fetches another as a user who cannot write its home;
  - Claude Code, at the exact version asked, `claude-code=<version>-1`, installed by apt from Anthropic's signed repository of the channel, `downloads.claude.ai/claude-code/apt/<channel>`; a named version comes from `latest`, which keeps the most history. apt verifies the repository's index against Anthropic's release key alone, and the package against the index's checksum. The key is committed beside the Dockerfile as `claude-code.asc`, and the build refuses it unless it is one key whose fingerprint is the pinned `31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`, the one Anthropic publishes. gpg reads it in a stage of its own and is not in the image. The package puts Claude Code at `/usr/bin/claude`. The image holds no credential.
- **A new Claude Code is chosen by making a new image:** run the verb with a new `--claude`, and point `sessions.image` at the tag it prints.
- **The project's code is not in the image.** A session clones it over its route from the hub's repository into its home volume, as its container starts (see Code reaches a session through the hub's repository, below); nothing of the build host is mounted for it.
- **Permission checks are skipped inside the container** (`--dangerously-skip-permissions`). The container is the sandbox: it holds no key of the owner's, and its one credential beyond Claude Code's is its bearer, which the hub takes only from its route, so what Claude does in it stays in it until something the hub serves takes it out, and git takes out only branches under the session's own name.
- **The model is always stated,** from the settings, as print mode otherwise picks its own.
- **Limits are the hub's.** Each container is capped by CPU and memory (`HostConfig.NanoCpus`, `Memory`), and at most `most_running` sessions are awake at once across the hub. Only awake sessions count: a hibernating or archived session holds no container, and reading any session's transcript is unlimited. A new session, or a wake, past the cap is refused, and the refusal names the awake sessions, so the owner chooses one to hibernate. The hub never hibernates a session to make room. Defaults: 4 CPUs and 8 GiB each, 4 awake, 55 minutes idle.
- **A session idle long enough hibernates.** Once a session has been `Idle` for the idle time, `idle_secs`, it is wound down:
  1. if it has had a turn since its last `compact_boundary`, the hub writes it a notice, a user's line tagged in the transcript as the hub's, whose text is a setting: it will be compacted and hibernated next, and it should write down its loose threads, unfinished work, open questions, uncommitted changes, and what to pick up next, then commit its work in progress and push it to a branch under `sessions/<n>/` named for what it is, not one branch shared by all its work, so the owner and the other sessions can see it. It says nothing of why, as `hibernate_session` sends the same notice (below), and a session hibernated early has not been idle. The hub waits for that turn's `result`;
  2. it writes `/compact`, also the hub's, and waits for its `result`;
  3. it stops the container and removes it, keeping the session's home, and the session is hibernating.

  Each wait has a deadline, a setting; past it, the transcript notes which step was overdue and the container is stopped anyway. A line said during steps 1 and 2 makes the session active again: the rest is cancelled, and it stays awake. A session with nothing new since its last compaction goes straight to step 3.
  - **The idle time is the prompt cache's lifetime.** A session idle that long reads its whole context afresh on its next turn whatever the hub does, so compacting it then costs nothing a warm cache would have saved, and a session still warm is never compacted for nothing. Claude Code writes a session's cache to last an hour (`ephemeral_1h`), so `idle_secs` is 55 minutes: the five minutes left keep the wind-down's own turns, the notice and `/compact`, reading the cache warm.
  - **`hibernate_session` does the same on demand:** the notice, the compaction, and the stop. It is refused while the session is `Working`, `Waiting`, or `Compacting` from a compaction the hub did not ask for, the owner's `/compact` or Claude Code's own, saying which as the list shows it, so it never cuts a turn or a compaction short or leaves an ask unanswered; the owner interrupts or answers first if they mean it, and asks again once a compaction ends. A session already winding down, its notice or the compaction the hub asked for, or hibernating is answered as it stands.
  - **Nothing ends a session but archiving.** Hibernation keeps everything a session is, and a hibernating session is ready to be picked up again.
- **A line said to a hibernating session wakes it, as `wake_session` does.** The hub starts a new container on its home, which resumes its conversation with `--resume`, and then delivers the line. Lines said while it starts wait, and go in order once its stdin is attached. A wake counts against the cap as a new session does, and one past it is refused, naming the awake sessions.
- **Archiving a session** stops and removes its container if it is awake, and keeps its record: its name, its transcript, and its home's volume. An archived session never wakes again, is read as any other, and keeps its name taken.
- **A session's builds reach the store through its drop box.** Its target directory is a volume Docker keeps, not a path the hub names, so `check_in`, which reads a path on the hub's machine, cannot reach it, and a path a session names on the hub's machine is not the session's to name. So each session is given one directory of the build host, its drop box, which the store keeps beside its entries as `drops/<n>` and its stockroom makes before each container, bound at `/session/drop`. The session copies a build it wants to run there, and calls `check_in` with its path there, `/session/drop/<file>`; called by a session, `check_in` reads nothing else: a path outside the box, or one that climbs out of it, is refused before the store is asked, and the store's `CheckInDropped` names the session and one plain file name, never a path. The stockroom opens that name in that session's box without following a link (`O_NOFOLLOW`) and without waiting on a pipe (`O_NONBLOCK`), and copies it only when what it opened is itself a regular file. This holds against code the session writes: the box's directory is the hub's, and its container cannot replace the mount it is given; the only way a name in it reaches another file of the build host is a link, which is never followed, and a hard link can be made only to a file the container sees, which is only what is in its own box. What the session puts there is its own build, and nothing more of the build host leaves with it. The container runs as the hub's own user (`sessions.user`), so it writes its box and the hub reads it.
  - **Why not the other ways:** reading the session's target volume where Docker keeps it reads a directory only root may enter, and would follow whatever links the session left in it. Docker's archive API reads a path inside the container's own root, but answers a tar of the whole file, which a build hundreds of megabytes large would cross the engine whole as mail, or need a stream into the store that nothing has. Sending the bytes over the route has the same weight, and Claude cannot write a binary as a tool's argument.

### The hub reaches Docker through its Unix socket

- **Docker's Engine API is HTTP over `/var/run/docker.sock`.** The hub uses it directly, not the `docker` command:
  - `POST /containers/create`, `/start`, `/stop`, `/kill`, `DELETE /containers/{id}`, and `GET /containers/{id}/json` to make, end, and inspect a session's container;
  - `POST /volumes/create` to make a session's volumes;
  - `GET /containers/json`, filtered by the label every session container carries, to count what runs;
  - `POST /containers/{id}/attach`, upgraded, for stdin and stdout;
  - `GET /containers/{id}/logs?follow=1` for stdout and stderr, from the container's start;
  - `GET /events` to learn at once that a container died.
- **Three things are built for it, each in the crate it belongs to:**
  - **a Unix transport** beside `Tcp`, a stream connection to a socket path;
  - **an HTTP/1.1 client in `aethereal-http`:** requests with `Content-Length` bodies, responses with `Content-Length` or chunked bodies, and an upgrade that hands the connection back as a raw stream. It is written for the subset Docker speaks, not taken from a crate;
  - **a Docker client in the sessions capability's crate, `aethereal-sessions`:** a root, `Docker`, asked at its typed path. It answers typed requests (`Create` from a `ContainerSpec`, `Start`, `Stop`, `Kill`, `Remove`, `Inspect`, `List` by a label, and `CreateVolume` by a `VolumeName` with its labels) and serves typed streams (`Attaching`, whose first part is the container's stdin and each later part its output; `Logging` from a time on; `Watching` the start, die, and OOM events of the containers that carry a label), each paced by its asker's credit, with the 8-byte stream frames of an attach and of logs taken apart into stdout and stderr. No request, path, or JSON of its asker's reaches Docker: a container is made only from a `ContainerSpec`, and named only by its id as Docker gives one, never by a name or a path; a volume is named only by a name Docker takes, checked as it is made and again as it is written. Each request goes on a connection of its own, which the client hangs up once its reply is read, as `Http`'s client takes one request at a time and an attach or the events hold theirs for hours. Every path names API version 1.44, so a daemon answers in the shapes the client reads. Its errors are named cases: not found (`404`), a conflict (`409`), another status, a socket missing or with nothing listening, and a malformed reply.
- **The container's stdin and stdout belong to Docker, not to the hub.** A hub that restarts loses no turn: the container keeps working, and the hub re-attaches and reads what it missed from the logs.
- **A session's output is read from its logs, followed from its container's start, and its stdin written through its attach.** The transcript knows how many bytes of the latest container's stdout and stderr it holds, so a logs stream opened again, after the hub restarted or a stream ended while the container runs, skips them and records each line once, with none missed between an attach and a catch-up. What the attach carries of the output is let go. A container's logs ending, or its attach, asks Docker for its state: one still running is followed again, and one that is not has ended.
- **Every ask of Docker carries a deadline,** a setting, past which the capability takes it as unanswered (ADR-0041); a stop's deadline adds its grace.

### Sessions belong to the hub

- **A session is the hub's, not an engine's.** A session is used from whichever engine the owner is at, and every trusted engine can open any session; which sessions an engine shows as tabs is that engine's own (see The console is the chat).
- **When an engine closes,** only its open tabs end. A turn running carries on, a line already sent is still delivered, and a question waiting for an answer stays waiting until an engine opens the session and answers it.
- **The capability keeps its sessions through `Files`, in `Save`, as any actor does,** so the hub has one service that touches its disk, and where `Save` lives is the hub's `Files` setting:
  - `sessions/index` lists every session's number, written whole as a session is added;
  - `sessions/<n>/record` is a session's name, conversation id, runs, and where it stood (starting its container of a run, named by the session's number and the run, as Docker has not answered its id; awake in its container of a run, named by its id; hibernating; hibernating with its last container lost, so a hub that starts again still shows it lost; or archived), written whole;
  - `sessions/<n>/transcript` is its transcript, each entry a frame, its length and then its bytes, appended (ADR-0039's `Writes::Append`).

  One write runs at a time: a session's new frames are appended, and only once that append is answered is its record written, so a record never stands ahead of its transcript, and no two appends to one transcript are in flight at once.

  A session's container exists only while its record says it may, by the order of writes alone. Waking a session first writes its record saying it starts its container of the next run, which claims no entry of the transcript, and nothing of the run, its volumes, its credential, or its container, is made until that write has landed; a record that does not land refuses the wake. A container is removed before the record saying the session hibernates is written, whether it was stopped, ended by itself, failed to start, or was found not running. So a hub killed at any point leaves a record that names every container of its sessions that may exist.

  An append a crash cuts short leaves a frame whose length runs past the file's end, which a read leaves out. `Files` lists no `Save` directory, and needs not: a hub that starts again reads the index, then each session's record and transcript; no index is no session, a record that is missing or does not read leaves its session out, and a transcript that is missing is empty. It then finds their containers: it follows Docker's events for its label before it lists the containers that carry it, so nothing that happens to one falls between the two; it reads only what each record says and what Docker lists, never when either was written. A container a record names, starting or awake, that runs is adopted: the transcript notes its run started unless it does already, so it counts the run's output from the start, and the hub re-attaches to it and reads what it missed from its logs. One a record names that does not run is noted lost and removed, and the session left hibernating once it is gone; a record whose container is not listed leaves its session hibernating, noted lost. Each container carrying its label that no record names is reported, never removed. A list Docker fails, or does not answer, fails the hub before any session is noted or any record written: which sessions still run is unknown, so every record is left as it is, and the hub, restarted by its service, lists again. Asks that come while it does wait for it.
- **The transcript is the hub's own record,** not Claude Code's session file, which is Claude Code's format and may change. The hub keeps every event, numbered in order within its session from 1, and appended to the session's transcript as it comes, so a read after a restart goes on from the same numbers: each line of the container's stdout, as Claude's event when it is JSON; each line of its stderr; each line written to it, tagged with who said it, a caller of the hub's tools or the hub itself, and later the engine; each interrupt; and what the hub did with the container. A turn Claude starts by itself, as a background subagent finishes, is recorded as any other.

### The link carries chat for trusted engines

`REVISION` is raised, and the link gains frames. The hub's `Engine` actor adds the engine's id to what it forwards, so a frame names no engine and none can claim to be another.

| Up (engine → hub) | Means |
|---|---|
| `Say { session, text }` | a line typed in chat mode |
| `Ran { session, line, printed }` | a command the owner ran here in `!` mode, with `session`'s tab open, and what it printed |
| `Answer { ask, allow }` | an approval answered |
| `Interrupt { session }` | cancel the session's running turn; the session carries on |
| `Hibernate { session }` / `Wake { session }` | hibernate the session, or wake it |
| `Open { session, after }` / `Close { session }` | the engine follows the session's events from event `after`, or stops following them |
| `New { name }` / `Archive { session }` | a session made, or archived |

| Down (hub → engine) | Means |
|---|---|
| `Sessions { list, now }` | every session: its name, state, its container's state, its last activity, and how many of its asks wait, sent whole on every change, with the hub's time as it was written |
| `Show { session, events }` | events from the transcript, the backlog first, then each as it comes |
| `Ask { ask, session, what }` | something in `session` waits for the owner's answer |
| `Declined { chat, why }` | a chat frame of this engine's that the hub could not do, and why |

- **The engine sends only what its owner did.** Everything about the engine that Claude needs, a frame, a log, its stats, Claude asks for through the tools that already cross the link. Nothing is pushed up unasked.
- **The list is sent whole.** It is a few dozen entries at most, which is cheaper than tracking what changed, as `Sheets` is.
- **Events are numbered within their session.** `Open { after }` returns every event after `after`, so an engine opens a tab from the last event of it that it holds, from the start when it holds none, and the hub sends it each event once. The engine keeps every event of each tab it has opened, closed or not, and its console builds only the rows in view, so scrolling back reads earlier events from what the engine holds, never again from the hub: the link has no bound below which events are not sent, and a tab opened from the latest would lose its backlog.
- **Kept by each engine for itself,** and never sent: which sessions it shows as tabs, their order, which tab is open, where each is scrolled, a line half typed, and how tall its console is.
- **In the engine, `Link` hands the chat on.** An actor of the engine tells `Link` it would `Listen`, and is shown the session list and the asks that wait as they stand, then each `Sessions`, `Show`, and `Ask` as it comes, as the sessions' `ShowSessions`, `ShowEvents`, `ShowAsk`, and `ShowDeclined`; it tells `Link` the sessions' `Chat` its owner did, which `Link` writes up as its frame, and one too large for a frame is logged and not written. Each row's last activity is a time on the hub's clock, and two engines' clocks are their own (ADR-0041), so `Link` puts each on its own clock, as long before its own time as it was before the frame's `now`. `Link` keeps the list and the asks it was shown, letting an ask go once its session waits on none, so an actor that listens late is shown them. An untrusted engine is shown nothing, so its listeners hear nothing.
- **The overlay's chat crosses to `Link` through a root of its own,** `ChatRelay` (`aethereal-overlay`), which depends on the overlay and `Link` both, so the overlay depends on no link (ADR-0059). A program with both lists it after them; one with no link lists none. As it begins it tells the overlay it `Relays` the chat, and `Listen`s to `Link`; it tells the overlay what `Link` shows it, and `Link` the `Chat` the overlay tells it, taking each only from the actor whose it is. The overlay keeps the actor that told it `Relays` and tells it the chat; until one does, its console shows no chat and sends none, as an engine with no link keeps the console as it was.
- **`REVISION` is 6.** The chat's vocabulary is the sessions capability's (`aethereal-sessions`: `Chat`, `SessionRow`, and the transcript's `Numbered` events), which the link's frames carry, so the link's crate depends on it.
- **A trusted engine joins the sessions as it links.** Neither `Engines` nor an `Engine` depends on the sessions (ADR-0059): a hub that runs them lists `ChatToSessions` (`aethereal-link`) after `Engines` and `Sessions`, which depends on both. As it begins it asks `Engines` to `HearTrusted`, and `Engines` tells it each engine the hub trusts as a `TrustedEngine`, a reference to its `Engine`: every one linked trusted already, as it asks, so an engine trusted before it hears reaches the sessions all the same, and each after, once its token is taken. It tells each such `Engine` `ChatTo` the sessions, and steps aside. An `Engine` keeps each place it is told its chat goes, and once `Engines` answers that its token was the owner's, or at once when it is told a place after that, it tells each that it `Joined` as its engine, from its own actor; `Sessions` takes the sender itself as that engine and watches it, refusing a sender that names an engine another actor joined as, or that joined as another engine already; each chat frame after is told to the same places as `Chatted { engine, chat }`, from the same actor, which `Sessions` takes only from the actor that joined as that engine. So `ChatToSessions` hands over a reference and nothing more: no engine speaks through it, none speaks as another, and an `Engine` that any actor tells `ChatTo` joins and chats only once the hub trusts it. `Sessions` shows a joined engine the session list at once, and each ask that waits, as `ShowSessions`, `ShowEvents`, `ShowAsk`, and `ShowDeclined`, which its `Engine` writes down as `Sessions`, `Show`, `Ask`, and `Declined`.
- **What is shown is worked out as each turn of `Sessions` flushes,** so nothing that changes the list or a transcript goes unshown: the list, each row a session's name, state, its container's state, when its transcript last grew, and how many of its asks wait, is sent whole when any row changed; and for each session an engine follows, every event after the last shown, 32 to a `ShowEvents`. Its `Engine` writes as many events to a `Show` frame as fit in one, halving what does not fit; an event too large for any frame, which a long tool output can be, is left out and logged, and `read_session` still reads it.
- **An ask is Claude Code's `can_use_tool` control request,** the one thing print mode asks its host to answer: `{"type":"control_request","request_id":…,"request":{"subtype":"can_use_tool","tool_name":…,"input":…}}`. `Sessions` numbers it, keeps its request's id and input, and shows it to every joined engine as `Ask`, its `what` the tool's name and input; an `Answer` writes the control response Claude Code reads, `{"behavior":"allow","updatedInput":<input>}` or `{"behavior":"deny",…}`, and notes it in the transcript, by its engine. An ask answered already is passed over, and the asks of a container that is removed go with it. Claude Code sends such a request only when it is started with `--permission-prompt-tool stdio` and without `--dangerously-skip-permissions`, and every session is started with `--dangerously-skip-permissions`, as the container is the sandbox: so today nothing raises an ask, and the frames are there for the session that is started to ask, which is not settled.
- **A chat frame that cannot be done is declined to the engine that sent it,** as `Declined`, with the refusal the hub's tools would answer: a `New`, a `Wake`, or a `Say` that would wake a session, past the cap, names the awake sessions; and a `Hibernate` of a session `Working`, `Waiting`, or `Compacting` says which. The overlay prints it in the console's open tab. Nothing else comes back: the engine sees the list as it stands.

### Trusted and untrusted engines

- **An engine the owner starts is trusted.** An engine a session spawns or mints a token for is untrusted. The hub decides when the engine links, from who asked for its token or its spawn, and records it on the engine's `Engine` actor. The engine never says what it is.
- **Each session reaches the hub's tools by a route of its own,** so the hub tells a session's `mint_token` and `spawn_engine` from the owner's. The route is a second port, bound where containers reach it and named only to sessions, on which every request bears a bearer the hub mints for its session and gives its container in its environment, as it gives the credential: the bearer names the session, and a request with none or another is refused. The owner's port stays on the loopback, which a container on a network of its own does not reach.
  - **The hub's two ports are two stacks of its program** (ADR-0035), each an actor type of `aethereal-hub`'s that owns its port, named for who connects to it: `LocalStack` on 8890, for this machine's programs, bound on the loopback whatever `Tcp`'s interface or its section says (`local_stack.port`), and `ContainerStack` on 8893, for the session containers, bound on the gateway of Docker's default bridge (`172.17.0.1`) unless set otherwise (`container_stack.port`, `container_stack.interface`). Each is set in its own section, as a stack's settings suggest no flags, which the two sections would both suggest (ADR-0035). `aethereal-hub` is the one place that names `Mcp` and `Sessions` together, so the stacks are defined there. Each lists its stages as one tuple of types ending in `McpRoutes`, `aethereal-mcp`'s one route, `POST /mcp` to `Mcp`, and attaches the principal `Caller` (`aethereal-tools`: `Caller::Owner`, or `Caller::Session { session }`) in the stages before it:

    ```
    LocalStack      127.0.0.1:8890    Layers<(MarkOwner, McpRoutes)>    MarkOwner, pure, attaches Caller::Owner      ─▶ POST /mcp ─▶ Mcp
    ContainerStack  172.17.0.1:8893   Layers<(Sessions, ContainerRoutes)>  Sessions, asked Inbound<()>, attaches Caller ─▶ POST /mcp ─▶ Mcp
                                                                                                                 └▶ /git/… ─▶ Git
    ```

    `LocalStack` failing to bind fails the boot, and the hub does not start; `ContainerStack` failing to bind is logged, and the owner's port is served without it. `ContainerStack`'s last stage is the hub's routes type, `ContainerRoutes`: `POST /mcp` to `Mcp`, and git's three routes to `Git`, behind the same stage (see Code reaches a session through the hub's repository, below).
  - **`Mcp` routes tool calls, and nothing else.** It serves no port, holds no bearer, and names no scheme: it takes `Request<Caller, ()>` only from a stack (ADR-0035: `FromStack`; ADR-0058). Each call it forwards names its caller, the principal its request came with (`Call::caller`), which no caller writes, as no tool's input names one; `EngineTools` asks `Engines` for a token or a spawn for that caller (`MintFor`, `SpawnFor`).
  - **`Sessions` answers who a bearer is.** It mints each container's bearer, so it is `ContainerStack`'s authenticator, an actor layer: it handles `Inbound<()>`, takes it only from a stack, and answers `Inward<Caller>`. A request whose credentials name the bearer of a session's live container, as `Bearer <32 hex digits>` or as the password of `Basic` credentials of any user, is passed as that session; any other is answered with a challenge, `Basic` and the realm `aethereal`, which git's credential helper answers with `Basic`, so a session's git carries the bearer too. Every bearer held is compared, in a time that does not hang on where they differ. A registry actor that `Sessions` told of each bearer would serve as well, listed in the stack's layers in its place; `Sessions` already holds them. On the way out it is asked `Outbound`, as every actor layer is, and answers `Outward::Pass` with the head unchanged; it lists no body part (ADR-0035: `InboundPart`, `OutboundPart`), so a body passes it untouched.
  - **The bearer is 16 bytes of the host's randomness,** drawn by `Sessions` for each container of a session and given to it as `AETHEREAL_HUB_BEARER`. `Sessions` keeps it, in memory, as the bearer of the session's container from before it asks for the container, which takes the place of the session's bearer before, and lets go of it once the container is removed; it tells no other actor of it. Claude Code's MCP config for the route names the variable, `"Authorization": "Bearer ${AETHEREAL_HUB_BEARER}"`, which Claude Code expands from its environment, so the bearer is never an argument of the container's command, which every process list and `docker inspect` show. The bearer is a secret, kept as the credential is: it is never a setting, an argument, a log line, a record, or a value of a tool's answer, and it crosses the engine only as the provisioning job's answer and the `Create`, and, as the container presents it, in the `Inbound` `ContainerStack` asks, each `Debug` written without it.
  - **A hub that restarts holds no bearer.** A container that outlived it bears one the new hub never minted, so its calls are refused until it next hibernates and wakes; the bearer is never written down for a restart to read, as a record would keep a secret.
  - **A container joins Docker's default bridge,** a network of its own, and reaches the route at `sessions.hub_url`, `http://172.17.0.1:8893/mcp` unless set otherwise.
  - **The session tools are the owner's.** A session's call of `new_session`, `message_session`, `read_session`, `list_sessions`, `interrupt_session`, `hibernate_session`, `wake_session`, or `archive_session` is refused: a session that drove another would be the pipeline of sessions this hub is not built for (see Alternatives).
- **An untrusted engine keeps the link as it is:** it lists its tools and answers the hub's calls, which is everything a session needs to test it. Every chat frame from it is dropped and logged, and none is sent to it. Its overlay shows no chat.
- **Trust is the hub's to decide.** `Engines` keeps who asked for each token and each spawn beside it, and answers the `Engine` that takes it whether its engine is trusted (`TokenFor::External { trust }`, `TokenFor::Spawned { trust }`), which the `Engine` keeps; `list_engines` shows each engine's `trust`.
- **A session reaches only the engines it started.** The hub's tools that take an engine, `describe_engine`, `call_tool`, and `terminate_engine`, reach an engine for a session only when its trust is `Untrusted { session }` naming that session (`Trust::reachable_by`). Before such a call reaches the engine, `EngineTools` asks `Engines` the engine's trust (`TrustOf`, answered `EngineTrust`), and refuses the call of any other engine, saying a session reaches only the engines it started and that `list_engines` lists them. The owner's engines, another session's, and an id no engine is linked under are refused alike, so a refusal never tells a session which engines the owner runs. What is checked is what is reached: an engine's id is never given twice, and its trust is fixed as it links. A session's `list_engines` lists only the engines it started, and among the spawned engines that ended only the ones it asked for, as each ended engine is listed with the trust it was spawned with. `mint_token` and `spawn_engine` stay a session's, as what they start is its own. The owner's calls reach every engine, and are not checked.
  - **Only its own, not any untrusted engine,** because the trust already names the session that started each engine, and sessions are separate tasks: one session's engine runs code that session is midway through testing, and another session that drove it, captured it, or terminated it would act on work it does not know, the pipeline of sessions the session tools are refused for.
  - **The owner's engines are hidden from a session's list, not only refused,** because a session can do nothing with an engine it cannot reach, and what the list shows of one, its name and tools, and of an owner's spawn that ended, its stderr, is the owner's.
- **An untrusted engine is not kept from the owner's clipboard, and the hub does not pretend to.** An engine a session spawned runs code the session wrote, as the owner's own user in the owner's display session, so it can ask the compositor for the selection through any library or by speaking Wayland or X11 itself; a gate in the engine's own code or settings, such as `ReadClipboard` answering `Refused`, would hold only for builds that keep it, which is no hold against the code it is there to stop, and would read as one. Nothing the hub does at a spawn holds either: the engine finds the display's socket without being told, and could not open a window to be tested without it. What does keep it from the clipboard is running untrusted engines outside the owner's display session, as another user or in a nested display of their own, which is not built (see Open questions). Until then, the hub's tools reach only the engines a session started, but those engines run in the owner's display session all the same, so the owner's clipboard is as open to a session's engines as to any program the owner runs, and nothing the overlay pastes reaches an untrusted engine, which shows no chat.
- **Why:** a work engine runs code a session has just written, its link included. A half-made build that sent a line every frame, resent an old `Answer`, or let one session's text reach another as if typed, would act on real sessions. Only the hub's check holds against code the engine runs.

### Code reaches a session through the hub's repository

- **The hub keeps one bare repository, the monorepo, and serves it on the sessions' port over git's smart HTTP.** A session fetches all of it, and pushes only branches under its own name, `sessions/<n>/`; the owner moves `main` themselves, over ssh. The owner's port has no git route.
- **`Git`, a root of a crate of its own, `aethereal-git`, serves it:** a handler of a stack (ADR-0035), shipped with the hook every push runs. The container stack's routes type, `ContainerRoutes`, routes `GET /git/info/refs`, `POST /git/git-upload-pack`, and `POST /git/git-receive-pack` to `Git`, beside `POST /mcp` to `Mcp`. Every route is behind `Sessions`, so a request without a live session's bearer is challenged before its body is read, and no program runs for it. `Git` takes `info/refs` only for `service=git-upload-pack` or `service=git-receive-pack`: git's dumb protocol, which reads the repository's files as they lie, is not served (`403`), and nor is a request on the owner's behalf, which no route of the sessions' port brings.
- **The hub makes the repository as it starts.** As `Git` begins it asks `Processes` to run `git init --bare --initial-branch=main` on its setting `git.repository`, which leaves a repository already there as it is, then checks that the hook is in place, a file git can run in `git.hooks`: git runs no hook it does not find, and would take every push. Until both have exited well, every git request is answered `503`. If either fails, `Git` logs why and answers every git request `503` from then on, and the hub serves on, as a `ContainerStack` that cannot bind leaves the owner's port served. The settings, the section `git`, are the repository, git's program, the hooks' directory, an absolute path as git reads a relative one from the repository, and `most_running`.
- **Each request runs `git http-backend` through `Processes`** (ADR-0040), its stdin and stdout connected, `most_running` at once (8 by default), past which a request is `503`. Requests are independent: git's own ref locks order two pushes. The program sees only the environment `Git` states (`Environment::Only`):
  - CGI's variables, named from what `Git` read the request as, never as sent: `REQUEST_METHOD`, `PATH_INFO`, and `QUERY_STRING`; and from the request's headers, `CONTENT_TYPE`, which the program checks, `HTTP_CONTENT_ENCODING`, as git's client gzips a large fetch's request, and `GIT_PROTOCOL`, from `Git-Protocol`, without which it is spoken version 0;
  - `REMOTE_USER`, `session-<n>`, from the `Caller` `Sessions` attached: who the hook lets push, and without which `git http-backend` takes no push;
  - `GIT_PROJECT_ROOT`, the repository, and `GIT_HTTP_EXPORT_ALL`, so it is served with no marker file;
  - `PATH`, where a git named by its name alone is found, and the programs its hook runs;
  - `GIT_CONFIG_NOSYSTEM` and `GIT_CONFIG_GLOBAL=/dev/null`, so no configuration of the machine's or of a user's changes what it does;
  - `core.hooksPath`, `git.hooks`, through `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`, and `GIT_CONFIG_VALUE_0`, configuration on the command line's level, above the repository's own, so the hook is the hub's and nothing in the repository chooses it.
- **The request's body streams into the program's stdin as it arrives,** read through `BodyHandle::read` and written one write at a time, each part's credit granted back once its write is sent, so the client is held to what the program has taken; at its end, stdin is finished. **The program's stdout is read up to the end of its CGI head**, its `Status` the response's status, `200` when it names none, and the request is answered once its body is written whole, or once the program's stdout has ended, as the stack cuts a body its handler answers before its end. The response's body is `Streamed` from `Git`, of a length not known, each part of stdout sent as the stack grants credit and granted back to the program's pipe only then, so a client that stops reading holds the program back. A stack that does not open the body within a minute closed its connection before the answer came, and the program is stopped.
- **A request or a response that ends early stops the program:** a client that stops reading (`Enough`), a body that does not come whole, or a stack that ends. A program whose stdout ends before its head does is answered `502`; once its head is written, one that does not close its stdout and then exit well ends the body `Failed`, which the client sees cut short.
- **A session works in a clone of the repository that outlives its containers.** Its work tree is at `/session/home/work`, on its home volume, so it survives hibernation, a lost container, and a reboot, and no work is ever lost. Its working directory stays `/session/home`, as Claude Code keys a conversation by its working directory, and `--resume` finds it there. The code reaches it only by a clone over the route, never through a mount.
- **The start script readies the tree before Claude Code starts.** It is the container's command, a POSIX `sh` script of the image run with `set -eu`, and once its bootstrap succeeds it `exec`s Claude Code. With no `AETHEREAL_GIT_URL`, the hub serves no repository, and it readies no tree. Otherwise:
  - it writes git's author and committer, `session <n>` at `session-<n>@aethereal.invalid`, an address that resolves nowhere, so every commit says which session made it;
  - it checks that the credential helper answers for the repository's URL, dropping what it answers;
  - when nothing is at `/session/home/work`, it clones the repository there; when something is, it points its `origin` at the URL, which is a setting and may move, and runs `git fetch origin`, which updates only the remote-tracking refs: it never resets, checks out, merges, or rebases, so it changes no file of the tree and loses no uncommitted work.
- **Bootstrap is all or nothing.** Each step runs within `AETHEREAL_BOOTSTRAP_SECS`, `bootstrap_secs`, 5 minutes by default, and one that fails or runs past it ends the container: the script prints why to stderr, which the transcript keeps, and exits with a code of its own, `78`, sysexits' `EX_CONFIG`. Claude Code never starts, nothing carries on half set up, and the container does not try to recover.
- **A failed bootstrap is a failed start, not a lost container.** When a run ends with `78`, the hub removes its container, notes in the transcript that the run's bootstrap failed, with the code, and leaves the session hibernating with no container, never `Lost`, so a failed start never reads as lost work and never brings the lost-wake line. Waking it runs the whole bootstrap again. The hub answers a waker once the container is attached, as it does any start, so a failed bootstrap then shows as the session hibernating, with its note. Every other exit is a lost container, as before. A hub that comes back to a container that has already ended reads only that it does not run, and notes it lost.
- **git reaches the hub with the session's bearer, and never stores it.** The image's system config names one credential helper, `git-credential-aethereal`, which answers git's `Basic` challenge for the repository's URL alone, user `session` and password `AETHEREAL_HUB_BEARER`, read from the environment as git asks, and answers nothing for any other place, so the bearer goes nowhere but the hub. The bearer is new for each container, so nothing written to disk would last anyway. The URL is the setting `git_url`, `http://172.17.0.1:8893/git` unless set otherwise, the sessions' port's `/git`, given as a variable, so neither the script nor the prompt spells out an address.
- **A session pushes its own branches, and its work in progress before it hibernates.** Its branches are `sessions/$AETHEREAL_SESSION/…`, each named for what it holds; the hook refuses any other ref. Uncommitted work survives hibernation, but the owner sees only what is pushed, so the wind-down's notice tells it to commit and push its work in progress first.
- **The hook** is `crates/aethereal-git/hooks/pre-receive`, a short POSIX `sh` script, copied to `git.hooks` as the hub is deployed. It refuses the whole push unless every ref it updates is under `refs/heads/sessions/<n>/`, `<n>` the session `REMOTE_USER` names: a session creates, moves, force-moves, and deletes its own branches, and `main`, tags, and another session's branches are refused, each with a line git prints to the pusher naming the ref and the rule.

### The console is the chat

- **One stream per session, in every engine that shows it.** Lines from every engine, Claude's answers, and commands the owner ran are interleaved in order. Claude reads each of the owner's lines tagged with its engine's id, `[37]`; the console shows it after who typed it and a prompt mark: `local > what do you see?` for a line typed at the engine showing it, once it knows its own id, and `rapid-owl > what do you see?` for one typed at another, the tag in a label's colour of its own so it never reads as part of the line, on a shade a step lighter than the transcript, so the owner's turns stand apart from Claude's as a prompt's lines do in a terminal. An engine's name is made from its id alone, so every engine calls one engine alike (`engine_name`): the id is mixed by a fixed 32-bit hash, whose top six bits pick an adjective of a fixed list of 64 and the next six a noun of another, and where an engine is named in output, tools, or documentation the id follows, `rapid-owl:37`, so two engines whose words fall alike are still told apart; a transcript's tag shows the words alone (`engine_words`), keeping the id out of the conversation's view. Once an engine knows its own id, its own name stands at the start of the tab strip, a label in `label`'s ink and not a tab, set apart from the console's tab by the break's room, and the pointer resting on the `local` tag of its own lines shows `local · brisk-thresh · engine 5`, the one place in the chat its id shows; until then neither shows. Both are the engine's own and never sent. Changing either list, its order, or the hash renames every engine. An engine shows its own lines fully and others' dimmed; it filters nothing, since Claude saw one conversation. No frame names an engine its own id, so an engine learns it from the transcript: the first line said or run at an engine whose text is the oldest the engine sent that session and has not seen come back is its own, and that engine's id is its. Until then no line is shown as its own.
- **One flow: an engine command looks the same in every tab.** Each tab's prompt is in one of two modes, shown as its mark: chat mode, `>`, and `!` mode, `!`, as Claude Code's own bash mode is entered.
  - **`!` is a mode, not part of the line.** In a session's tab, `!` typed on an empty line puts the tab in `!` mode: the `!` is not typed, and the mark becomes `!`. The mode stays across lines until Backspace on an empty line returns the tab to chat mode. Each tab keeps its own mode, the engine's own and never sent.
  - **The console's own tab is always in `!` mode,** marked `!`, and cannot leave it. A command there runs, as ADR-0053 reads it, and is sent nowhere.
  - **In `!` mode in a session's tab, every command runs here and is sent to the session.** It runs the engine's own tool at once, during a turn or not, and never waits on Claude; what it prints shows under it. The engine then sends it as `Ran`, naming the session whose tab is open, and the hub notes it in the transcript and writes it to the session as a line of its own, which starts a turn, as a `!` command in Claude Code does: tagged with its engine and marked, `[37] !capture`, then what it printed on the lines after it. The chat's words are commands as any other: one rule, so they are sent too. An image an answer brings is sent as the one line of text the console prints of it.
  - **In chat mode, a line is said to Claude, and a `/` line is Claude Code's.** Every line goes as `Say`, and Claude reads it tagged with its engine, `[37] what do you see?`. A line that starts with `/` passes whole to Claude Code, which reads a command only as a whole message, so the hub writes it alone and untagged.
  - **`clear` is the console's, `/clear` Claude Code's.** `clear` in `!` mode clears the console's scrollback, the engine's own; a session's transcript is the hub's record and is never cleared. `/clear` in chat mode starts Claude Code's conversation afresh: it answers with a `conversation_reset` event, which the transcript shows as a divider, as it does a compaction, keeping every event before it.
- **The chat's words are the engine's tools** (ADR-0053: Commands are tools), each a verb and its noun, never a bare common word: `new_session <name>` makes a session, which joins this engine's tabs and opens once the hub lists it; `interrupt_session [session]` cancels the running turn of the session named, or of the one whose tab is open, and the session carries on; `hibernate_session [session]` and `wake_session [session]` hibernate and wake it; and `archive_session [session]` archives it. A session is named by its tab's name. The overlay's tools' worker serves them, and the overlay offers them with it to the engine's tools root the first time the hub lists the sessions, so only an engine the hub trusts has them; the worker asks the overlay, whose chat they change, for each, and answers once the overlay has told the link or said why not, and from then they run from any tab, `help` lists them, and Tab completes them, as every command does. Typed in a session's tab in `!` mode, they run here and are sent as `Ran`, as any command is. A call of them a session makes is refused: the sessions are the owner's.
- **The overlay's words and the hub's tools reach the same asks.** The overlay's own tools are the five above, each sent up the link as its frame (`New`, `Interrupt`, `Hibernate`, `Wake`, `Archive`). The hub serves the same five, by the same names, in its own toolbox for its MCP caller, with three more beside them: `message_session`, `read_session`, and `list_sessions`, which the overlay does by typing a line, by opening a tab, and with its session list. Both reach the same asks of `Sessions`, and are refused alike.
- **Esc interrupts.** With the prompt line empty in chat mode, Esc, or `interrupt_session`, sends `Interrupt`, and the hub writes the interrupt control request to the session's stdin. With text in the prompt line, Esc clears it first; on an empty line in `!` mode, it returns the tab to chat mode. All hold with a session's tab open; with the console's own open, Esc closes the console, as it did before the chat.
- **Lines sent during a turn go in at once,** and Claude Code queues them itself, answering an interrupt with what it still holds (`still_queued`). The transcript records each where it was said, so it reads in the order the owner typed.
- **A turn may start with no line,** when a background subagent finishes. The hub records it as any turn, and the tab shows it working.
- **Compaction shows, and loses nothing.** A `compact_boundary` event becomes a divider in the transcript with its token counts. The hub lists the session `Compacting` from Claude Code's `status` of compacting until its `compact_boundary`, another status, or the end of its turn, whoever asked for it: the wind-down, the owner's `/compact`, or Claude Code itself as its context fills. So the tab's icon reads the hub's row alone, as every other state does. The transcript keeps every event before it.
- **Subagents fold.** Events carrying `parent_tool_use_id` are shown under the tool call that started their subagent, closed until opened.
- **An ask shows above the prompt line,** for the session whose tab is open, with what it asks and a button to allow it and one to deny it, which send `Answer`; it is let go once answered there, or once the list counts no ask of its session that waits. The band counts the sessions that wait on the owner.
- **The console drops down from the top, as it does now,** grown to hold the transcript. The prompt line is at its bottom edge and the tabs under it, nearest the scene; a session waiting on the owner shows on the band too. The console's own tab is the first, the engine's scrollback, where every line runs here as ADR-0053 reads it; the session tabs this engine shows follow it. A break, a firm line, parts the console's own tab from the sessions', and a light line parts each session's from the next, each a line of text tall and centred against the tabs' titles. Control-Tab opens the next tab and Control-Shift-Tab the one before, round from the last to the first, and Alt with a digit from 1 to 9 opens the tab at that place, Alt-1 the console's own, while the digit alone still types. Until the hub lists the sessions, which it never does to an untrusted engine, no session tabs show and the console is what it was. The console's height is set by dragging the line between it and the band, and kept per engine.
- **Each engine keeps its own tabs.**
  - Which sessions an engine shows, their order, and which is open are its own, never sent, and not kept past its restart.
  - An engine shows only the sessions it chose. A session made at it with `new_session` joins its tabs, at the end; one made elsewhere, at another engine or through the hub's tools, appears in the session list, not as a tab.
  - A tab is dragged along the strip to reorder it.
  - Closing a tab hides it from this engine: the engine stops following it (`Close`), the session carries on, and every other engine's tabs are untouched.
  - **The session list** shows every session the hub holds, awake, hibernating, or archived, each with its status and its last activity. Choosing one opens it as a tab here, which is how a hidden session comes back; an archived one opens to be read, with no prompt line.
  - An engine is told at launch which sessions to open with, by name and in order, in the overlay's setting `sessions`, given as every setting is (ADR-0028); a name the hub does not list is skipped and noted in the console's own tab.
- **Each session tab shows its status as an icon:** starting, idle, working, compacting, waiting, hibernating, or lost (ADR-0053: Colours). It is the session's state, except while its container is starting or lost, which the icon shows instead.
- **The console is a sheet under the band.** The band is a see-through HUD over the scene; the console's panels are nearly opaque, and the line between the two, its grip, is a firm seam twice a divider's width across a dark well, so the band's graphs never read as the console's text. A gap between them would show the scene, which changes with every program, so the console's edge would read only as well as the scene behind it allows.

## Consequences

- **The owner works from an engine:** one engine they sit in, sessions in its console, and work engines that sessions spawn, restart, and test without ever restarting the owner's.
- **Sessions are contained.** A session's files, builds, and processes stay in its container and its home's volume, its share of the build host is capped, and two sessions never write the same tree.
- **The hub is the one place sessions live.** A hub restart costs no turn, and an engine restart costs nothing. A session lives as long as its record: hibernating costs it a compaction and a resume, and nothing but archiving ends it.
- **New crates and crate code:** the Unix transport, the HTTP client in `aethereal-http`, `Files`' append, the sessions capability, `aethereal-sessions`, with its Docker client, and session tools in the hub's toolbox (`new_session`, `message_session`, `read_session`, `list_sessions`, `interrupt_session`, `hibernate_session`, `wake_session`, `archive_session`) so sessions are used and tested before the overlay has a chat; and the git capability, `aethereal-git`, its hook, and the CGI head a handler reads in `aethereal-http`.
- **The link's revision changes,** so an old engine and a new hub refuse each other at `Hello`.
- **The widget library has gaps the chat needs:** a text input of several lines, a clipboard (which the window does not have), markdown turned into widgets, images inline in the transcript, a scroll that stays cheap over a long transcript (the library's draw stage), and a surface for approvals.
- **The build host's Docker keeps its data, the sessions' home volumes among it, on a disk other than the system disk,** before sessions run.
- **Each session is told where it is:** the capability appends a short prompt, the setting `prompt`, which defaults to `crates/aethereal-sessions/image/prompt.txt`, beside the image's Dockerfile. It says the session runs in a container for the owner's engine work, with its home at `/session/home`; that it hibernates when idle, after a notice, and wakes with its conversation resumed, and should write down its loose threads when told; that lines come from the hub as well as the owner; that its work tree is at `/session/home/work`, whose remote `origin` is the hub's repository, fetched at each start; that it may push only branches under `sessions/<n>/`, never `main`, tags, or another session's branches, which the hub refuses anyway; that uncommitted work survives hibernation but the owner sees only what is pushed, so it pushes its work in progress when told it will hibernate; and that it keeps heavy builds bounded. With the sessions' route it says that the hub's tools are how it spawns and tests engines, that a build reaches the store through `/session/drop`, and that it never changes the owner's own engine or its window. With the trusted engines' chat it says what `[37]` means: the owner's line typed at engine 37, or a command run there.
- **Order of work:**
  - A, the hub: the Unix transport; the HTTP client; the Docker client; `Sessions` and its tools; the session image, which holds the volumes' directories owned by the session's user, with the shared cargo home, each session's target directory, and the prompt.
  - The sessions' own route to the hub's tools comes with the trusted engines, in B.
  - B, the engine: the library's draw stage; text editing and the clipboard; markdown and images; the link's chat frames and trusted engines (after `Sessions`); the overlay's chat (last).

## Open questions

- **Beyond the hub's repository.** Spokes, pushing to GitHub or a public split, landing to `main` beyond the owner's ssh, review, and the build queue are not settled.
- **One image or one per project.** The session image is aethereal's, in its own repository. Whether another project's sessions get an image of their own, from a Dockerfile in that project, is not yet decided.
- **The Desktop app.** Reaching a container session from Claude's desktop app is on hold, as is Claude sending the owner a message at whichever engine they are at.
- **Untrusted engines outside the owner's display.** An engine a session spawns shares the owner's user and display session, and with them the owner's clipboard, input, and screen. Running it as another user, or in a nested display the hub owns and captures, would keep it from them; how a window is then tested, and seen by the owner when they want to, is not decided.

## Alternatives considered

- **The Anthropic API, with the hub running the agent loop:** the hub would own every step, but the owner works on a subscription, and the API is billed apart.
- **The engine running `claude` itself, through `Processes`:** the session would end with the engine, every engine would need Claude Code and a credential, and several engines could not share one conversation.
- **One session per engine:** engines come and go, a conversation spanning engines would be cut, and every session costs its own context on the subscription.
- **Hibernating the least recently used session to make room past the cap:** a wake would never be refused, but a session the owner left warm on purpose would be compacted under them. The refusal names the awake sessions, and the owner chooses.
- **Every trusted engine showing every session as a tab:** with long-standing sessions, archived ones, and sessions made through the hub's tools, every console would fill with tabs the owner is not working in there.
- **`claude -p` directly on the build host, no container:** simpler, but sessions would share one tree and the whole machine, and each command would need the owner's approval rather than the few that leave the container.
- **A container per turn:** nothing to keep alive, but a build or a background subagent left running would die at the turn's end.
- **The `docker` command through `Processes` with pipes:** works, but a hub restart closes the pipe and stops the container's process, and every answer is printed text to parse. The API gives structured state and an event stream, and leaves the pipes with Docker.
- **Docker's API on a TCP port:** anyone who reaches the port controls the build host.
- **A relay inside the container listening on a socket on the mount:** a program to write and keep, for what attach and logs already do.
- **Named pipes on the mount:** `claude` exits when the last writer closes, and is killed writing to a pipe with no reader, so the hub's restart ends the session.
- **The overlay calling the hub's MCP server for chat:** each engine would need an MCP client, a second connection, and a second credential, where the link already proves which engine it is.
- **Engines pushing captures and scene state to the hub:** it duplicates tools Claude can already call, and sends what nobody asked for.
- **Filtering each engine's view to its own lines:** Claude saw one conversation, and answers about another engine's command would arrive with nothing they refer to.
- **Several people on one hub:** one person's subscription cannot serve others, and serving several would mean API keys, owners on sessions, and sharing. It is a redesign if it is ever wanted, and nothing here is built for it.
- **A session that starts other sessions, each in its own container:** the shape of an autonomous pipeline, out of scope; a session's subagents run in its own container.
